# S4：纯 TS/WASM 材质图像管线

**结论：通过。** 不用 sharp/libvips，只用 Node 内置的 `node:zlib`、`node:crypto`，纯 JS 的 pngjs，以及 WASM 版的 libwebp，就能完成材质的上传校验、规范化、hash、2D 头像、等距 3D 渲染和 WebP 输出：
- **正确性**：与 sharp 逐像素对照 49 组，差异为 0；另有 31 张黄金图做回归。
- **性能**：常见的 64×64 皮肤，整个上传流程约 1.4 ms，比 sharp 还快；高清图慢 2–3 倍，但只在上传时付一次。
- **依赖**：生产依赖里没有原生模块，也没有安装脚本。

还有一点：sharp 并不是完整的退路。它没有 3D 光栅化能力，3D 预览无论选哪条路都要用 JS 实现。

对应 ADR：`docs/adr/0008-zero-native-deps.md`。实施由 Codex 完成，验收、补充实验和取舍由主会话完成。完整的数据记录见 [REPORT.md](REPORT.md)。

## 运行

## 结果

### 1. 解码前必须自己把关，不能信任库

用 IHDR 声明 64×64、IDAT 却能解压出 200 MiB 的文件测试：
- 不加防护的 fast-png 峰值内存 672 MiB；
- 隔行（Adam7）版本让 pngjs 峰值达到 472 MiB；
- 只检查 IHDR 宽高也挡不住，因为宽高本身是合法的。

做法是先自己解析块并校验 CRC，再用 `node:zlib` 的 `inflateSync(…, { maxOutputLength: 精确预期长度 })` 解压，长度不符就拒绝。解码库只拿到 IHDR、PLTE、tRNS、IDAT、IEND 这几种块，其余块（tEXt、iCCP、eXIf、APNG 帧……）全部丢弃。

防护后的结果：
- 应当拒绝的 11 种输入都在约 2 ms 内被拒绝，内存没有上涨；
- 另外 4 种按设计接受，多余的数据被剥离：IEND 之后的尾随数据、附加元数据、解压后 200 MiB 的 iCCP、APNG（只取默认图像）；
- 30 种合法格式组合全部正确解码。

两个库的默认行为都不能直接用：
- **pngjs**：遇到 tRNS 时会把 RGB 一起清零；16 位转 8 位时四舍五入。游戏用的 stb_image 取高字节。所以要关掉库的缩放，自己做 `v >>> 8` 和透明色匹配。
- **fast-png**：低位深的 Adam7 有 6 种组合解错，默认也不校验 CRC。**不采用。**

### 2. hash：建议改为像素 hash（B）

对比了两种定义：
- **A**：`sha256(规范化后的 PNG 字节)`；
- **B**：`sha256(u32be(宽) ‖ u32be(高) ‖ RGBA8 像素)`。

同一组像素分别用 3 个编码器、4 个压缩级别编码，得到 9 个不同的 A，B 始终只有 1 个。11 张真实材质用两个解码库解码，B 全部一致。

A 取决于编码器和 zlib 的具体输出，Node 升级或换 CPU 架构都可能让它变化，变了就会导致同一张图被存两份、去重失效。B 只取决于像素。**建议新材质的 hash 采用 B。** 存储的文件仍是规范化后的 PNG，Minecraft 客户端只把 URL 里的 hash 当缓存键，不校验文件内容。

导入的旧材质保留 BS 原来的 hash（ADR-0006）。建议另存一列"像素 hash"：导入时对旧文件只读解码算出 B，这样旧材质和新上传的材质也能互相去重，同时不改动旧文件和旧 URL。

### 3. 渲染正确

- `avatar2d` 和 `preview2d` 与 sharp 的独立实现（extract + 最近邻缩放 + composite）比对：7 张皮肤 × 7 种输出，0 差异。
- 3D 没有独立的对照实现。依据是：UV 按 skinview3d 源码核对过，有朝向和遮挡的定向测试，主会话也逐张看过总览图，没有发现镜像或遮挡错误；slim 手臂宽 3，旧格式补全的左臂、左腿正常，HD 皮肤正常。
- 预处理与游戏客户端一致：64×32 转 64×64，基础层强制不透明，旧格式帽子层按客户端规则修正。这些修正只作用在渲染用的副本上，不改动存储的像素，alpha 为 0 的像素原有的 RGB 全部保留。
- 模型推断与 skinview-utils 的 `inferModelType` 等价（主会话已对照源码），7 张真实皮肤的推断结果与预期一致。

### 4. 性能（linux-arm64 Neoverse-N1，中位数，ms）

完整上传流程（防护、解码、校验、重新编码、两种 hash），Node 26：

| 输入 | 纯 TS | sharp |
|---|---|---|
| 64×32 真实皮肤 | 0.8 | 2.2 |
| 64×64 真实皮肤 | 1.4 | 2.4 |
| 512×256 HD 皮肤 | 36 | 22 |
| 1024×512 HD 披风 | 113 | 54 |
| 1024×1024 随机噪声（最坏情况） | 329 | 198 |

渲染。`render.ts` 是实施方的版本，热循环里逐像素分配内存；主会话用同样的算术重写了无分配版本（`perf-ceiling.ts`），42 项输出逐像素一致。下表是 Node 24 的数据：

| 任务 | `render.ts` | 无分配版本 |
|---|---|---|
| 2D 头像 512 | 18.5 | 0.8 |
| 3D 头像 512 | 81 | 34 |
| 全身 3D 512 | 34 | 19 |
| 3D 头像 128 + PNG 编码 | 6.2 | 4.9 |

编码：WASM 版 WebP 比 `node:zlib` 写的 PNG 编码器快 2–4 倍，体积小 42%（31 张代表性输出合计）。WASM 冷启动需要 13–19 ms，内存增加 3–8 MiB。

### 5. 打包

生产依赖只有 pngjs、@jsquash/webp、wasm-feature-detect，加上作为对照保留的 fast-png 及其依赖 fflate、iobuffer。扫描结果：`.node` 文件 0 个，`binding.gyp` 0 个，安装脚本 0 个。WASM 有标量版（281 KB）和 SIMD 版（346 KB），运行时检测 CPU 能力后选择。

## 移植进正式代码时的做法

1. **解码**：块解析、CRC 校验和有界解压由我们自己做（`png.ts` 的 `guard`）。
   - 反滤波和格式转换暂时交给 pngjs，同时显式处理 16 位和 tRNS。
   - 解压后的扫描行已经在手里，自己写反滤波大约 150 行，可以省掉 pngjs 的第二次解压。这在正式实现时再决定，pngjs 可以留作测试里的参照。
2. **上传大小**在 HTTP 读取请求体时就要限制，不能等到 Buffer 已经分配好。
3. **hash 用 B**，存储格式是规范化 PNG（只保留 IHDR、IDAT、IEND；编码参数固定，并记录管线版本）。
4. **WebP 作为可选的派生格式**。WASM 加载失败时回退到 PNG，不能因此阻断上传。
5. **上传、渲染、编码都放进 worker 池**。这些都是同步 CPU 运算，高清图会阻塞事件循环几百毫秒。sharp 的做法本质上也是这样，它在 libuv 线程池里运行。
   - worker 池要有队列上限和超时；
   - 渲染结果按 `(材质 hash, 输出类型, 模型, 尺寸, 渲染器版本)` 缓存，上传时预先生成常用尺寸；
   - 同一张图的并发请求合并成一个生成任务。
6. **渲染代码按无分配的方式写**：用类型化数组，热循环里不创建对象。`perf-ceiling.ts` 就是这样写的。

## 遗留风险

- 没有实测在 Windows、macOS 和 x64 上分发 ZIP 包。WASM 和纯 JS 理论上与平台无关，但要等发行流水线建好后在 CI 里验证。
- 3D 渲染没有和游戏内截图逐像素比对。相机角度和光照参数是暂定的，视觉方向确定后再调，黄金图随之更新。
- 只覆盖了列出的语料，不等于 PNG 解析器的安全证明。正式代码应该接入模糊测试（fuzz）。
- 与 sharp 的 0 差异是在这台机器的 libvips SIMD 舍入下得到的，其他架构上 sharp 的结果可能有 1 LSB 的差异。我们自己的算法输出是确定的。
