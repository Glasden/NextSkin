# S5：插件通过远程 Kysely 驱动访问自有表

**结论：可行。** 插件在独立进程里用 Kysely 正常写查询，驱动只把操作节点树发给核心。核心按白名单**重建**这棵树，把表名改写成带插件前缀的物理名，再用自己的方言编译器重新编译执行。

在 SQLite（node:sqlite）、PostgreSQL 17、MySQL 8.4 上，47 项端到端检查全部通过：
- 正常用法 10 项；
- 拒绝越权、注入和资源滥用 28 项；
- 回归用例 5 项；
- 事务、数据完好性、进程安全带、性能 4 项。

插件进程以 `node --permission` 启动，环境变量为空，读不到核心的文件和环境变量。

对应 ADR：`docs/adr/0010-plugin-api.md`（插件自有表），`docs/adr/0009-plugin-runtime.md`（plugin host）。

## 运行

```bash
npm ci
DB=sqlite npx tsx src/scenario.ts
DB=postgres PG_URL=postgres://... npx tsx src/scenario.ts
DB=mysql MYSQL_URL=mysql://... npx tsx src/scenario.ts
npx tsc -p tsconfig.json
```

| 文件 | 所在进程 | 内容 |
|---|---|---|
| `src/sanitize.ts` | 核心 | 节点树重建器，安全边界 |
| `src/gateway.ts` | 核心 | 请求网关：invocation、事务、执行 |
| `src/remote-dialect.ts` | 插件 | 不连库的 Kysely 方言 |
| `src/host.ts` | 插件 | plugin host 子进程入口（Node 原生类型剥离运行） |
| `src/test-plugin.ts` | 插件 | 测试插件：正常用法和攻击用例 |
| `src/scenario.ts` | 核心 | 启动子进程、执行全部检查 |

## 工作方式

1. 插件侧用核心实际方言的适配器和编译器构建查询，所以 `returning` 等能力判断与核心一致；驱动只发送 `compiledQuery.query`，插件编译出的 SQL 字符串被丢弃。
2. 核心为每次插件调用（迁移、拦截器、路由……）签发一个 invocation。DDL 权限和"加入核心事务"只由核心登记的 invocation 决定，不信任插件的任何声明。
3. 拦截器在核心事务内被调用时，插件在这次调用里的查询都在核心事务上执行，随核心事务一起提交或回滚。已验证三种数据库都成立。
4. 重建规则：
   - 每种节点只复制已知字段，未知类型或多余字段一律拒绝；
   - 运算符、函数、聚合、数据类型、外键动作、排序方向走白名单；
   - 数据来源只能是声明过的表；引用限定符只能是声明过的表或本查询定义的别名；
   - 拒绝原始 SQL、CTE、schema 限定、DML 中的立即值、EXPLAIN。

## 对插件 API 的约束（已写入插件 SDK 的 AGENTS.md）

- **插件 id**：`^[a-z][a-z0-9]*(-[a-z0-9]+)*$`。
- **表名、索引名、约束名**：`^[a-z][a-z0-9]*(_[a-z0-9]+)*$`，即小写、不允许连续下划线。
- **物理名**：`p_<id，连字符换成下划线>__<名字>`，长度不超过 63。按上面两条规则，`__` 在物理名里只出现一次，可以唯一拆分，不同插件不可能拼出相同的名字。
- **查询形态**：
  - 只能有一个 FROM 项，多表用带 ON 的 JOIN（最多 4 个，只支持 inner / left）；
  - 不支持 INSERT…SELECT、CTE、窗口函数；
  - RETURNING 只能用在 INSERT 上。
- **参数**：日期一律用 ISO 字符串，不接受 `Date`（node:sqlite 会把它静默绑定成 NULL）。字符串参数不超过 64 KiB，二进制不超过 256 KiB。
- **规模上限**：节点数 5000、深度 64、列表长度 1000、结果 10000 行。
- **插件自己开的事务**：有并发上限和超时；超时自动回滚，过了期限的提交会被拒绝。

## 独立审核发现的问题与修复

审核由 Codex（`gpt-6-astra`，xhigh）执行。它在输出最终结论时被 OpenAI 的内容安全过滤拦截，但审核过程中的探测脚本已经全部运行，结果由主会话复现确认。以下各项都已修复，并有对应的回归用例。**修复后没有再做独立复审。**

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 物理名可碰撞：插件 `a` 的表 `b__c` 与插件 `a__b` 的表 `c` 都拼成 `p_a__b__c`；SQLite 表名不区分大小写，`Victim` 与 `victim` 也会撞 | **跨插件读写、删除别的插件的表**（严重） | 插件 id 和对象名强制小写、禁止连续下划线；网关构造时校验 |
| 2 | 两个一元负号嵌套，编译成 `--"n"`，变成 SQL 行注释 | 查询被截断（实测只会导致语法错误，但属于编译输出失控） | 一元负号的操作数统一加括号 |
| 3 | 事务并发上限的检查发生在 `await` 之前，并发请求可以同时通过 | 上限失效，可能耗尽连接池 | 先同步占位，再开启事务 |
| 4 | SQLite 驱动同步执行，慢查询期间超时定时器无法触发，过期的事务仍能提交 | 事务时限失效 | 提交时再检查一次期限，过期则回滚并拒绝 |
| 5 | 带 RETURNING 的 INSERT…SELECT 先写入，再检查结果行数 | 报错时数据已经写进去了 | 禁止 INSERT…SELECT；RETURNING 只允许用在 INSERT 上 |
| 6 | 逗号连接的多表 FROM（笛卡尔积） | 资源消耗 | 只允许一个 FROM 项 |
| 7 | 参数大小不设限；`Date` 在 SQLite 上被静默绑定成 NULL；二进制参数被逐字节当成节点计数 | 资源消耗、数据错误、误判 | 限制大小、拒绝 `Date`、跳过类型化数组 |

## 遗留的设计风险（上线前必须处理）

1. **SQLite 上，插件查询会阻塞整个核心。** node:sqlite 是同步的，在主线程执行。即使只能访问自己的表，插件也能用带 `ON 1=1` 的 JOIN 构造一条昂贵的查询，占住事件循环。
   - 方向：SQLite 模式下，插件查询放到 worker 线程里的独立连接执行（WAL 模式支持并发读）；或者对插件查询做代价预估。
2. **SQLite 只有一个连接，同一时刻只能有一个事务。** 插件开着的事务会让核心所有数据库操作排队，直到它提交或超时。
   - 方向：SQLite 模式下把插件事务超时压到很短（例如 200 ms），或者干脆不给插件开事务的能力，只保留"加入核心事务"。
3. **PostgreSQL 和 MySQL 没有设置语句级超时。** 需要实现：PostgreSQL 用 `SET LOCAL statement_timeout`，MySQL 的 SELECT 用 `MAX_EXECUTION_TIME` 提示。
4. **结果行数是取回之后才检查的**，大结果集仍会先占用内存。应当把行数上限下推成 LIMIT。
5. **IPC 消息本身没有大小上限**，需要在 host 和核心之间的传输层加上。

## 性能

经过 IPC、重建、重新编译之后，单条简单查询比核心直连多约 0.4–0.5 ms：

| 数据库 | 插件 | 核心直连 |
|---|---|---|
| SQLite | 0.46 ms | 0.04 ms |
| PostgreSQL | 0.90 ms | 0.40 ms |
| MySQL | 0.80 ms | 0.33 ms |

对插件的业务查询来说可以接受；不适合在热路径上逐行查询。
