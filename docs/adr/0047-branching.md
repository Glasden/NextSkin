# ADR-0047 分支：main 是主干，大改动开功能分支走 PR，修旧版本时才从标签拉维护分支；main 和维护分支只有维护者能写

- 状态：已采纳
- 日期：2026-10-21
- 补充 ADR-0035：SDK 的发布提交照旧直接进 main；"仓库没有 PR 流程"不再成立，不用"Version Packages" PR 的决定不变
- 补充 ADR-0040：修订版可以从维护分支发；取代"发布流程"第 1 条"标签指向的提交在 main 上"

## 背景

到 0.1.0 为止，所有提交直接进 main，没有 PR，ADR-0035、ADR-0040 都按这个写。0.1.0 发布以后，这样做有三件事办不到：

- **修已发布的版本**。main 上已经有下一个版本的改动时，0.1.0 要出修复版，不能把 main 整个发出去：迁移是单向的（ADR-0040），服主升了就回不去。
- **合进主干之前跑完 CI**。本地的 `pnpm check` 不含 `test:db`、`e2e`、`test:visual`、`test:pack`，它们要等推到 main 才在 CI 上跑；main 坏了就一直坏着，直到下一个提交修好。仓库已经公开，公开仓库的 GitHub Actions 不计分钟数，PR 上跑完整的 CI 不再有成本上的顾虑。
- **谁能写 main**。仓库有三位有写权限的协作者，main 没有任何保护：任何一位都能直接推送、强推、删除 main，也能推 `v*` 标签触发发布工作流（推镜像和建 Release 仍要维护者在 environment `release` 里批准）。两个 environment 也都允许从任意分支部署。

用户拿到的是 GitHub Releases 上的 ZIP、GHCR 上的镜像和 npm 上的包，没有人从分支直接部署。

## 决定

### 主干

- main 是主干，随时可以发版。发版照旧在 main 上改版本号、打标签（ADR-0035、ADR-0040）。
- 小改动直接进 main：文档、只有一个提交的修复。
- 下面这些开分支（`feat/<名字>`，修问题用 `fix/<名字>`），提 PR，CI 全部通过后合并：
  - 加迁移；
  - 改协议端点（不变量 1）；
  - 改插件 SDK 的公开 API（不变量 9）；
  - 要分几个提交才做得完的功能。
- 合并用 rebase 或 squash，保持线性历史，不用合并提交。分支合并后删掉。

### 维护分支

- 已发布的版本要修问题时才建：从这个次版本最新的标签拉 `release/X.Y`，不预先为每个次版本建。
- 修复先进 main，再用 `git cherry-pick -x` 挑到维护分支，main 就不会漏修。修复只对旧版本成立时（main 上那段代码已经改写），直接在维护分支上修。
- 在维护分支上改 `packages/launcher/package.json` 的版本号、打 `vX.Y.Z` 标签，走和 main 上相同的发布工作流。这个改版本号的提交不挑回 main。
- 镜像标签不用另外处理：`release-image-tags.yml` 只在这个版本是对应范围里最新的正式版时才移动 `X.Y`、`X`、`latest`，给旧的次版本发修订版不会把 `latest` 指回去（ADR-0040）。
- **修订版不带迁移**。Kysely 的迁移器要求已执行的迁移在新版本里都还在，并且排在所有未执行的迁移前面，否则报 `corrupted migrations`，核心打不开。迁移按编号顺序命名：维护分支上加一条 `0046_a`，main 上的 `0046` 是另一条，站点从这个修订版升到下一个次版本时就打不开。非要改库才能修的问题，从 main 发下一个次版本。
- 插件 SDK 不建维护分支：候选期的修订从 main 发，`release.yml` 也只在推到 main 时运行。1.0.0 之后要给旧的 SDK 次版本发修订版时再定。

### 权限

- GitHub 的规则集：
  - **分支**：main 和 `release/**` 只有仓库管理员能创建、推送、删除、强推（规则全开，bypass 只给 Repository admin）。其他协作者开自己的分支、提 PR，由维护者合并。
  - **标签**：`v*`、`@nextskin/*` 只有仓库管理员能移动、删除。发布标签被移动，已经发出去的 ZIP、镜像和 npm 包就对不上源码。不限制创建：`@nextskin/*` 由 `release.yml` 用 `GITHUB_TOKEN` 创建；别人推的 `v*` 标签会触发构建，但推镜像和建 Release 仍要维护者批准。
- environment：`npm` 只允许 main 部署，`release` 只允许 `v*` 标签部署，两个照旧要维护者批准。
- 不设"必须通过的状态检查"：CI 对只改文档的提交不运行（`paths-ignore`），设了以后这样的 PR 永远等不到结果。维护者合并前自己看 CI。
- Renovate 只开 PR，不自动合并，不受规则集影响。

### 工作流

- `ci.yml`：推送到 `release/**` 也运行。
- `release-site.yml` 的核对：标签指向的提交在 main 上，或者在这个次版本的维护分支 `release/X.Y` 上。

## 后果

- 发版和以前一样，多出来的只有大改动的 PR 和偶尔的维护分支。
- 修复要记得挑到维护分支；只修在维护分支上的，下一个次版本会把问题带回来。
- main 可能领先于最新的发布。文档里指向 `tree/main` 的链接显示的是主干上的内容，不一定是用户手里的那个版本。
- 其他协作者推不了 main 和维护分支，改动都经过 PR。

## 考虑过的其他方案

- **长期的 dev 分支，发版时合进 main（git-flow）**：main 等于最新发布，可没有人从分支部署，这个性质用不上。代价是每次发版多一次合并，修复要合回 dev；GitHub 的默认分支还得改成 dev，否则外部 PR 和 Renovate 都指向 main，这样一来仓库首页显示的又是 dev。所有工作流和 ADR 也都要从 main 改过去。
- **所有改动都走 PR**：单人维护时，文档和单提交的修复也开 PR，只是多点几下，CI 照样跑在推送之后。
- **预先为每个次版本建维护分支**：大多数次版本不会有修订版，分支只会堆着。
- **把协作者降成只读**：他们还要开分支、提 PR；规则集只管 main、维护分支和发布标签就够了。
