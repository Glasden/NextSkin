# ADR-0051 后台的失败任务页：核心任务的死信由超级管理员查看、重试、删除；去掉了链接的邮件不能重试

- 状态：已采纳
- 日期：2026-10-22
- 补充 ADR-0021："死信"一节的后台查看、重试、删除落到核心任务上；邮件任务的错误码细到 SMTP 的错误类别
- 补充 ADR-0027：新增具名权限 `jobs.manage`

## 背景

ADR-0021 定了任务彻底失败后移进 `failed_jobs`，"后台可以查看、重试、删除"，管理员能看到发送失败的具体邮件。插件系统落地时只给插件任务做了这件事：插件详情页列出 `plugin:<id>:` 开头的死信，能重试、删除（ADR-0033）。核心自己的任务（名字以 `core:` 开头：发邮件、材质文件的回收、几个定时清理）进了死信，后台看不到，站长只能查库。

最常见的情况是 SMTP 配置坏了：设置填错、密码过期、服务商封了端口。这段时间里所有邮件试满 5 次后进死信，站长修好设置之后，没有办法把它们重新发出去，也不知道漏发了哪些。

邮件任务进死信时去掉了载荷里的链接（链接里带着重设密码、验证邮箱的令牌，ADR-0021），这几种邮件原样放回队列只会再失败一次。另外，核心任务失败时只记固定的错误码（不变量 11），邮件失败几乎都记成 `error`，看不出是认证失败还是连不上服务器。

## 决定

### 范围和权限

- 新页面"失败任务"（`/admin/failed-jobs`）只列核心任务的死信，即名字以 `core:` 开头的。插件任务的死信照旧在插件详情页：判断它要结合插件的版本、启用状态和设置，放在插件页里看更合适。
- 新增具名权限 `jobs.manage`，只给超级管理员。载荷里有收件地址；死信多半是设置或存储出了问题，这些只有超级管理员能改；重试会真的把邮件再发一次。
- 导航项排在"插件"后面。有 `jobs.manage` 的人在后台概览看到"有几个后台任务失败了"的提示，链接到这一页：站长平时不会主动打开它。

### 列表

- 最新的在前，每页 50 个，显示总数。死信只保留 30 天（ADR-0021），不另做筛选。
- 每行：任务的名称（核心任务有文案，不认识的显示任务名）、编号、内容、尝试次数、入队和失败的时间、错误、操作。
- 内容：邮件写模板和收件地址，收件人还在就链接到用户详情页；其余任务显示载荷的 JSON（文件回收是材质的 hash，清理已卸载的插件是插件 id 和插件包的 hash，定时清理是空的），不含敏感内容。
- 错误：认识的错误码写成说明（超时、邮件没配置、SMTP 的错误类别），不认识的原样显示。

### 重试

一条死信能重试，要同时满足：

1. 运行中的核心登记了这个任务名的处理函数。没有处理函数的任务放回队列后永远不会被认领；
2. 处理函数认这份载荷：`JobHandler` 新增可选的 `retryable(payload)`，默认认。

邮件的 `retryable` 用发送时的校验判断。带链接的三种（验证邮箱、找回密码、确认新邮箱）进死信时去掉了链接，不能重试，页面上说明"链接已经去掉，让用户重新申请"；它们的链接本来也只有几个小时的有效期。其余三种（邮箱已更改、绑定了第三方账号、管理员修改了账号）能重试。进死信时改成保留渲染要用的内容："管理员修改了账号"的修改时刻 `at`、"绑定了第三方账号"的第三方名称，它们都不敏感，没有它们就渲染不出邮件。已经进了死信、缺这些内容的旧行仍然不能重试。

不能重试时接口返回 409 `dead_letter_not_retryable`。重试的语义同 ADR-0021：放回 `jobs`，`attempts` 从 0 开始，同一去重键的任务已经在队列里时直接丢掉这条。

### 全部重试、全部删除

SMTP 修好之后一条条点重试不现实，所以页面上有"全部重试"和"全部删除"：

- 全部重试只重试能重试的，其余留着，返回重试了几个、跳过了几个；全部删除删掉全部核心死信。
- 都只作用于页面打开时已经有的死信：请求带上页面看到的最大编号 `through`，只处理编号不大于它的行。页面打开之后才失败的任务，管理员还没看过，不该被一起删掉。
- 一个事务做完。死信只保留 30 天，数量有上限。

### 邮件的错误码

邮件任务的处理函数补上 `errorText`：SMTP 库的错误带着固定的类别码（`EAUTH`、`ECONNECTION`、`ETIMEDOUT`、`EDNS`、`ETLS`、`EENVELOPE`……）和服务器的三位应答码，记成 `smtp:EAUTH`、`smtp:EENVELOPE:550` 这样的形式。类别码只认白名单里的，两者都不含服务器返回的文字，不会带出收件地址和密码（不变量 11）。只认发信这一步抛出的错误：读库时的网络错误也带 `ETIMEDOUT` 这类代码，但不是 SMTP 的问题。认不出类别码的仍然记 `error`。

### 审计

每次重试、删除写一条审计，动作 `job.deadLetter`，对象类型 `job`：

- 单条：对象 id 是死信的编号，details 记 `action`（`retry`、`delete`）和任务名；
- 全部：对象 id 记 0，details 记 `action`（`retryAll`、`deleteAll`）、处理的个数，全部重试另记跳过的个数。一个都没处理时不写。

死信重试或删除后就不在表里了，审计记录里的对象不链接。

## 后果

- 站长能看到漏发了哪些邮件、发给谁，修好 SMTP 之后一次重发；验证邮箱、找回密码这类只能让用户重新申请。
- 邮件失败的原因能在后台看出个大概：认证、连接、TLS、收件地址被拒。
- 插件任务的死信仍然分散在各个插件页。插件列表已经有"失败的任务"一列，概览的提示只算核心任务。
- 命令行的 `doctor` 不检查死信，它只看运行环境。

## 考虑过的其他方案

- **管理员也能看**：载荷里有收件地址，而死信的原因多半在只有超级管理员能改的设置上，管理员看了也修不了。
- **插件的死信也合并进这一页**：插件页已经有，再放一份要处理两处入口的权限和文案；插件的死信要结合插件的状态判断。
- **重试带链接的邮件时重新签发链接**：等于替用户申请重设密码、验证邮箱，用户没有发起过这次申请；链接的有效期本来就短，让用户自己重新申请更简单。
- **全部操作不带上限编号**：页面打开之后新失败的任务会被一起删掉、重试，管理员没看到过它们。
- **按任务名筛选**：核心任务只有十来种，死信只留 30 天，一页 50 个够看；等真有需要再加。
- **进死信时给站长发邮件**：死信最常见的原因就是邮件发不出去。
