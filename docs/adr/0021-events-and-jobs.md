# ADR-0021 事件和后台任务：数据库里的一张任务表，事件在业务事务里按订阅者展开成任务

- 状态：提议
- 日期：2026-10-18
- 取代 ADR-0002 里"队列可以换成 Redis 驱动"的部分，以及 ADR-0018 里"邮件放进进程内的发送队列"的部分，两份 ADR 的其余部分不变

## 背景

接下来的写操作（添加角色、上传材质、衣柜、举报）都要用到三样东西：
- 在业务事务里发出事件（ADR-0010 的 Event：提交后投递，至少一次）；
- 排后台任务（SDK 的 `jobs.enqueue`，支持 `delaySec`、`dedupeKey`）；
- 原子地改积分并记流水（不变量 5，SDK 的 `adjustScore`）。

现状：
- 邮件队列在进程内存里（ADR-0018），进程崩溃会丢掉还没发出的邮件；
- 注册给了初始积分，但没有流水；`user.registered` 事件的位置空着（`users/register.ts`）；
- `docs/schema.md` 定的要点是：建一张 `outbox_events` 表，再写一个分发器，认领未分发的事件、为每个订阅者生成任务。

约束：
- 四种数据库都要能跑，不能依赖 `SKIP LOCKED`、`LISTEN/NOTIFY` 这类方言特性（不变量 6）；
- 默认部署只有一个进程加 SQLite（ADR-0002），写锁是全局的，事务里不能做网络请求（ADR-0008）；
- 入队必须和业务写入在同一个事务里提交，否则会出现"事务提交了、任务丢了"或"任务执行了、事务却回滚了"。

## 决定

### 任务表

所有后台工作都是 `jobs` 表里的一行，包括事件投递、插件任务，以及核心自己的任务（例如发邮件）。表里只放还没完成的任务：完成就删除，彻底失败就移到 `failed_jobs`。

| 列 | 类型 | 说明 |
|---|---|---|
| id | 自增 | |
| name | varchar(128) | 处理函数的键，例如 `core:mail`、`plugin:<id>:job:<任务名>`、`plugin:<id>:on:<事件名>` |
| payload | 长文本 | JSON。插件入队的载荷限 64 KB |
| dedupe_key | varchar(255)，可空 | 与 `name` 组成唯一索引 |
| run_at | 时间 | 最早执行时间；任务执行期间，这一列是租约到期时间 |
| lease_id | varchar(36)，可空 | 本次认领生成的随机值 |
| attempts | integer | 已经开始执行过几次 |
| last_error | varchar(500)，可空 | |
| created_at | 时间 | |

- 另建 `(run_at, id)` 索引。
- 去重：入队用 `insertOrIgnore`，同一个 `(name, dedupe_key)` 已经有未完成的任务时不再入队。表里只有未完成的任务，唯一索引自然只覆盖它们，不需要 schema.md 原方案里"失败时清掉去重键"的处理。
- 入队函数接受事务对象，与业务写入一起提交或回滚；不在事务里时传 `db`，就是一条单独的 INSERT。
- 重试次数和超时取处理函数的定义（SDK 的 `maxAttempts` 默认 5、`timeoutMs` 默认 60 秒），不存在行里。

### 认领与执行

- 执行器跑在核心进程里。空闲时每秒用读连接查一次到期的任务：条件是 `run_at <= 现在`，按 `run_at, id` 排序，取空闲槽位数那么多条，并且只查本实例注册了处理函数的 `name`。停用的插件，任务留在表里，重新启用后继续执行；卸载插件时删除它的任务。
- 认领是一条带条件的 UPDATE：`set run_at = 现在 + 超时 + 30 秒, lease_id = 新随机值, attempts = attempts + 1 where id = ? and run_at <= 现在`。影响 1 行才算认领成功。
  - 多个实例同时认领同一行时，后到的 UPDATE 会等前一个提交，再按新值重新判断条件，结果影响 0 行。PG 和 MySQL 在 READ COMMITTED 下都会对并发修改过的行重新判断 WHERE，SQLite 本来就串行执行。
- 处理函数在事务之外执行。执行结束后按 `id` 和 `lease_id` 收尾；租约已经被别的执行者接手的，不动它：
  - 成功：删除这一行；
  - 失败但还有次数：`run_at` 推迟一段退避时间（从 10 秒开始指数增长，加随机抖动，上限 1 小时），清空 `lease_id`，记下错误；
  - 失败且次数用完：在一个事务里插入 `failed_jobs`，删除原行。
- 次数在认领时就加一。处理到一半进程崩溃，租约到期后任务会被重新认领，那一次也计入次数。认领时发现次数已经用完的，直接移进 `failed_jobs`，不再执行。反复把进程搞崩的任务最终会进死信，不会无限重来。
- 超过超时时间，处理函数收到的 AbortSignal 会被 abort，这次执行按失败处理。
- 执行器有全局的并发上限，每种处理函数还可以单独限制并发（邮件沿用现在的 2）。
- 停止时不再认领新任务，等执行中的任务结束，等待时间有上限。到时还没结束的，等租约到期后由下次启动接手。
- 新任务入队后不通知执行器，最多等一个轮询周期就会被执行。
- 启动器落地之前，Web 进程启动时（`instrumentation.ts`）就打开核心、启动执行器。这样重启后的积压任务不用等第一个请求。

### 死信：failed_jobs

- 列：`id`、`name`、`payload`、`dedupe_key`（不建唯一索引）、`attempts`、`last_error`、`created_at`（原任务的入队时间）、`failed_at`（建索引）。
- 后台可以查看、重试、删除。重试就是把任务放回 `jobs`，`attempts` 从 0 开始；同键的任务已经在队列里时，直接丢掉这条。
- 只保留 30 天：每次写入 `failed_jobs`，都在同一个事务里删掉 `failed_at` 早于 30 天的行。这样不需要另设定时任务。
- `last_error`：
  - 核心的处理函数只记固定的错误码，与现在的邮件队列一样，因为外部服务返回的消息里可能带着敏感内容；
  - 插件任务记插件抛出的消息，截到 500 字符，SDK 文档要求消息里不放密钥；
  - 诊断包不导出这两张表的载荷和错误。

### 事件：在业务事务里按订阅者展开

- `emit(tx, 事件名, actor, data)` 在业务事务里执行：为每个订阅了这个事件的处理者插入一个任务，载荷是完整的事件信封（SDK 的 `EventEnvelope`，`id` 是随机 UUID）。没有订阅者就什么都不写。
- 每个订阅者各写一份信封，正好满足 SDK 的另一条要求：`user.registered` 的 `extra` 只能包含该插件自己贡献的表单字段。
- 不建 `outbox_events` 表，也没有分发器。`jobs` 表本身就是 outbox：任务和业务写入在同一个事务里，提交之后才可见。
- 订阅者集合取发出事件那一刻：已启用的官方插件，加上 plugin host 当前这一代的 manifest。之后才启用的插件，收不到它启用之前发出的事件。
- 同一个订阅者收到事件的顺序没有保证，重试会打乱先后。处理函数需要最新状态时，应该自己去读，不能依赖事件的顺序。SDK 的事件说明里要补上这一句。

### 积分

- `adjustScore(tx, { uid, delta, reason, subject })` 是修改 `users.score` 的唯一途径：
  - 用 `score = score + ?` 原子更新，扣减时带上"余额足够"的条件，影响 0 行就抛 `score_insufficient`；
  - 再读回余额，写一条 `score_transactions`（列见 schema.md）；
  - 必须在调用方的事务里执行。
- 注册：用户先以 0 分插入，再用 `adjustScore` 加上初始积分；初始积分为 0 时不写流水。
- 导入器不走这个函数，但同样为每个积分非零的用户写一条"导入"流水。
- 这样，每个用户流水的 `delta` 之和恒等于 `score`，对账报告可以检查这一点。lint 禁止在这个辅助函数之外写 `users.score`（导入器例外）。

### 邮件

- 发送邮件改成 `core:mail` 任务，取代进程内的队列。载荷只存模板名、收件地址、uid、链接和链接的过期时间，到发送时再按收件人的语言渲染。链接已经过期的任务直接丢弃。
- 进死信时，载荷里的链接要去掉：链接里带着重设密码或验证邮箱的令牌。
- Better Auth 的回调（重设密码、验证邮箱）在它的事务之外被调用，回调里直接用 `db` 入队。
  - 要是在它的事务里入队，SQLite 上两边会互相等写锁，正是 ADR-0018 背景里说的那种卡死。
  - Better Auth 1.7.10 里，只有注册、`/update-user` 和 OAuth 建号会在事务里执行。前两个我们已经关掉，三者都不调用这两个回调。
  - SQLite 上的测试覆盖这两条路径。哪次升级后回调进了事务，测试会以写锁超时失败。
- 注册的验证邮件仍然在提交之后入队，因为链接要由 Better Auth 签发。提交和入队之间进程崩溃，会丢掉这一封，用户可以重新发送。

### 定时任务（随第一个定时任务落地）

- 建 `job_schedules` 表，列：`name`（主键）、`next_run_at`（时间）。
- 执行器每 30 秒检查一次到期的条目。对每个到期的条目，在一个事务里用条件 UPDATE 把 `next_run_at` 从旧值改成下一次执行的时间；影响 1 行，就入队对应的任务，去重键用条目名。
  - 停机期间错过的多次执行，只补跑一次；
  - 上一次还没跑完，不会叠加新的。
- cron 表达式按站点时区（`site.timeZone`）解释，用一个纯 JS、支持时区的解析库。站点时区改了以后，重新计算 `next_run_at`。

## 后果

- 采纳时改写 `docs/schema.md` 的"事件与任务"一节：去掉 `outbox_events`，补上 `jobs`、`failed_jobs`、`job_schedules`；"落地顺序"一节同步修改。`audit_logs` 照原设计，随第一个管理操作落地，这一次没有写入它的地方。
- 后台任务的队列始终在数据库里，Redis 档位（ADR-0002）也不例外。入队必须和业务写入一起原子提交，Redis 做不到。
- 投递延迟最多是一个轮询周期（1 秒）。空闲时，每个实例每秒执行一次走索引的读查询；在 SQLite 上走读连接，不占写锁。
- 每个任务至少要写三次：入队、认领、删除，每次都是很小的写入。按现在的量（邮件、插件事件）没有问题。以后要是有每个请求都会发出的高频事件（例如 `yggdrasil.serverJoined`），要结合订阅者数量重新评估。
- 至少一次：处理函数执行完、删除任务之前进程崩溃，任务会再执行一次。邮件偶尔会重复发一封；插件的处理函数按 SDK 的要求，用事件 id 去重。
- 管理员能看到发送失败的具体邮件（收件地址和模板），ADR-0018 里"只能看到失败计数"的限制不再存在。

## 考虑过的其他方案

- **schema.md 原方案：`outbox_events` 表加分发器**。分发器要处理认领，要处理"自增 id 的顺序不等于提交顺序"，要为每个订阅者生成任务，还要定期清理已分发的事件，换来的只是一份事件历史。改成在事务里直接展开，少一张表、少一个循环，也少一跳延迟。
- **现成的队列库**：pg-boss、graphile-worker 只支持 PostgreSQL，BullMQ 需要 Redis（ADR-0002 不把 Redis 设为必需）。而且它们都不能在我们的 Kysely 事务里入队。
- **用 `SELECT … FOR UPDATE SKIP LOCKED` 认领**：PG、MySQL 8、MariaDB 10.6 以上都支持，SQLite 不支持，只能按方言分支。现在的并发量，用条件 UPDATE 就够了。
- **死信留在 `jobs` 表里、清掉去重键**：认领查询和唯一索引都得排除死信行。单独一张表更简单，BS 的服主也熟悉 Laravel 的 `failed_jobs`。
- **入队后立即通知执行器**：通知必须在提交之后发（事务可能回滚，也可能整体重试），这需要给 `transactionWithRetry` 加一个提交后的回调。对邮件和插件事件来说，1 秒的延迟可以接受，先不做。
