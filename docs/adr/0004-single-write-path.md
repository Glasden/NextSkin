# ADR-0004 写操作唯一入口：领域用例；Web UI 走公开 API

- 状态：已采纳
- 日期：2026-10-16

## 背景

如果网页用 Server Actions 写数据、第三方用 REST API 写数据、插件再通过第三条路径写数据，那么权限校验、CSRF、限流、审计、插件拦截器就要实现三遍，三处行为迟早会出现差异。BS 的历史问题里有不少正是这类差异，例如积分在并发请求下被重复结算。

## 决定

- 所有业务写操作都实现为**领域用例**：位于不依赖框架的 TS 包中，接收调用者身份和经过校验的输入，在一个数据库事务内完成全部状态变更。拦截器在用例内触发，事件写入 outbox。
- HTTP 层（Hono）只做三件事：解析输入、调用用例、序列化结果。Route handler 里不写 SQL，也不写业务规则。
- **Web UI 是公开 API 的第一个客户端**：浏览器里的写操作调用的就是对外公开的那套 API，Server Actions 不承担任何写操作。
- 读操作可以绕过 HTTP：服务端组件直接调用领域层的查询服务，但同样要传入调用者身份，用同一套授权规则。
- 积分、点赞数这类计数一律在事务内原子更新，不允许"先读、再算、再写回"。

## 后果

- 公开 API 必然完整，因为网页自己就依赖它。
- 插件能力 API（ADR-0010）也调用这些用例，不另起一套实现。
- 新增功能的固定顺序：先写用例，再写 API，最后写 UI。这个顺序要写进 AGENTS.md 的任务配方。

## 考虑过的其他方案

- **网页的写操作用 Server Actions**：开发起来更顺手，但会形成第二条写入路径，并且它的端点同样对外暴露，并不比 API 更安全。
