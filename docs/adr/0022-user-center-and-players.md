# ADR-0022 用户中心和角色管理：写接口认会话 Cookie，删除角色退还当初实付的积分

- 状态：已采纳
- 日期：2026-10-18

## 背景

登录和注册已经落地（ADR-0018），但登录之后没有地方可去，只能回到占位的首页。两步验证、通行密钥、Yggdrasil Connect 的页面也都要放进用户中心。REST 接口目前只有一个不需要登录的注册接口。

BS 6.0.2 的角色管理（`PlayerController`）：
- 添加：角色名规则与注册相同，扣 `score_per_player`（默认 100）积分，余额不足时拒绝；
- 改名：不收积分；
- 删除：开着 `return_score`（默认开）时，按删除时的 `score_per_player` 退还积分；
- 注册时一起创建的角色不扣积分；
- 开着"必须验证邮箱"时，整个角色管理都要先验证邮箱；
- 被封禁的用户进不了用户中心（`RejectBannedUser`）。

BS 的签到（`UserController::sign`）：在 `sign_score`（默认 10,100）之间随机加分；距上次签到满 `sign_gap_time` 小时（默认 24）才能再签，开了 `sign_after_zero` 则改为过了零点就能签。

BS 这里有两个积分问题：
- **退还的是现价，不是当初付的。** 注册时送的角色是免费的，删掉照样退 100 积分；管理员调价之后，删旧角色会多退或少退。
- **签到是先读、再算、再写回**（`$user->score += …; $user->save()`）。同时发两个请求，两次都能签到成功。

## 决定

### 范围

这次做三件事：
- 用户中心的外壳：布局、导航、登录检查；
- 仪表盘：积分、签到、最近的积分变动、角色数；
- 角色管理：列表、添加、改名、删除。

不做：
- 给角色换材质、清除材质，随衣柜一起做；
- 个人资料，下一步连同两步验证、通行密钥一起做；
- 公告，随后台的设置页一起做；
- 头像。

### 页面

- 仪表盘是 `/user`，角色管理是 `/user/players`。不沿用 BS 的 `/user/player`：网页本来就是重新设计的（ADR-0001）。
- 登录、注册成功后进入 `/user`。没有登录时访问用户中心，跳到 `/sign-in?next=<原路径>`。`next` 只接受站内路径，防止被用来跳到别的网站。
- 被封禁的用户：页面显示"账号已被封禁"，写接口返回 403 `user_banned`（与 BS 相同）。
- 导航项由核心登记在一张表里。插件运行时落地后，再合并插件声明的 `area: 'user'` 导航项（ADR-0011）。
- 数据流沿用 ADR-0003、ADR-0004：
  - 服务端组件调用领域层的查询，传入调用者身份；
  - 客户端组件通过 REST 写入，成功后调用 `router.refresh()`，让服务端组件重新取数据。
  - 暂不引入 TanStack Query（ADR-0012 选定的请求库）：现在的页面没有需要在浏览器里分页或轮询的列表。

### REST 接口的身份

- 写接口认 Better Auth 的会话 Cookie。CSRF 仍然靠现有的 Origin 检查；Cookie 是 SameSite=Lax。
- 新加一个中间件，取出会话里的用户，没有登录时返回 401 `unauthenticated`。
- 用例接收调用者的 uid，自己检查封禁和邮箱验证（ADR-0018："各用例自己检查"）。插件的能力 API 绕过 HTTP 直接调用用例（ADR-0004），检查放在 HTTP 层会漏掉这条路径。
- 第三方用 OAuth 访问令牌调用这些接口，留到设计 API scope 时再做。
- 新接口：

| 接口 | 请求 | 成功响应 |
|---|---|---|
| `POST /api/players` | `{ name }` | 201，角色 |
| `PATCH /api/players/{pid}` | `{ name }` | 200，角色。以后换材质也走这个接口 |
| `DELETE /api/players/{pid}` | — | 200，`{ refunded }` |
| `POST /api/user/check-in` | — | 200，`{ delta, score, nextAt }` |

- 角色的响应格式与 SDK 的 `Player` 相同。别人的角色和不存在的角色一样返回 404 `player_not_found`，不透露这个角色是否存在。

### 角色的积分

新设置项，默认值取 BS：

| 设置 | 默认 | 对应 BS |
|---|---|---|
| `score.perPlayer` | 100 | `score_per_player` |
| `score.refundOnDelete` | 开 | `return_score`。BS 里它同时管角色、材质和衣柜的退还，这里也一样 |

- 添加角色时扣 `score.perPlayer`。为 0 时不扣分，也不写流水。注册时一起创建的角色不扣分，与 BS 相同。
- 删除角色时，**退还的是这个角色当初实际扣的积分**，不按删除时的单价。实际扣的数记在 `players` 的新列 `score_paid` 上（整数，非空，默认 0）：
  - 注册时送的角色，`score_paid` 是 0，删掉不退；
  - 管理员调价，不影响已有角色的退还；
  - 导入时 `score_paid` 一律设为旧站的 `score_per_player`：BS 删除任何角色都按现价退还，所以迁移那一刻用户删掉角色能拿回多少，迁移之后仍然是多少；
  - 以后在后台把角色转让给别人时，`score_paid` 清零：新主人没有付过这笔积分。
- 改名不收积分，与 BS 相同。
- 事务里的第一条写语句锁住这个用户在 `users` 里的行（`docs/schema.md` 的加锁顺序）：
  - 添加时，这条语句就是扣积分的 UPDATE；不扣分时，执行一条不改值的 UPDATE。
  - 删除时先锁用户行，再按 id 和 user_id 删除角色，确实删掉了一行才退分。同一个角色被并发删除时，只退一次。
- 改名撞上别人同时改成的同名，由 `name_key` 的唯一索引兜底。PG 上违反唯一约束会让整个事务作废，所以要等事务失败之后，在事务外把唯一冲突转成 `player_name_taken`。`packages/db` 为此补一个识别唯一冲突的辅助函数，在四种数据库上测试。

### 签到

新设置项，默认值取 BS：

| 设置 | 默认 | 对应 BS |
|---|---|---|
| `checkIn.score` | 10–100 | `sign_score` |
| `checkIn.gapHours` | 24 | `sign_gap_time` |
| `checkIn.resetAtMidnight` | 关 | `sign_after_zero`；开启时按站点时区（`site.timeZone`）过了零点就能再签 |

- 用一条带条件的 UPDATE，同时判断能不能签到并写入 `last_check_in_at`（`docs/schema.md` 里 users 表的约定）。确实改到了一行，才调用 `adjustScore` 加分，原因是 `score.reasons.checkIn`。同时发来的两次签到只有一次成功。
- 抽到 0 分时，只记签到时间，不写流水（`adjustScore` 不接受 0）。
- 还没到时间就签到，返回 409 `check_in_too_early`，参数里带下次可以签到的时间。
- 签到不要求验证邮箱，与 BS 相同。

### 事件

- 添加、改名、删除角色，分别在事务里发 `player.created`、`player.renamed`、`player.deleted`。注册时一起创建的角色也补发 `player.created`。这几个事件 SDK 里已经有了，插件 API 不变。
- 拦截器 `player.create`、`player.rename` 和注册一样，等插件运行时落地后接入，位置现在就留好。
- 签到暂时不发事件。SDK 里没有签到事件，需要时按插件 API 变更的流程加。

### 组件和角色卡片

- 新组件写进 `packages/ui`，配 story 和截图基线：
  - Dialog：添加角色、改名、删除确认；
  - Menu：用户菜单；
  - 用户中心的导航：桌面端放在侧栏，移动端改成横向；
  - EmptyState：还没有角色时显示。
- 角色卡片：上半部分是展台，放角色的 2D 正面；下半部分是角色名、UUID（等宽字体，可以复制）、更新时间和操作。
- 2D 正面的出图接口随材质上传一起落地，现在也没有办法给角色设置材质，所以展台上先放一个人形占位，并说明游戏里会显示默认皮肤。

## 后果

- 新迁移给 `players` 加 `score_paid` 列。导入器的对照表要加上这一列，以及上面几个设置项的映射。
- 删除角色要连带清掉指向它的数据：
  - `device_code_selections` 已经有级联外键；
  - Yggdrasil 的令牌，以及 Connect 记在 `oauth_consents.reference_id` 里的角色，在各自的切片落地时处理。
- 以后材质的退还按同样的思路设计：退当初实际扣的积分，不退现价。具体在材质的 ADR 里定。
- e2e 补上用户中心的主流程：登录 → 仪表盘 → 签到 → 添加、改名、删除角色。

## 考虑过的其他方案

- **按删除时的单价退还（BS 的做法）**：注册送的角色删掉能换积分；管理员调价后，退还的数额和当初付的对不上。
- **按积分流水查当初扣了多少**：导入的角色没有扣分的流水，退不了；转让之后，查到的是原主人的流水。
- **在 REST 中间件里检查封禁和邮箱验证**：插件的能力 API 直接调用用例，不经过 HTTP，会漏掉检查。
- **用 TanStack Query 管理页面数据**：多一层浏览器里的缓存，还要和服务端渲染的数据保持一致。现在的页面在写入之后刷新一次就够了。
- **用 Server Actions 写数据**：ADR-0004 已经否决。
