# ADR-0061 更新检测和一键升级：核心每天读一份签名的版本清单；ZIP 部署改成版本目录加指针，由常驻的管理进程准备、切换和回滚；SQLite 和没有迁移的升级失败时自动回滚，MySQL、PostgreSQL 带迁移的升级要先确认已经备份；Docker 只检测不升级

- 状态：已采纳
- 日期：2026-10-23
- 取代 ADR-0040"不做"里的"自动检查更新"一条
- 补充 ADR-0039：根目录分成实例目录和程序目录；启动器多一种被管理进程监管的模式；根目录的 `nextskin.mjs` 改成分发命令的入口
- 补充 ADR-0040：发行包的布局改成版本目录；升级的步骤由管理进程执行；SQLite 的迁移前备份也覆盖官方插件的迁移；发布流程多签一份版本清单
- 补充 ADR-0028（新设置项）、ADR-0029（新定时任务）、ADR-0052（新的系统通知）
- 补充 ADR-0054：多一个读 R2 的 Worker 和不开代理的 `dl` 记录

## 背景

### 现状

- 升级全靠手工（ADR-0040"升级"）：停服务，删掉 `server/`、`cli/`，解压新包覆盖，再启动；迁移在核心打开时执行。回退要换回旧程序，SQLite 还要把备份放回去、删掉 `-wal` 和 `-shm`。
- 站点不知道有新版本。ADR-0040 把"自动检查更新"列为不做，理由是要让站点向外报到，留待另行决定。
- 维护者给一个 MySQL 站点手工升级时用过一份脚本：备份 → 停服务 → 换程序 → `doctor` → `migrate`（这两步失败就换回旧程序再启动）→ 启动 → 等 `/api/health`。一键升级就是把这条流水线做进程序。

### 已有的部件

| 一键升级要的 | 现有的 |
|---|---|
| 优雅停止 | 启动器经 IPC 给核心发 `shutdown`，先收任务，30 秒后强杀（ADR-0039） |
| 知道旧服务退干净了 | 数据目录的 `nextskin.lock` 是操作系统的文件锁，进程一退就放开 |
| 预检 | `doctor` 查 Node、配置、数据库、迁移状态，库比程序新时报失败 |
| 备份 | SQLite 在 `openCore` 里迁移前 `VACUUM INTO`，留 3 份（ADR-0040） |
| 新版本起来了没有 | `/api/health` 在核心打开以后才返回 200，打开失败是 500；维护模式下照常返回 |
| 程序完整 | `server/VERSION` 和启动器版本对不上就以 78 退出 |

### 核对过的事实

- **根目录**：启动器取 `cli/main.mjs` 的上一级为根目录，`.env`、`data/` 和相对路径都按它解析（ADR-0039）。直接把程序放进 `releases/<版本>/`，数据目录就会落进版本目录，删旧版本时连数据一起删。
- **迁移的原子性**：Kysely 的迁移器在方言支持事务 DDL 时，把一批迁移放在一个事务里执行。自写的 SQLite 方言和 PostgreSQL 支持，迁移失败时库保持原样；MySQL、MariaDB 不支持，DDL 隐式提交，失败时库停在中间：已执行的迁移记了下来，旧版本因为"库里有不认识的迁移"拒绝打开，新版本又没迁完。
- **官方插件的迁移**：官方插件随发行包升级，`invitation-codes`、`share-registration-link` 有自己的迁移（`plugin_migrations`），在核心打开、启用插件前执行。
  - SQLite 的迁移前备份只在有核心迁移时触发（`migrateCore` 的 `beforeUpgrade`）；
  - `doctor` 只查核心迁移，`migrate` 命令也只执行核心迁移；
  - 旧版本遇到不认识的插件迁移不拒绝，只跳过。
  所以"这次升级没有迁移"只看核心迁移会判断错。
  （落地时补充：上面"在核心打开、启用插件前执行"不对。官方插件的迁移只在后台启用它的那一刻执行（`setEnabled` → `plugins.migrate`），核心打开时不执行。已启用的官方插件在新版本里多出来的迁移因此一直不会执行，插件的代码却已经按新的表结构在跑。切片 2 改为核心打开时、启用插件之前，执行已启用的官方插件待执行的迁移，每个插件拿着它自己的锁；失败时核心打不开，和核心迁移失败一样。）
- **`ready`** 在核心打开失败时也发（ADR-0039），不能单靠它判断升级成功。
- **Windows**：`child.kill()` 不论传什么信号都是强杀（TerminateProcess），能按顺序停下的只有 IPC。
- **体积**：0.4.0 的 ZIP 是 15.6 MB。Cloudflare Workers 静态资源单个文件的上限是 25 MiB，而且每次部署都要带上全部文件，历史版本的 ZIP 不在仓库里。
- **国内访问**：文档站和宣传站的 Worker 用路由、不用自定义域，因为自定义域由 Cloudflare 建一条开代理的 DNS 记录，指不到优选 IP（ADR-0054，`apps/site/wrangler.jsonc`）。R2 公开桶的自定义域同样由 Cloudflare 建记录，没有核实能不能改成不开代理；`r2.dev` 的地址有限速，官方说明不用于生产。

## 决定

### 进程和目录

```
面板 / systemd / NSSM / MCSManager
 └─ nextskin.mjs start            管理进程：选版本、监管启动器、准备和切换版本
     └─ releases/<版本>/nextskin.mjs start   这个版本的启动器（ADR-0039）
         └─ 核心进程 └─ plugin host
```

```
nextskin/                 实例目录，环境变量 NEXTSKIN_HOME
├─ nextskin.mjs           入口：查 Node 版本、换上待生效的管理进程、分发命令
├─ manager/               管理进程的代码
├─ manager.next/          待生效的管理进程，下次启动时换上
├─ releases/
│  ├─ 0.5.0/              一个版本的程序：nextskin.mjs、cli/、server/，运行时不改
│  ├─ 0.4.0/              上一个版本，留作回滚
│  ├─ current.json        指针
│  ├─ .staging/           下载和解压中的版本
│  └─ manager.lock、manager.sock、manager.token、update-log.jsonl
├─ package.json  README.md  .env.example
├─ .env
└─ data/
```

- **管理进程只做版本的事**：选版本启动和监管、检查更新、下载、校验、解压、升级、回滚、清理旧版本、回应控制请求。不加载领域层，不连数据库，不读 `.env`。要知道的数据库情况（方言、待执行的迁移）从新版本的 `doctor --json` 拿。
- **管理进程把每个版本的启动器当黑盒**，不直接拉起 `server.js`：读配置、把环境变量换成 Next 认的名字、检查发行目录，这些都随版本变，留在各版本自己的启动器里。两者之间只有下一节的约定，这样管理进程很少需要更新。
- **指针是 `current.json`，不是符号链接**：Windows 上建链接要权限，junction 只存绝对路径（ADR-0040 背景）。内容是 `current`、`previous`、`bundled`（见"手动解压"）和升级失败过的版本；先写临时文件再改名替换，Windows 上改名被占用（EPERM）时重试。
- **管理进程的锁**：`releases/manager.lock`，做法和数据目录的锁相同。宝塔重启时不等旧进程退出就启动新的，新的管理进程等锁，最多 40 秒，等的时候收到停止信号就放弃。
- **不用管理进程**：环境变量 `NEXTSKIN_MANAGER=off` 时，入口在本进程里直接加载当前版本的启动器，进程模型和 ADR-0039 一样，后台只有检测。镜像里设这个变量。

### 管理进程和启动器之间

- 管理进程带 IPC 通道拉起 `releases/<版本>/nextskin.mjs start`，另传：
  - `NEXTSKIN_HOME`：启动器按它解析 `.env`、`data/` 和相对路径，程序文件照旧从自己的目录找。没有这个变量时和 ADR-0039 一样按自己的目录解析，直接运行版本目录里的命令行也照旧能用。
  - `NEXTSKIN_MANAGED=1`，以及控制通道的地址和令牌（见"控制通道"）。
- 消息只有两种，和启动器与核心之间的一样：
  - 启动器发 `ready`，带版本、监听地址和端口：核心发来 `ready` 之后转发；
  - 管理进程发 `shutdown`：启动器按 ADR-0039"停止"的顺序停下，然后退出。
- **IPC 断开就停**：管理进程被强杀（MCSManager 的"终止"、任务管理器结束进程）时，启动器按收到 `shutdown` 处理，和核心对启动器的做法一样。
- **停止只经 IPC**，不发信号：Windows 上发信号就是强杀。
- **退出码**：
  - 0：停下了。管理进程没让它停却退出了，说明别人直接停了它（宝塔给整棵进程树发 SIGTERM 时，管理进程自己也收到了），管理进程跟着以 0 退出，不重启；
  - 78：配置错误，不重启。升级过程中出现就算预检失败；
  - 其他：退避后重启，规则同 ADR-0039"崩溃重启"。启动器自己会重启核心，所以这种情况很少见。
- **停止的时间**：管理进程收到停止信号后发 `shutdown`，35 秒后还没退出就强杀启动器（启动器 30 秒强杀核心，核心自己 35 秒兜底）。外面监管方的停止超时照旧是 40 秒。
- 只有带这份约定的版本才能放进 `releases/`。清单里每个版本写明它要的管理进程协议版本 `managerProtocol`。

### 控制通道

- POSIX 上是 unix socket `releases/manager.sock`，Windows 上是命名管道 `\\.\pipe\nextskin-<实例目录的 hash>`。一行一个 JSON 请求。
- **令牌**：管理进程每次启动生成 32 字节的随机令牌，写进 `releases/manager.token`（POSIX 上 0600），并经环境变量交给启动器、再交给核心；命令行读这个文件。plugin host 的环境是空的（ADR-0009），拿不到。令牌不进日志（不变量 11）。
- **只接受这些请求**：
  - `status`：当前版本、上一个版本、进行中的升级和进度、最近一次的结果；
  - `check`：读清单，列出比当前新的正式版；
  - `prepare <版本>`：执行流水线的准备阶段，站点照常运行；
  - `apply <版本>`：执行切换，MySQL、PostgreSQL 带迁移时要带 `backupConfirmed`；
  - `rollback`：回到 `previous`，规则见"回滚"；
  - `cancel`：只在准备阶段有效。
- **不接受路径和地址**，版本必须在签过名的清单里。不能换到比 `previous` 更旧的版本：核心被攻破时，最多能触发安装官方签过名的新版本，不能被装回有已知漏洞的旧版本。
- 核心一侧是新的领域用例：只有超级管理员能调，每次 `prepare`、`apply`、`rollback` 写审计日志，记下操作者、目标版本和是否确认了备份（ADR-0027）。
- 落地补充：
  - 协议是一次连接一个请求、一行 JSON，`prepare`、`apply`、`rollback` 校验完就回 `accepted`，在后台执行，进度从 `status` 读；`apply`、`rollback` 等响应写完、连接关上才开始停站。`check` 没有做成控制请求：核心自己每天检查，命令行的 `update --check` 在本进程里读清单。格式见 `packages/manager/README.md` 和核心的 `packages/domain/src/updates/manager-client.ts`。
  - socket 的路径超过 100 字节时改放 `os.tmpdir()/nextskin-<hash>.sock`。Windows 的命名管道 Node 设不了访问控制，只靠令牌。
  - 管理进程的错误码在核心里加 `update_` 前缀再交给前端，免得 `busy`、`internal` 这类名字占掉全局的错误文案；后台优先显示管理进程给的那句说明。

### 更新检测

- **清单**：`https://dl.nextskin.org/releases/v1.json`，是一组版本条目。只收正式版，每个条目写：
  - 版本号、发布日期、发布说明的链接、是否含安全修复；
  - ZIP 的文件名、SHA-256、大小；
  - 最低 Node 版本、`managerProtocol`。
  - 落地补充：条目里没有下载地址，由版本号和文件名拼出来（`packages/updates` 的 `downloadUrls`）。"是否含安全修复"先不进条目：签名在批准发布任务时完成，那时发布说明还没写，见 `docs/PROGRESS.md`。
- **每个条目单独签名**，不签整份清单：
  - ed25519，用 `node:crypto` 校验，不加依赖。公钥内置在核心和管理进程里。
  - 私钥是 environment `release` 的 secret。签名在批准后的发布任务里完成，签的是这个版本的条目和 `SHA256SUMS`，两份签名作为 Release 的附件。草稿发布后把条目合进清单、上传到 R2 的工作流只搬运签好的条目，用不到私钥。
  - 手动下载的服主也能核对：`SHA256SUMS.sig` 可以用 OpenSSL 3 校验（`openssl pkeyutl -verify -pubin -inkey 2026-10.pem -rawin -in SHA256SUMS -sigfile SHA256SUMS.sig`），部署文档写明，公钥另放在文档站（`/release-keys/<key id>.pem`）和仓库里，测试守着它和内置的一致。
  - 换密钥要先发一个内置了新公钥的版本。
- **防的是什么**：
  - Cloudflare 账号或任何下载渠道被攻破：攻击者能换掉 ZIP、`SHA256SUMS` 和清单，但签不出条目，管理进程和核心都拒绝。最多扣住新版本不让站点看到，或者让下载失败；后台显示最近一次成功检查的时间，扣得久了看得出来。
  - 拿旧的条目冒充：只认比当前新的版本，回滚只能回到 `previous`（见"控制通道"）。
  - 防不了 GitHub 被攻破：拿到维护者账号的人能批准发布任务、用私钥签名。见"考虑过的其他方案"里的离线签名。
- **谁来检测**：核心的定时任务 `core:update-check`，每天一次（ADR-0029）；后台也能点"检查更新"。
  - 请求不带查询参数和自定义请求头，不带站点地址、站点名、用户数这类信息。对比在本地做。
  - 设置项 `updates.check`，在"高级"分区，默认开（ADR-0028）。关掉后不发任何请求，后台显示"已关闭"。
  - 发现新版本：后台概览和更新页显示提示；每个版本给超级管理员发一次系统通知（ADR-0052，新类型 `update.available`）。含安全修复的版本在提示里标出来。
- **管理进程自己再读一次清单**，不信核心转来的数据。
- **下载渠道**：
  - ZIP 和清单放 R2，由一个只有几行的 Worker `nextskin-dl` 经 R2 绑定读出来返回。它挂在路由 `dl.nextskin.org/*` 上，`dl` 是不开代理的 CNAME，指向 `edge.nextskin.org`，和文档站、宣传站一样走优选 IP（ADR-0054）。不用 R2 的自定义域和 `r2.dev`，原因见背景。
  - R2 不收出流量费，免费额度是每月 10 GB 存储、1000 万次读；Worker 免费档每天 10 万次请求。Worker 只是把 R2 的流原样转出去，用不了多少 CPU。
  - GitHub Releases 作第二个地址：管理进程先试 `dl`，失败再试 GitHub。国内访问 GitHub 慢（ADR-0040"下载渠道"）。
  - 和文档站一样，优选 IP 没在国内网络上实测过（ADR-0054）。
  - 代理沿用 Node 的 `NODE_USE_ENV_PROXY` 和 `HTTPS_PROXY`，落地时核对 Node 24 上能不能用。

### 升级的流水线

**准备**（`prepare`，站点照常运行，任何一步失败就删掉 staging、报告原因）：

1. 取清单，核对目标版本条目的签名；目标版本比当前新；`managerProtocol` 不高于本管理进程支持的。
2. 检查剩余空间：ZIP、解压后的程序，SQLite 还要加上库的大小（备份）。
3. 下载到 `releases/.staging/`，核对 SHA-256 和大小。
4. 解压：拒绝绝对路径、`..` 和链接，只取 `releases/<版本>/` 和 `manager/`。解压完改名成 `releases/<版本>/`。Node 没有内置解压 ZIP，打包一个纯 JS 的实现（ADR-0008）。
5. 预检：对着在用的库运行新版本的 `doctor --json`，只读。得到：
   - Node 版本够不够（面板装的 Node 不会跟着升级）、配置能不能解析、数据库连不连得上；
   - 方言；
   - 待执行的核心迁移，以及已启用的官方插件待执行的迁移；
   - 已安装的插件里，声明的 `api` 和新版本的插件 API 版本不合的；
   - 这次升级落在下面哪一档。

   结果交给后台显示：要停多久（几秒到三十多秒）、要不要先备份、哪些插件会受影响。

**切换**（`apply`）：

6. 按档位核对：MySQL、PostgreSQL 有迁移而请求里没有 `backupConfirmed` 就拒绝。
7. 给启动器发 `shutdown`，等它退出。管理进程随后自己拿住数据锁，挡住这期间的 `start` 和导入，直到第 10 步拉起新版本之前才放开。
8. 运行新版本的 `migrate --json`，得到执行了哪些迁移、SQLite 备份在哪里：
   - `migrate` 改为同时执行已启用的官方插件的迁移；
   - SQLite 的迁移前备份改为"核心或已启用的官方插件有要执行的迁移"时触发，`openCore` 里的同一条规则一起改。
9. 改 `current.json`：`current` 是新版本，`previous` 是旧版本。
10. 拉起新版本的启动器，等它的 `ready`，再请求 `http://127.0.0.1:<端口>/api/health`（监听 `::` 时用 `::1`）直到 200，最多等 2 分钟。迁移在第 8 步做完了，这里不受库的大小影响。
11. 成功：写 `update-log.jsonl`；把新的 `manager/` 放进 `manager.next/`；删掉 `current`、`previous` 以外的版本目录（Windows 上删不掉的下次再删）。

**失败时**：

| 失败在 | SQLite | PostgreSQL | MySQL、MariaDB |
|---|---|---|---|
| 1–5 准备 | 站点没停，删掉 staging | 同左 | 同左 |
| 8 迁移 | 库没变（整批一个事务），换回旧版本启动 | 同左 | 库可能停在中间：换回旧版本启动；旧版本打不开时就停在那里，状态写明要用升级前的备份恢复 |
| 10 没有迁移 | 换回旧版本启动 | 同左 | 同左 |
| 10 有迁移 | 停掉新版本，用第 8 步的备份换回库（连同删掉 `-wal`、`-shm`），换回旧版本启动 | 旧版本会拒绝迁移过的库，不自动回滚：新版本留着（核心打开失败时每个请求都会重试），状态写明要人工处理 | 同左 |

- 自动回滚只发生在新版本一直没通过健康检查的时候。那时核心没打开过，没有写入，换回备份不丢数据。
- 失败的版本在 `current.json` 里记下，后台不再把它当作"可以升级"，直到清单里出现更新的版本或管理员重新选它。
- 最近一次的结果存在 `update-log.jsonl`，新起来的核心经 `status` 读到，后台显示"已升级到 0.5.0"或"升级失败，已回到 0.4.0，原因……"。

### 回滚

`rollback` 只回到 `previous`：

- 那次升级没有迁移：直接换回去。
- SQLite 有迁移：用那次升级的备份换回库。后台和命令行写明"升级以后的所有写入都会丢失"，要确认。之后上传的材质文件留在存储里，由孤儿文件的回收清掉（ADR-0029）。
- MySQL、PostgreSQL 有迁移：程序不碰库。管理员先自己用备份恢复，再确认"库已经恢复到升级之前"，管理进程只换程序。

### 手动解压

- ZIP 的顶层照旧是 `nextskin/`（ADR-0040），内容就是上面的布局，**不带 `current.json`**。覆盖解压照旧就是升级，面板里的启动命令（`npm start` 或 `node nextskin.mjs start`）不用改。
- 管理进程的版本号就是打包时同一个 ZIP 里那个版本的版本号。启动时发现自己的版本不同于 `current.json` 里的 `bundled`，就当作一次手动升级：从第 5 步开始走同一条流水线（不下载），失败时同样回到 `current`。一键升级在第 11 步就把 `bundled` 记成新版本，下次启动不会误判。
  - 落地补充：MySQL、PostgreSQL 有迁移时，启动不替管理员确认备份：照旧运行 `current`，日志说明要先备份、再到后台确认或运行 `update --backup-confirmed`；准备好的结果留着，后台确认后直接切换。
- **从旧布局换过来**：第一次启动时根目录里有 `server/`、`cli/`，没有 `current.json`。这一次没有 `previous`；新版本通过健康检查后删掉 `server/`、`cli/`。
  - 要回到旧布局的版本，照 ADR-0040 的手工回退解压旧版本的 ZIP：旧的启动器在根目录里运行，按自己的目录找 `server/`、`.env`、`data/`，不理会 `releases/`。
  - 旧版本没有这份约定，不能放进 `releases/` 由管理进程启动。
  - 落地补充：从旧布局换过来失败时以 78 退出，不让面板和 systemd 反复重启、每次重跑预检和迁移；旧程序还在，按上面手工回退。

### 管理进程自己的更新

- 管理进程是被面板或 systemd 监管的主进程，替换不了正在运行的自己。新版本带来的 `manager/` 先放进 `manager.next/`，**下次服务重启时**由入口换上：`manager.next` 的版本比 `manager` 新才换。
- 入口 `nextskin.mjs` 只做三件事：查 Node 版本（ADR-0039）、换上待生效的管理进程、加载它。覆盖它不影响正在运行的进程。
- 目标版本要求的 `managerProtocol` 高于现有的管理进程：`prepare` 拒绝，提示"先重启一次服务，让新的管理进程生效"。协议要尽量少改，这种情况才少见。

### 各部署方式

后台的更新页在所有部署方式上相同：当前版本、部署方式、新版本和发布说明、预检结果、备份要求、上一次升级的结果。只有最后一步不同。

| 方式 | 一键 | 说明 |
|---|---|---|
| systemd | 能 | `ExecStart` 照旧指向 `nextskin.mjs start`，`KillMode=mixed`、`TimeoutStopSec=40`、`RestartPreventExitStatus=78` 不变。能做权限分离（下一节） |
| 宝塔 Node 项目 | 能 | 停止时整棵进程树都收到 SIGTERM，见"退出码"；重启不等旧进程退出，见"管理进程的锁"。每次启动都 `chown -R` 给运行用户，做不了权限分离。Node 是面板装的，第 5 步拦住提高了 Node 下限的版本 |
| 1Panel 运行环境 | 能 | 代码目录挂进容器、可写，启动命令照旧是 `exec node nextskin.mjs start`，管理进程是 PID 1。Node 版本由运行环境的镜像决定，提高下限时提示去面板里换 |
| MCSManager | 能 | "终止"强杀最外层的进程，靠"IPC 断开就停"；运行用户要能写 `releases/` |
| Windows（控制台、NSSM） | 能 | 停止只经 IPC；Ctrl+C 会发给同一个控制台里的所有进程，落地时实测三层进程各自怎么处理；删旧版本目录、替换 `current.json` 被杀毒软件占着时重试 |
| Docker、Compose | 不能 | 镜像不可变、根目录只读、版本就是标签（ADR-0040）。镜像里设 `NEXTSKIN_MANAGER=off` 和 `NEXTSKIN_DEPLOYMENT=docker`，更新页显示 `docker compose pull && docker compose up -d` 和备份提示。SQLite 的迁移前备份照样生效 |

镜像里不做一键升级：在容器里改程序违背只读根目录；挂 Docker socket 等于把宿主机的 root 交给核心。

### 权限分离（可选）

一键升级要求程序目录对某个用户可写。可写的如果就是运行核心的用户，核心被攻破后，攻击者可以自己放一个"版本"进 `releases/`、改掉 `current.json`，下载时的签名校验就形同虚设。

- **能分离的部署**（systemd、MCSManager）：管理进程以单独的用户运行，`nextskin.mjs`、`manager/`、`releases/` 归它，服务用户只读；`.env` 和 `data/` 归服务用户。管理进程拉起启动器时降到服务用户（`spawn` 的 `uid`、`gid`），令牌文件只有管理用户能读。核心只能经控制通道发白名单里的请求。
- **不能分离的部署**（宝塔、1Panel、Windows）：服务用户本来就能写程序目录。部署文档写明这是便利和隔离的取舍。
- **不想要一键升级的**：让程序目录对运行用户只读，或者设 `NEXTSKIN_MANAGER=off`。管理进程发现写不了 `releases/` 时只检测，更新页说明原因。
- 落地补充：
  - 降权要 CAP_SETUID，所以"单独的用户"就是 root：环境变量 `NEXTSKIN_RUN_AS=<服务用户>` 打开分离，用 `id -u`、`id -g` 解析（走 NSS）。启动器、预检的 `doctor` 和 `migrate` 都降到这个用户，去掉 `HOME`、`USER`、`LOGNAME`。
  - socket 是 `root:<服务用户的组>`、`0660`，核心连得上、别的用户连不上；令牌文件仍只有 root 能读，核心只从环境变量拿令牌。管理进程自己写进数据目录的文件（新建的数据锁、SQLite 回滚换回的库）改归服务用户；分离时数据锁用内存 journal，不留 root 的 `-journal`。
  - 服务停着时命令行自己执行的 `update`、`rollback`，以 root 运行而没设这个变量、数据目录又属于别的用户时拒绝（78）：root 跑的迁移会在数据目录里留下服务读写不了的文件。常驻的管理进程不查：没有降权时它拉起的服务和迁移是同一个用户。
  - 在容器里以 root 实测过降权、socket 和令牌的归属与访问；systemd 单元本身没有实测。

### 命令行

- 新命令：
  - `update [--check] [--to <版本>] [--yes] [--backup-confirmed]`：服务运行时经控制通道交给管理进程；服务停着时命令自己执行同一条流水线（拿管理进程的锁和数据锁），最后不启动服务。
  - `rollback [--yes]`、`update status`、`releases`（列出版本目录和指针）。
- 其余命令由入口转给当前版本的命令行，带上 `NEXTSKIN_HOME`。部署文档的命令表不变。
- 落地补充：服务停着时的 `update`、`rollback` 迁移、改指针，不启动服务，也就不做健康检查（新版本有问题要等下次启动才知道），部署文档写明了。不是终端时要 `--yes`。

### 发布流程

- 发布任务在批准后生成并签名这个版本的条目和 `SHA256SUMS`，附在草稿 Release 上。草稿发布时，和加镜像标签的工作流一样，另一个工作流把 ZIP 和签好的条目上传到 R2、重新生成 `v1.json`。它用的 Cloudflare 令牌只有这个桶的写权限，和私钥不在同一个 environment。预发布不进清单。
  - 落地补充：工作流是 `release-dl.yml`。上传用只能读写这个桶的 R2 S3 凭据，放在单独的 environment `dl`；Worker 用 `docs` environment 的令牌部署，同文档站。清单每次从所有正式版 Release 附带的 `release-entry.json` 整个重建，R2 上缺的 ZIP 顺手补传，所以失败了重跑一次就行。
- e2e 加升级用例：从上一个正式版的 ZIP 经管理进程升到这次构建的版本，SQLite 和 PostgreSQL 各一遍；注入"健康检查不过"和"迁移失败"，核对回滚。
  - 落地补充：分成三处。从上一个正式版覆盖解压升级（真的迁移、真的健康检查）是发布工作流里的冒烟（`packages/manager/scripts/upgrade-smoke.ts`），SQLite 和 PostgreSQL 各一遍（PostgreSQL 有迁移时照部署文档停着服务运行 `update --backup-confirmed`，再启动），要下载上一个正式版，不进 CI。e2e 里另起一个经管理进程运行的实例，核对控制通道从核心到管理进程走得通；其余六个服务设 `NEXTSKIN_MANAGER=off`，共用一个发行目录也不会抢管理进程的锁，也不在要打包的目录里留下 `current.json`。"健康检查不过""迁移失败"和各档的回滚由 `packages/manager` 的测试用假的版本启动器注入，没有签名清单就做不了的一键升级全程也在那里测。
- 发布说明照旧要写有没有迁移（ADR-0040）；后台显示的迁移情况以预检的结果为准。

### 落地

分五个切片，前两个不依赖管理进程，在现在的布局下就能做完、测完：

1. **更新检测**：签名、R2 和 `nextskin-dl`、发布工作流、`core:update-check`、设置项、通知、后台提示。
2. **启动器和命令行一侧**：`NEXTSKIN_HOME`、被监管的模式（转发 `ready`、IPC 断开就停）、`doctor --json`（含官方插件的迁移和插件 API 是否兼容）、`migrate --json` 和执行官方插件的迁移、备份的触发条件。
3. **管理进程和版本目录**：入口、锁、监管、流水线、手动解压、从旧布局换过来、e2e 的升级用例。
4. **控制通道、后台的更新页、`update` 和 `rollback` 命令**。
5. **部署文档**：每种方式的一键升级，systemd 的权限分离；在宝塔、1Panel、Windows（含 NSSM）上实测。

落地时要验证：

- unix socket 的路径长度上限（Linux 108 字节、macOS 104 字节），超了换到哪里；
- Windows 上 Ctrl+C 和关闭控制台时三层进程的停止顺序，命名管道的访问控制；
- 管理进程常驻的内存；
- 宝塔停止、重启时三层进程的表现。

## 后果

- ZIP 部署能在后台一键升级，失败时按档位回滚；所有部署方式都能在后台看到新版本、发布说明和预检结果。
- 多一个常驻的 Node 进程（管理进程）。
- 磁盘上常驻两个版本的程序（各约 60 MB），升级时再加 staging。
- 每次升级停几秒到三十多秒，期间反向代理返回 502。SQLite 只能有一个写进程，做不了蓝绿切换。
- 站点每天向 nextskin.org 发一次请求，可以关掉。
- 发布流程多一把签名私钥要保管；私钥泄露时，已经发出去的管理进程会接受攻击者签的条目，只能发新版本换公钥、让服主手动升级。
- Cloudflare 账号被攻破时，攻击者能扣住新版本，但推送不了代码。
- 不能做权限分离的部署上，服务用户能改程序文件。
- 回到旧版本后，新版本排进队列、旧版本不认识的任务进死信（ADR-0051），重新升级后可以重试。
- 从旧布局换过来的那一次没有可回滚的上一个版本。

## 考虑过的其他方案

- **启动器自己升级，不另加管理进程**：正在运行的是旧版本的启动器，它要么用旧代码监管新版本的核心，版本之间的耦合比一份小约定大得多；要么升级完以特殊退出码请外面重启自己，宝塔、手动运行的控制台外面没有人重启它。
- **核心自己下载、替换程序**：核心是最容易被攻破的进程，又正是要被替换掉的那个。
- **原地覆盖，旧文件挪进备份目录**：中途断电会留下一半新一半旧的程序；Windows 上占用中的文件改不了名；回滚要再拷一遍。版本目录加指针，切换只是改一个文件。
- **用符号链接 `current -> 0.5.0`**：Windows 的问题见上。
- **控制请求经 IPC 一路转发（核心 → 启动器 → 管理进程）**：省掉 socket 和令牌，但命令行进不了这条链，最后还是要一个 socket，两种通道不如一种。
- **Docker 里也一键升级**（挂 Docker socket、Watchtower 这类工具）：见"各部署方式"。
- **只用 HTTPS 和 `SHA256SUMS` 校验，不签名**：信任绑死在下载渠道上。Cloudflare 账号被攻破时，ZIP 和 `SHA256SUMS` 能被一起换掉，国内的镜像渠道也就没法用。
- **签整份清单，带一个递增的序号**：能发现清单被换成旧的，但整份清单要在草稿发布后的工作流里重新签，私钥就得离开要批准的那一步。条目签名下扣住新版本照样做得到，靠"最近一次成功检查的时间"看出来。
- **ZIP 放 Workers 静态资源**：单个文件 25 MiB 的上限迟早会撞上；每次部署都要带上全部历史版本，而它们不在仓库里。
- **离线签名**（私钥只在维护者的机器或硬件密钥上，每次发版在本地签）：GitHub 被攻破也签不出来，代价是发版多一步手工操作，现在不做。折中的做法是另内置一把离线保管的备用公钥，只用来签"不再信任 CI 那把钥"的声明，清单里带上它，已发出去的站点读到就生效，不用等手动升级。等用户多了再考虑。
- **MySQL、PostgreSQL 由程序自动备份**（调 `mysqldump`、`pg_dump`，或者自己导出）：机器上不一定有这些工具；库可能很大，导出时还要处理一致性和锁表。ADR-0040 已经决定不做。
- **降级迁移**：ADR-0040 决定不做，回退靠备份。
- **让旧版本接受只加列、加表的新迁移**：这样的升级不用恢复库就能回滚，但每个迁移都要按"旧版本还能用"来写和审查，现在不做。
