# ADR-0006 新 schema + 只读导入器，不沿用旧表结构

- 状态：已采纳
- 日期：2026-10-16

## 背景

两份研究报告都建议沿用 BS 现有的表结构，在原库上直接升级。那个建议的前提是新旧系统需要并行运行、随时回滚到 Laravel，而 ADR-0001 已经放弃了这个前提。

旧 schema 的问题：没有外键；主键命名不统一（`uid`、`pid`、`tid`）；配置以字符串键值对存储；权限是一个整数；计数字段冗余。新功能（RBAC、会话、通行密钥、审计、插件注册表、outbox）也都需要新表。

## 决定

- NextSkin 使用自己设计的新 schema。
- 提供导入命令 `nextskin import blessing-skin --from <dsn>`：
  - **只读**旧库，旧库可以和新库在同一台数据库服务器上；
  - **幂等**，可以重复运行，大站可以先试跑，切换前再做一次最终同步；
  - 结束时输出对账报告：各表行数、材质文件是否存在、抽样比对结果。
- 必须原样保留的数据：
  - `uid`、`pid`、`tid` 的数值，旧链接只需 301 跳转；
  - 材质 hash 和材质文件，文件不重新编码；
  - 密码 hash，用旧算法校验，用户登录成功后重新哈希（ADR-0007）；
  - 玩家名、邮箱、积分、衣柜、举报记录、OAuth client；
  - **yggdrasil-api 插件自建的 UUID 映射表和 RSA 签名私钥**。
- 回滚方式：服主切回旧站即可，旧库在整个过程中从未被写过。

## 后果

- UUID 是整个迁移中后果最严重的一项：只要玩家的 UUID 变了，所有游戏服务器上的背包、领地、权限数据都会和玩家对不上。导入器必须有专门针对这一项的测试，对账报告必须单独列出 UUID 的比对结果。
- 新上传的材质用新的图像管线规范化后计算 hash。同一张图如果在旧版上传过、在新版再上传一次，会因为字节不同而多存一份。这个代价可以接受，不需要为此和 Imagick 做到字节级一致。
- 新库切换上线后产生的写入不会回流到旧库，所以"回滚"只在切换后很短的窗口内是无损的。这一点要在文档里写明。

## 考虑过的其他方案

- **沿用旧 schema、原地升级**：节省了导入步骤，但把旧 schema 的全部问题带进新系统，并且回滚无法做到"旧库从未被写过"。
- **Expand/Contract 渐进迁移**：适合一个持续运营、需要不停机的站点，不适合分发给成千上万服主的软件。
