- 日期：2026-10-18
- 补充 ADR-0009：启动器落地之前，plugin host 由核心进程拉起；多实例部署时各实例自己换代
- 补充 ADR-0010：第一版的公开面；插件不能自己开事务；事务内的拦截器只能访问插件自己的表
- 补充 ADR-0011：第一版只有声明式 UI，运行时组件推迟
- 取代 ADR-0018 里"验证码由官方插件接"的部分：验证码以后做进核心

## 背景

ADR-0009、0010、0011 定了插件系统的形状，也就是它的上限：
- 安装插件跑在 plugin host 里，拿不到数据库凭据，热重载按整个 host 换代；官方插件在核心进程里，用同一套 API；
- 插件用一个声明式对象定义，构建时提取成 manifest；六类扩展点；没申请的能力在类型上就不存在，运行时核心也会拒绝；
- 插件只接触 DTO，不接触表结构；没有通用 filter，不能往页面注入 HTML。

S2、S3、S5 都已通过。SDK 草案在 `packages/plugin-sdk`：17 个事件、6 个拦截点、4 类 Provider、10 项能力、3 个可以加字段的表单、5 个插槽，外加运行时组件。

核心这边已经有的：
- 事件在业务事务里按订阅者展开成任务（ADR-0021）。SDK 的 17 个事件里，16 个已经在各个用例里发出，只有 `user.loggedIn` 没有；
- 任务、死信、定时任务（ADR-0021、0029），任务名已经留好了插件的格式：`plugin:<id>:job:<任务名>`、`plugin:<id>:on:<事件名>`；
- 设置表单从 JSON Schema 生成，机密项加密存储（ADR-0028），当时就定了插件的设置页复用它；
- 具名权限和 `can()`，管理员和超级管理员拥有全部插件权限（ADR-0027）；审计日志的操作者可以是插件；
- `docs/schema.md` 定了 `plugins`、`plugin_kv`、`plugin_migrations` 的要点。

还没有的：
- 一个拦截点都没实现，注册用例里只留了注释（`users/register.ts`）；
- plugin host、启动器、构建命令 `nextskin-plugin build`；
- 通知（`notifications` 表只有要点）、第三方登录（ADR-0023 推迟了）、站点的 CSP。

约束：
- **插件 API 是 semver 契约**（ADR-0010 第 6 条）：新增是次版本，删除、改名、收窄是大版本。第一版放进去的东西就收不回来。SDK 还没发布，现在删是免费的。
- **SQLite 的写锁是全局的**（ADR-0008），事务里不能等慢操作。草案里 `user.register` 在事务内调用、预算 1500 ms：注册事务要握着写锁等一次跨进程调用，插件在里面发网络请求，全站的写入最多排队 1.5 秒。注册事务还由 `transactionWithRetry` 执行，可能整体重跑，拦截器也就可能被调用不止一次。
- S5 留下五个上线前必须处理的风险；节点树重建器修完问题后，没有再独立审核过。

要定的：
- 第一版开放哪些扩展点，草案里其余的部分怎么处理；
- 安装插件是否进第一版；
- 事务内拦截器的约束；
- plugin host 由谁拉起，多实例怎么同步；
- 安装、升级和卸载的流程；
- 验收标准、落地顺序和测试。

## 决定

### 原则：机制按最终形态做，公开面按需要开

- **机制**：进程边界和 RPC、manifest、能力的运行时检查、DTO 的可序列化、整代切换、插件表的网关。这些以后改不动，又是安全边界，第一版就按 ADR-0009、0010 的最终形态做。
- **公开面**：事件、拦截点、能力、Provider、表单、视图的种类。只开参考插件用得到的；以后要加，按插件 API 变更的流程走，是次版本。
- **SDK 1.0 只包含核心已经实现的东西。** 草案里推迟的部分从 SDK 删掉，设计留在 ADR-0010、0011 和 git 历史里。不留"类型里有、运行时拒绝"的东西：类型就是契约，留着就等于承诺。

### 验收：参考插件

下面四个参考插件只用公开 API 写成，放在 `plugins/*`。每一个都在两条加载路径（核心进程内、plugin host）上各跑一遍端到端测试，第一版才算完成。

| 参考插件 | 来源（ADR-0010） | 覆盖的扩展点 |
|---|---|---|
| 邀请码 | invitation-codes | 设置、插件权限、自有表和迁移、注册表单加字段、事务内的拦截器、事件、路由、后台表格页 |
| CDN 刷新 | refresh-ali-cdn、refresh-qcloud-cdn、purge-azure-global-cdn，合并成一个，设置里选服务商 | 事件、出站白名单、机密设置、重试和死信 |
| AuthMe 密码 | authme-integration 的密码部分 | passwordHasher |
| 第三方登录 | oauth 和 oauth-github、google、microsoft-live、littleskin，合并成一个 | login |

mojang-verification 和 forum-integration 不在第一版：前者要写核心数据（见"推迟"），后者还要连外部数据库。

### 第一版的公开面

**定义**：`definePlugin` 保留 `capabilities`、`network`、`settings`、`permissions`、`tables`、`migrations`、`on`、`intercept`、`providers`、`routes`、`jobs`、`cron`、`ui`。逃生舱 `setup` 推迟。

**事件**：现在已经发出的 16 个。`user.loggedIn` 删掉：登录在 Better Auth 里完成，核心还没有在事务里发它的位置，也没有参考插件需要。

**拦截点**：只有 `user.register`，并且不能改字段（`patch` 是 `never`）。
- 不能改字段的原因：昵称在事务之前校验，注册时还可能同时建同名角色。允许插件改昵称，就要在事务里重新校验，还要决定角色名跟不跟着改。邀请码只需要拒绝。
- 所有新建用户的路径都要经过它：注册表单，以后还有第三方登录的首次建号。安装向导创建第一个超级管理员时还没有插件；导入器不经过领域用例（ADR-0031）。这两处不调用。
- 策略改为：失败时拒绝（`closed`）、预算 300 ms、在事务内。四种数据库用同一个预算，这样在 PostgreSQL 上测过的插件，到了 SQLite 上表现也一样。邀请码在拦截器里只有一条带条件的 UPDATE，跨进程也只要几毫秒。

**事务内的拦截器只能访问插件自己的表**：
- `ctx` 里只有 `db`（加入核心事务），以及不用等核心回应的 `plugin`、`site`、`settings`、`t`、`log`、`signal`。`fetch`、`kv`、`jobs` 和读核心数据都不给，注册需要的信息都在 `input` 里。SDK 按 `interceptorPolicies` 在类型上收窄上下文，核心在运行时同样拒绝这次调用里的其他 RPC。
- 理由：写锁只等得起本地的数据库操作。事务整体重跑时，`db` 的写入随之回滚，可以安全地再来一次；网络请求回滚不了，KV 和入队也不加入核心事务。
- 需要访问外部系统才能决定放不放行的插件（例如查论坛账号），第一版写不出来。以后按需要加一个不在事务内的注册拦截点。

**能力**：`users.read`、`users.readPrivate`、`players.read`、`textures.read`、`textures.readFile`、`storage.kv`、`storage.tables`。
- 这些都只读核心数据，或者读写插件自己的数据。核心数据的 DTO 大多已经通过事件成为契约的一部分，按 id 读取的成本很低。
- `users.score`、`notifications.send`、`ui.script` 推迟。

**存储**：
- **KV**：按插件隔离，值是 JSON，单个值不超过 64 KB（同任务的载荷）。`ttlSec` 记成过期时间，读的时候过期就当作不存在，由定时任务清理。
- **插件自有表**：照 S5 的规则。把重建器从 `spikes/` 移植进核心时按 AGENTS.md 重新审视，移植后做一次独立审核。
- **插件不能自己开事务**：`ctx.db` 在类型上去掉开事务和独占连接的方法，网关也会拒绝。插件的每条语句单独提交，需要原子性就用一条带条件的语句（邀请码就是这样）。这样 S5 遗留风险的第 2 条就不存在了，事务的并发上限、时限、过期提交的拒绝也都不用做。
- S5 遗留的另外四条，第一版一起做：
  - 读查询走装了 authorizer 的专用 worker 连接，带期限函数，卡住时换掉 worker（S2 的架构 E）；
  - 语句级超时；
  - 结果行数上限下推成 LIMIT；
  - IPC 消息的大小上限。

**路由**：照 SDK，挂在 `/plugins/{id}/*` 下。
- 登录态只认会话 Cookie（同 ADR-0022），Cookie 登录的非 GET 请求校验 Origin。
- 请求体完整读入后转发，响应体同样有大小上限，不支持流式响应。

**UI**：只有声明式的。
- 导航项，`area` 是 `user` 或 `admin`。
- 页面：表格、表单、统计、Markdown 四种视图。Markdown 照 ADR-0028 的方式渲染，不渲染原始 HTML。
- 设置页由 settings schema 生成，复用 ADR-0028 的表单。
- 能加字段的表单只有 `auth.register`。`user.profile` 和 `texture.upload` 删掉：没有拦截点或事件能把这两处的字段值交给插件。

**Provider**：`passwordHasher` 和 `login`。
- **passwordHasher**：接在核对已存密码的函数上（`auth/password.ts`），网页登录和启动器登录都经过它。
  - 哈希既不是当前算法、也不是 BS 的旧格式时，先在核心进程里按各插件声明的 `detect` 匹配，匹配上了才发起跨进程调用。
  - 校验通过后，立刻换成当前算法（ADR-0007）。
  - 明文密码会交给插件，安装时按高风险展示。
  - 落地时补充：
    - 敏感操作前的核对密码（删除账号、改邮箱）也经过它，但不换算法，和 BS 旧格式一样。
    - 失败时关闭：没有插件认领、插件不可用、超时（每次 5 秒）、抛错、返回值不是布尔值、熔断中，都按密码不对处理。多个 Provider 匹配上同一个哈希时，按插件 id、再按声明顺序调用，有一个通过就算通过。日志只记插件 id、Provider 和失败原因，不记插件抛出的消息：消息里可能带着明文。
    - 换算法用带条件的更新，只替换核对过的那个旧哈希：网页登录在登录之后要再核对一次（等插件、算 bcrypt），这期间密码被重设或修改了，就不拿旧密码覆盖新密码。BS 旧格式原来的写法有同样的问题，一起改了；启动器登录本来就是这样。
    - 插件格式的哈希同样有 BS 的 trim 回退（ADR-0031）：按原值不通过、原值首尾有空白时，再用 trim 之后的值调用一次。核心之外的格式只能从 BS 导入，旧站的网页登录同样会 trim。
    - SDK 的 `verify` 去掉了 `uid`：Better Auth 核对密码时只给出哈希和密码，拿不到用户。哈希要带齐校验需要的信息（盐、算法参数）。
    - 导入器保留插件格式的哈希（补充 ADR-0031"认不出的哈希不建这一行"）：核心认不出、但看起来像哈希的值（8 到 255 个可打印的 ASCII 字符）原样保存，留给插件认领，报告里列出数量。authme-integration 在 `SALTED2MD5`、`SALTED2SHA512` 下把每个用户的盐存在 `users.salt` 列，导入器把盐和摘要拼成 `$authme$<算法>$<盐>$<摘要>`（`auth/legacy-passwords.ts` 的 `formatAuthmeSalted`），由 AuthMe 插件认领。
    - 官方插件 `authme-password` 认领 `$SHA$` 和 `$authme$` 两种前缀，算法照 AuthMe。旧插件"AuthMe 直接读写皮肤站的 users 表"那部分做不了。
- **login**：核心要先做第三方登录（账号绑定、解绑、首次登录建号），另写 ADR。
  - 首次登录建号也经过注册用例，`user.register` 拦截器和注册表单字段照样生效。否则从第三方登录就能绕过邀请码。

### plugin host

- **启动器落地之前，由核心进程拉起 host。** 核心在 `instrumentation.ts` 里打开时拉起它，和任务执行器的做法一样（ADR-0021）。
  - 启动参数照 ADR-0009：`--permission`，只能读插件目录，环境变量为空。（落地时 Windows 上留着 `SYSTEMROOT`：它是系统目录，不是机密，没有它 OpenSSL 取不到熵，`crypto.getRandomValues` 会抛错。）
  - host 和核心之间的 IPC 一断开，host 就自己退出，核心退出后不会留下孤儿进程。（落地时用 host 的 stdin/stdout 传带长度前缀的帧，不用 Node 内置的 IPC：内置 IPC 要把整条消息收完才解码，限不住消息大小。）
  - 启动器落地后，改由启动器拉起。
- **网络**：`ctx.fetch` 按 `network` 白名单检查。插件要是绕过 `ctx.fetch`，直接用 `node:net` 或全局的 `fetch`，就只能靠 Node 的权限模型拦。实现时确认 Node 26 的权限模型能不能限制出站网络：能就打开；不能，就把这一点照实写进安装界面和文档。这符合 ADR-0009"安全带而不是沙箱"的定性。（落地时确认：Node 26 的权限模型不给 `--allow-net` 就禁止出站网络和监听，host 照此启动；Node 24 拦不住，后台的插件页和安装确认框照实提示。）
- **只认 manifest**：
  - 核心按 manifest 登记路由、事件、拦截器、Provider、任务和定时任务，按 `plugins` 表里授予的能力放行 RPC。
  - 新一代 host 加载后报告各插件实际的定义；和 manifest 对不上，这一代的健康检查就失败，不切换。管理员确认的就是 manifest。
- **整代切换**照 ADR-0009。健康检查失败，就停在旧的一代，这次启用或升级报错。
- **多实例**：
  - 插件包存进 ADR-0002 的存储接口：默认是本地磁盘，多实例部署时是 S3 兼容驱动。每个实例换代之前，把本地还没有的版本取下来，按 `integrity` 校验后解到自己的 `data/plugins/{id}/{版本}/`。（落地时目录按插件包的 sha256 命名，即 `data/plugins/{id}/{sha256}/`：版本号相同、内容不同的两个包（同时上传、卸载后重装）不会解到同一个目录，正在运行的 host 不会读到别的包的代码。）
  - 每个实例有自己的 host。每个实例每 5 秒读一次 `plugins` 表里的启用集合（id、版本、授予的能力），和当前这一代不同，就自己换代。
  - 取不到表里这个版本的包（落地时补充）：这个实例上不启用它，旧版本的 manifest 和代码都不能代替新版本。不知道新版本拦不拦截注册，就按拦截处理，注册按失败策略关闭；它的路由返回 503；任务留在表里。后台照样列出它，标着"取不到插件包"，能停用、卸载，不能启用。
  - 迁移由处理管理员请求的那个实例在启用之前跑完。
  - 同一个插件的启用、停用、安装、升级、卸载和卸载后的清理，在各实例之间串行（落地时补充）：迁移、删存储里的插件包这些副作用回滚不了，事务里的行锁又不能跨过它们一直拿着。MySQL / MariaDB 用 `GET_LOCK`，PostgreSQL 用会话级的 advisory lock，都拿在一条专用的连接上，进程退出时数据库自动释放；每个进程同时只有一把锁占着连接（名字不同的排队），不会把连接池占满；SQLite 只有一个进程，用进程内的锁（`packages/db` 的 `withExclusiveLock`）。同名的锁拿不到时管理操作报"正忙"，清理任务推迟。改插件设置也拿这把锁，卸载之后不会被写回去。
  - 实例之间最多差 5 秒。这期间发出的事件，按发出事件的实例当时那一代的订阅者展开；ADR-0021 已经接受"之后才启用的插件收不到之前的事件"。
- **运行时防护**：
  - 每次调用都有超时。
  - host 崩溃后退避重启。短时间里连续崩溃，就不再重启，在后台的插件页提示管理员。这期间事件和任务留在表里，拦截器按失败策略处理，插件路由返回 503。
  - 某个插件的同一个拦截器或 Provider 连续失败，就在冷却期内不再调用它，直接按失败策略处理。这样 `user.register` 不用每次都握着写锁等满 300 ms。
  - 核心现在没有指标系统，第一版只记日志：插件 id、调用点、耗时、结果。插件自己的日志带插件 id，核心不检查内容；SDK 文档要求日志里不写机密（同 ADR-0021 对 `last_error` 的要求）。
- **官方插件**在核心进程内运行，同样经过网关、能力检查和超时。参数和返回值按 host 的 IPC 同样的方式序列化一次，在进程内就能发现不可序列化的数据。

### 安装、升级和卸载

- **权限**：新增具名权限 `plugins.manage`，只映射给超级管理员。安装插件等于在服务器上运行它的代码；改插件设置也和改核心设置一样，只给超级管理员（ADR-0028）。
- **页面**：
  - 后台的"插件"页（`/admin/plugins`）列出官方插件和安装插件，显示状态、最近的错误和该插件的死信（可以重试、删除）；
  - 插件的详情和设置在 `/admin/plugins/{id}`；
  - 插件声明的页面在 `/admin/plugins/{id}/{页面}` 和 `/user/plugins/{id}/{页面}`。
- **安装**：
  1. 上传插件包，不超过 10 MiB。
  2. 在临时目录里解包，然后校验：
     - manifest 的格式和版本、id 的正则；id 不能和官方插件相同；
     - `api` 范围包含核心的插件 API 版本；
     - 每个文件的 sha256 和 `integrity` 一致；没有符号链接，路径不越出包目录；
     - `requires`、`conflicts` 能满足。（落地时补充：反过来也查，已启用的插件依赖它时，不能停用、卸载它，也不能升级到不满足依赖范围的版本。）
  3. 展示 manifest 里的能力（高风险的醒目提示）、出站 origin、路由、事件、拦截点、Provider 和表。超级管理员确认后，把插件包存进存储接口，解到本实例的插件目录，写 `plugins` 表。这时还没有启用。
- **启用**：先在 host 里跑插件的迁移（DDL 只能在迁移调用里执行，ADR-0010），然后换代。
- **升级**：流程同安装。能力或出站 origin 比旧版本多的，列出差别，要求重新确认。不支持降级，因为迁移只能往前走。
- **停用**：保留数据和设置，任务留在表里（ADR-0021）。
- **卸载**：先停用，再照 `docs/schema.md` 删除它的表、KV、设置、迁移记录和未完成的任务，以及它的定时任务条目、死信和存储里的插件包。（落地时分两步：设置、任务、定时任务条目、死信和 `plugins` 表的行在一个事务里删，KV 和迁移记录随行级联；同一个事务登记一个 12 分钟后执行的清理任务，删表和插件包。各实例最多 5 秒后停掉它，旧的一代还要做完在途的调用，表不能当场删；清理任务在表里，进程中途退出也不会丢。插件的表按物理名的前缀 `p_<id>__` 找，不依赖 manifest：处理卸载的实例可能没有这个包。卸载之后别的实例在同步之前又写进来的任务和定时任务条目，也由清理任务删掉。第一次安装、卸载后又装回来时，总是先删掉这个 id 留下的表、设置和任务，再做掉还没做的清理，不只靠清理任务的记录：清理进了死信，死信过了保留期也会被删掉；迁移记录已经随行删掉，留下的表会让新装的插件的迁移失败。）
- **审计**：以上操作和插件设置的修改都写审计日志，机密项不记值（ADR-0028）。
- **插件设置的写入**：先按 JSON Schema 校验，再交给插件按它自己的 zod schema 解析一遍（一次 RPC），两边都通过才保存。这样插件 schema 里的 `refine` 也有效。host 不可用时不能改插件设置。
- **信任**：第一版只有上传，没有插件市场和签名。上传的插件就是管理员信任的代码，安装界面按 ADR-0009 的定性写明。

### 推迟

以后要加都是次版本，各自按插件 API 变更的流程走。

| 推迟的内容 | 原因 | 影响 |
|---|---|---|
| 写核心数据的能力：积分、通知、以指定 UUID 建角色等 | 写操作只能经过领域用例（不变量 4），要设计"插件以 `actor: plugin` 调用指定用例"，每个用例一项能力，并写审计日志；另写 ADR | mojang-verification 这类插件要等这一步 |
| 其余五个拦截点，以及拦截器改字段 | 每个点都要定输入、可改字段和失败策略，现在还没有插件需要 | |
| 运行时组件（`ui.script`）和插槽 | 它把 React 的大版本绑进插件 API；要先做 CSP nonce、import map、shim 的生成和回归测试；没有参考插件需要 | 插件只能用声明式界面 |
| 验证码 Provider | 它的挂件必须是运行时组件 | 验证码做进核心，见下 |
| 邮件通道 Provider | 核心自带 SMTP，也没有参考插件需要 | |
| 插件自己开事务 | 没有参考插件需要；推迟后，SQLite 上的整套时限机制都不用做 | |
| `setup` 逃生舱 | 没有参考插件需要；有了它，manifest 就不再能说明插件做的全部事情 | 需要常驻连接的插件写不出来 |
| 独占的 host、容器档位、插件市场和签名、只授予部分能力 | 第一版先把单个 host 和上传做好 | |
| `packages/plugin-testing` | 先在仓库里给参考插件写测试，接口稳定后再整理成给插件作者用的包 | |
| 主题扩展点（DESIGN.md §2.3） | 开放 token 会把 token 的名字冻住，而现在 token 还在变；需要时先在核心里做主题切换 | |

**验证码**做进核心：用设置项选择 Turnstile、hCaptcha 或 reCAPTCHA，和把 gtag 改成核心设置项是同一个思路（ADR-0010）。BS 的 reCAPTCHA 设置以后导入到核心的设置项。什么时候做另定，在那之前仍按 ADR-0018 的办法挡滥用。

### 不做

ADR 已经否决的不变：通用 filter、往页面注入 HTML、插件访问核心表、同进程 `import()` 热重载。

### 落地顺序

1. **核心侧和官方插件**：
   - 插件注册表，构建命令里提取 manifest 的部分；
   - 上下文和能力检查；事件、任务、定时任务的订阅；设置页；KV；
   - 插件表的网关和专用 worker 连接；路由网关；声明式 UI；
   - `user.register` 拦截器和注册表单的字段。

   邀请码和 CDN 刷新在核心进程内跑通。
2. **plugin host**：RPC、权限、整代切换、多实例的同步；构建命令打包的部分；安装、升级、卸载和审计。上面两个插件在 host 里再跑一遍。
3. **Provider**：passwordHasher 和 AuthMe 插件；第三方登录先写 ADR，再做核心部分和插件。

三步都完成后，发布 SDK 1.0。

### 测试

- **网关**：把 S5 的 47 项检查移植成 `*.db.test.ts`，在四种数据库上跑。
- **事务内的拦截器**：
  - 拦截器的写入随注册一起回滚；
  - 事务重跑时拦截器再调用一次，写入不重复；
  - 超时和熔断之后，写锁按时释放（SQLite）；
  - 调用 `fetch` 等其他 RPC 被拒绝。
- **host**：
  - 读不到 `.env`、数据目录和 SQLite 文件；
  - 崩溃后重启；
  - 换代时在途的请求能完成；
  - manifest 和实际定义不一致时，停在旧的一代。
- **参考插件**：两条加载路径上的端到端测试。
- **SDK**：type-tests 覆盖新增的约束（例如事务内的拦截器里没有 `ctx.fetch`），api-extractor 报告比对公开面。

## 后果

- SDK 1.0 的公开面比草案小很多：16 个事件、1 个拦截点、2 类 Provider、7 项能力、1 个可以加字段的表单，没有插槽。BS 用户依赖的插件里，要写核心数据、要在浏览器里运行代码、要提供验证码的，第一版都迁移不过来。迁移指南要逐一写明。
- 只要有插件订阅了 `user.register`，host 不可用时注册就关闭（`closed`）。这是有意的：邀请码检查失效时，不能放任何人注册。
- 每个参考插件都要在两条加载路径上测试，端到端测试的时间大约翻倍。
- 每个实例多一个 host 进程的内存。多实例部署时，各实例切换到新一代的时间最多相差 5 秒。
- 采纳时：
  - `docs/schema.md` 补上 `plugins` 的列（插件包的 hash、最近的错误）和 `plugin_kv` 的过期时间；
  - `packages/plugin-sdk/AGENTS.md` 改写"当前状态"一节；
  - ADR-0009、0010、0011、0018 的状态注明由本 ADR 补充或部分取代。
- 落地后，AGENTS.md 的"当前阶段"和目录表补上 plugin host 和 `plugins/*`。

## 考虑过的其他方案

- **第一版只做官方插件，安装插件以后再做**：省掉 host、上传和换代。但这样"API 能跨进程"得不到验证，等 SDK 发布之后才发现跨进程的问题，就只能升大版本。BS 生态的价值也正在第三方插件。
- **草案全部做进第一版**：公开面一次冻住。五个拦截点没有使用者，失败策略和预算没有经过真实插件的检验；运行时组件还把 React 的大版本绑进了插件 API。
- **保留草案，未实现的部分在运行时报"未实现"**：照着类型写出来的插件会装不上。类型就是契约。
- **事务内的拦截器照草案给全部能力，只靠超时约束**：SQLite 上写锁要等跨进程调用再加上网络请求；事务重跑时，网络请求和 KV 写入会重复。
- **照 S2 的方案给插件开事务，SQLite 上时限 100 ms**：可行，但没有参考插件需要。第一版省掉整套时限、并发上限和过期提交的拒绝。
- **plugin host 等启动器落地再做**：启动器还没有排期。先由核心进程拉起，接口和 ADR-0009 一致，启动器落地后只换掉拉起它的进程。
- **验证码等运行时组件落地后再由插件提供**：运行时组件推迟了，验证码就要跟着无限期推迟。主流的三家服务做进核心，代价只是几个设置项。
