# ADR-0026 衣柜、换材质和举报：依赖材质的写操作先锁材质行，不做被收藏奖励，举报奖励在采纳时才发

- 状态：已采纳
- 日期：2026-10-18

## 背景

ADR-0025 落地材质的上传、修改和删除，并建好 `closet_items`，但用户只能靠上传往衣柜里放东西。ADR-0022 把给角色换材质留到了衣柜，ADR-0023 把头像留到了材质。`reports` 表的设计在 `docs/schema.md`。

BS 6.0.2 的做法：

- **衣柜**（`ClosetController`）：
  - 加入时扣 `score_per_closet_item`（默认 0）；别人的私有材质不能加（管理员可以）；不能重复加；上传者得到 `score_award_per_like`（默认 0）；
  - 移出时开着 `return_score` 就按现价退，收回上传者的奖励，自己角色上用着它的清掉；
  - 不要求验证邮箱。
- **给角色换材质**（`PlayerController::setTexture`）：材质必须在自己的衣柜里。属于角色管理，开着"必须验证邮箱"时要先验证。
- **头像**（`UserController::setAvatar`）：任何公开的或自己上传的皮肤，不要求在衣柜里。
- **举报**（`ReportController`）：
  - 同一个人对同一个材质只能举报一次，无论之前的举报处理与否；
  - `reporter_score_modification`（默认 0）为负时是举报的花费，采纳后退还；为正时是提交就发的奖励，驳回时收回。采纳时另发 `reporter_reward_score`（默认 0）；
  - 管理员处理时可以删除材质、封禁上传者或驳回。

BS 这里的问题：
- **收藏数是先读、再算、再写回**（`$texture->likes++`），并发加入衣柜会丢更新；余额检查和扣分之间也没有锁。
- **被收藏奖励收回时不看余额**，直接扣成负数；收回时也不判断上传者是不是收藏者自己，自己移出自己的材质，会被收回一份从来没发过的奖励。
- **换材质不检查材质类型和槽位是否匹配**，可以把披风设成皮肤。
- **能按 tid 举报别人的私有材质**，借此确认它存在。
- **处理举报时选"删除材质"，直接删掉文件**，不看还有没有别的条目指向同一个 hash，那些条目的文件也跟着没了。

## 决定

### 范围

这次做：
- 衣柜：列表、加入、改名、移出；
- 给角色换材质、清除材质；
- 头像；
- 举报：提交、查看自己的举报；
- 材质详情页（ADR-0025）补上加入或移出衣柜、设为角色的材质、设为头像、举报。

不做：
- 管理员处理举报、管理别人的衣柜：是管理操作，随第一个管理操作和审计日志一起做。到时删除材质走 ADR-0025 的删除流程，不直接删文件；
- 被收藏奖励，理由见"积分"。

### 页面

- 衣柜是 `/user/closet`，我的举报是 `/user/reports`，两者加进用户中心的导航。
- 衣柜：皮肤、披风分两个 Tab，可以按名字搜索，每页 20 个。每一件可以改名、移出、设为角色的皮肤或披风、设为头像。空的时候提供"去皮肤库看看"（DESIGN.md §7）。
- 材质详情（ADR-0025）：加入或移出衣柜、设为角色的皮肤或披风、设为头像、举报。
- 角色管理（ADR-0022）："换皮肤""换披风"打开 Dialog，从衣柜里选，可以搜索；也可以清除。
- 个人资料（ADR-0023）的账号概况显示当前头像，可以清除。
- 我的举报：材质、理由、状态、提交时间。
- 数据流同 ADR-0022。换材质的 Dialog 要在浏览器里分页、搜索衣柜，为它加一个只读接口 `GET /api/closet`，仍然不引入 TanStack Query。

### 接口

都认会话 Cookie（ADR-0022）：

| 接口 | 请求 | 成功响应 |
|---|---|---|
| `GET /api/closet` | `?type=skin\|cape&q=&page=` | 200，`{ items, total }` |
| `POST /api/closet` | `{ tid, name? }` | 201，衣柜里的一件 |
| `PATCH /api/closet/{tid}` | `{ name }` | 200，衣柜里的一件 |
| `DELETE /api/closet/{tid}` | — | 200，`{ refunded }` |
| `PATCH /api/players/{pid}` | `{ name?, skin?, cape? }`，材质传 tid 或 null | 200，角色（ADR-0022 预留的） |
| `PATCH /api/user` | 加上 `avatar?`：tid 或 null | 200，个人资料（ADR-0023） |
| `POST /api/reports` | `{ tid, reason }` | 201，举报 |

- 别人的私有材质与不存在的一样，返回 404 `texture_not_found`（ADR-0025）。
- 被封禁的用户，这些写接口都返回 403 `user_banned`（ADR-0022）。

### 衣柜

- 加入：公开材质和自己的私有材质都可以。名字默认取材质名，规则同材质名（ADR-0025）。扣 `score.perClosetItem`（ADR-0025 加的设置），实付记在这一件的 `score_paid` 上。已经在衣柜里时返回 409 `closet_item_exists`。不要求验证邮箱，同 BS。
- 移出：按实付退还（开着 `score.refundOnDelete` 时），收藏数减一，自己角色上用着它的清掉。头像不动：头像本来就不要求材质在衣柜里。
- 改名：只改这一件的名字。
- 收藏数和衣柜的增删在同一个事务里，用 `likes = likes ± 1` 原子增减（不变量 5）。
- 衣柜的插入用 `insertOrIgnore`，没插进去就是已经在衣柜里。这样 PG 上不会因为唯一冲突让整个事务作废。

### 角色的材质和头像

- `PATCH /api/players/{pid}` 的 `skin`、`cape` 传 tid 是设置，传 null 是清除：
  - 材质必须在自己的衣柜里，同 BS。不在的返回 404 `closet_item_not_found`；
  - 类型要和槽位一致：皮肤槽只接受 Steve、Alex，披风槽只接受披风，否则返回 400 `texture_type_mismatch`；
  - 换材质属于角色管理，开着"必须验证邮箱"时要先验证（ADR-0018）；
  - 更新 `updated_at`，发 `player.texturesChanged`。
- 头像：任何对自己可见的皮肤（公开的、自己上传的），不要求在衣柜里，同 BS。传 null 清除。不要求验证邮箱。发 `user.profileUpdated`（`fields: ['avatar']`）。头像的出图和 PlayerHead 组件见 ADR-0025。

### 并发

这几个操作都属于 ADR-0025"并发"一节里依赖材质可见性的一类：先锁自己的行，再锁材质的行，并确认材质对自己可见。

- 加入衣柜：就用收藏数加一的那条 UPDATE，条件里带上可见性（`is_public = 1 or uploader_id = ?`），改不到行就当作不存在。
- 换材质、设头像、举报：先对材质执行一条不改值的 UPDATE 锁住它，再读出来判断可见性。MySQL 对不改值的 UPDATE 不一定报告改到了行，所以不能拿影响行数来判断。

材质的上传者改成私有或删除时，先锁的也是材质行，所以两边排队执行：要么先换上、再被清掉；要么材质已经不可见，换不上。

### 积分

- 衣柜费按 ADR-0025：加入时扣，实付记在这一件上，移出时开着 `score.refundOnDelete` 才按实付退还。
- **不做被收藏奖励**（BS 的 `score_award_per_like`，默认 0）：
  - 奖励必须能收回，否则反复加入、移出就能刷分；
  - 但移出衣柜的是收藏者，被收回积分的是上传者。移出不能因为别人的余额而失败，`adjustScore` 又不允许扣成负数（ADR-0025 对上传奖励的理由相同）；
  - 需要时另写 ADR，例如按周结算，不再逐次发放和收回。
- **举报的花费和奖励**，新设置项：

| 设置 | 默认 | 对应 BS |
|---|---|---|
| `report.cost` | 0 | `reporter_score_modification` 为负时的绝对值 |
| `report.reward` | 0 | `reporter_reward_score`，加上 `reporter_score_modification` 为正时的值 |

  - 提交时扣 `report.cost`，实付记在 `reports.score_paid`；采纳时按实付退还，并发 `report.reward`；驳回时不退。处理举报在后台做，这次只扣花费、记下实付。
  - BS 的 `reporter_score_modification` 为正时，是提交就发、驳回时收回的奖励，有和被收藏奖励一样的收回问题，所以改成采纳时才发，导入时并进 `report.reward`。
- 积分流水的原因各用一个 i18n 键，关联对象写材质，举报写举报。

### 举报

- 只能举报对自己可见的材质。别人的私有材质返回 404，不能借举报确认它存在。
- 理由去掉首尾空白后 1 到 500 个字符。
- 同一个人对同一个材质只能举报一次，无论之前的举报处理与否，同 BS。由 `(reporter_id, texture_id)` 的唯一索引保证：用 `insertOrIgnore` 插入，没插进去就返回 409 `report_duplicate`，事务回滚，扣的花费也随之撤销。
- 要求先验证邮箱（ADR-0018）。
- 发 `report.created`。通知管理员要等站内信（`notifications`）落地。
- 删除账号时（ADR-0023、ADR-0025），举报记录留下，`reporter_id`、`uploader_id` 由外键置空。还没处理的举报，花费不再退还。

### 事件和插件 API

- 事件都在业务事务里发：`closet.itemAdded`、`closet.itemRemoved`、`player.texturesChanged`、`user.profileUpdated`（`avatar`）、`report.created`。SDK 里都已经有了，插件 API 不变。
- 拦截器 `closet.add`（在事务里）先留好位置，等插件运行时。
- BS 还有换材质、设头像、举报的拦截点（`can_set_texture`、`user_can_update_avatar`、`user_can_report`），这次不加。需要时按插件 API 变更的流程加。

### 组件

新组件写进 `packages/ui`，配 story 和截图基线，并补进 DESIGN.md 的组件清单：
- Tabs：衣柜的皮肤和披风。
- TexturePicker：换材质的 Dialog 里从衣柜挑一件。TextureCard 的展台太高，一页 20 个放进 Dialog 太长。

TextureCard、PlayerHead、Pagination、Textarea 由 ADR-0025 新增。

## 后果

- 新迁移：建 `reports`（带 `score_paid`）。`docs/schema.md` 已经随采纳更新。
- 在四种数据库上做请求级测试：
  - 并发加入、移出衣柜之后，收藏数等于衣柜里的条数；
  - 同一个人并发加入同一件，只扣一次积分；
  - 材质改成私有的同时，别人给角色换上它，最后别人的角色上没有它；
  - 同一个人并发举报同一个材质，只有一次成功，只扣一次花费；
  - 移出衣柜按实付退还，调价之后也不变。
- e2e 补上：另一个用户把材质加入衣柜 → 换到角色上 → CSL 返回它的 hash → 上传者改成私有 → 那个用户的衣柜和角色上都没有了；设头像；举报一个材质，在"我的举报"里看到它。

## 考虑过的其他方案

- **换材质不要求材质在衣柜里，对自己可见就行**：衣柜就只剩收藏的作用，衣柜费也没有了意义。BS 要求在衣柜里。
- **保留被收藏奖励，收回时扣成负数（BS 的做法）或最多扣到 0**：理由同 ADR-0025 的上传奖励。
- **举报的正向奖励照 BS 提交就发**：驳回时要收回，收回会遇到同样的余额问题；而且提交就发奖励，鼓励的是乱举报。
- **衣柜的插入撞上主键冲突时，在事务外转换错误（ADR-0022 改名的做法）**：衣柜只有主键这一个唯一约束，`insertOrIgnore` 在四种数据库上的语义一致，更简单。
