# ADR-0009 插件运行模型：官方插件在核心进程内，安装插件在 plugin host，整代切换

- 状态：已采纳（plugin host 由谁拉起、多实例的换代由 ADR-0033 补充；由启动器拉起 host 一句已被 ADR-0039 取代，host 一直由核心进程拉起）
- 日期：2026-10-16

## 背景

BS 的插件可以运行时安装、启用、停用，不需要重启。PHP-FPM 每个请求都从零开始，所以天然支持这一点。Node 是常驻进程，两份研究报告给出了两种方案：

- **同进程 `import('…?t=' + 时间戳)` 热重载**：不可行。ESM 模块按 URL 永久缓存在 loader 中，没有卸载接口，每重载一次就泄漏一整棵模块图。`AbortController` 只能撤销插件注册的回调，代码本身释放不了。此外，插件和核心在同一进程，可以读到 `.env` 和数据库凭据。
- **每个插件一个容器**：隔离最强，但普通服主的机器部署不了。

Node 官方明确说明：`vm` 模块和 permission model 都不能防御恶意代码。`isolated-vm` 和 `vm2` 在 2026 年都出现过沙箱逃逸。

## 决定

插件分两类：一套 API，两条加载路径。

| | 官方插件 | 安装插件 |
|---|---|---|
| 来源 | monorepo 的 `plugins/*`，随发行包分发 | 插件市场或手动上传 |
| 运行位置 | 核心进程内 | plugin host 进程 |
| 产物形式 | 和核心一起编译 | 预打包的单文件 ESM 加静态资源，放在 `data/plugins/{id}/{version}/` |
| 限制 | 可以申请核心内部能力 | 只能用公开能力；运行时不执行 `npm install`；不允许原生扩展 |

**plugin host** 是 `nextskin` 启动器拉起的一个子进程，承载全部安装插件：

- 以 `node --permission` 启动，只能读插件目录，环境变量为空，读不到 `.env` 和 SQLite 文件，也没有任何数据库凭据；
- 和核心之间用带类型的 RPC 通信：能力调用、hook 调用、HTTP 请求转发。

**热重载按整个 host 进程换代**：

1. 拉起第 N+1 代 host；
2. 加载新的插件组合，执行 setup 并做健康检查；
3. 原子切换注册表，新请求进入新一代；
4. 等待第 N 代处理完在途请求，然后让它退出。

ESM 卸载不了的问题，靠进程退出彻底解决。切换期间会短暂多占一份 host 的内存。

**可选档位**（同一协议，改走 unix socket 或 TCP）：

- 让重型或不稳定的插件独占一个 host；
- 把 host 放进容器，适合大站或高安全要求的运营者。

**运行时防护**：

- 没有插件订阅的 hook 点不会发生跨进程调用；
- 每次跨进程调用都有超时预算（拦截器的预算见 SDK 中的 `interceptorPolicies`）；
- 某个插件连续出错时自动熔断，并通知管理员；
- 每次调用都以插件 id 记录 trace span 和指标。

## 后果

- 默认档位提供的是**稳定性隔离、最小权限 API，再加一层"安全带"**，并不是能抵御恶意代码的沙箱。这一点必须对外如实说明。真正的信任来源是插件市场的签名与审核，以及安装时向管理员展示插件申请的能力。需要防御恶意代码时，使用容器档位。
- 插件 API 必须按"跨进程"来设计：所有调用都是异步的，所有数据都能序列化（ADR-0010）。
- 一个插件崩溃会导致同一 host 内的所有安装插件一起重启。核心不受影响，正在执行的 hook 按各自的失败策略处理。

## 考虑过的其他方案

- **每个插件一个 worker_threads**：可以单独卸载某个插件，但同一进程里无法给不同插件不同的权限，内存泄漏和原生层崩溃也会互相影响。可以作为将来的优化，暂不采用。
- **WASM 插件（Extism、组件模型）**：隔离很强，但插件开发体验差，npm 生态里的大部分库无法使用。
- **只允许外部服务（webhook + OAuth，类似 Shopify app）**：最安全，但破坏了"从市场安装后就能用"的体验，服主很难自己部署一个外部服务。
