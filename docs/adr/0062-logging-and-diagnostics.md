# ADR-0062 日志和诊断：核心用 Pino 写结构化记录，启动器把核心的全部输出存进数据目录、按大小轮换；后台的诊断页看健康摘要和日志、导出脱敏的诊断包

- 状态：提议
- 日期：2026-10-24
- 取代 ADR-0002 的"可观测性"一条：Pino 照旧；诊断页读日志文件，不用内存环形缓冲；OTel 导出不做
- 取代 ADR-0039 的"日志"一节
- 补充 ADR-0027：新增具名权限 `diagnostics.read`
- 补充 ADR-0028："高级"分区新增日志轮换的两个设置项

## 背景

ADR-0002 定了 Pino 结构化日志、可选的 OTel 导出、用内存环形缓冲做的诊断页和脱敏诊断包；ADR-0039 把日志文件和轮转交给面板、systemd、Docker。落地的只有后者：核心、启动器和管理进程用 `console.*` 写一行文字（`[auth] password_event_failed`），不带时间和级别；插件 `ctx.log` 的级别和字段也拼进了这行字符串。诊断页和诊断包都没有做。

"交给托管方"在各种部署方式下的结果不一样：

- systemd：journald 加时间、轮换，没有问题；
- Docker：默认的 json-file 驱动不轮换，`docs/deploy/compose.yaml` 没有设上限；
- Windows：`docs/deploy/windows.md` 让 NSSM 写进 `data/nextskin.log`，没开轮换，文件一直变大；
- 宝塔、1Panel、MCSM：各有各的输出缓冲和日志文件，留多久、有没有时间，文档没法一句话说清楚。

服主报问题时最需要的是一份带时间的日志和运行环境。现在要先教他去面板的哪里找，找到的常常没有时间、已经被截掉，或者重启之后就没了。核心崩溃重启正是最需要日志的时候，而内存环形缓冲恰好在这时丢掉内容，也看不到核心自己之外的输出（Next 打印的错误、崩溃时的堆栈、启动器的行）。

程序已经自己管着几样有上限的持久文件：`update-log.jsonl`（ADR-0061）、SQLite 迁移前的备份（留 3 份，ADR-0040）。

## 决定

### 记录的格式

- 一条记录一行 JSON（NDJSON）。固定的字段：
  - `time`：UTC 的 ISO 时间，精确到毫秒；
  - `level`：`debug`、`info`、`warn`、`error`、`fatal`；
  - `source`：`launcher`、`core`、`plugin-host`、`plugin`；
  - `msg`：消息。照现在的写法用固定的事件码（`password_event_failed`），不拼异常的消息（不变量 11）。
- 其余是结构化字段：`area`（现在行首的 `[auth]`、`[mail]`、`[plugins]` 这类标签）、`plugin`（插件 id）、`raw`（原始输出的行，见下文）等。
- 升级、回滚时，新旧两个版本的启动器先后写同一个文件。格式只加字段，不改已有字段的含义；读文件的一侧照样显示不认识的字段，解析不了的行当作原始文本。

### 核心的记录

- domain 建一个 Pino 根 logger，`base` 为空（不带 pid、hostname），时间和级别按上面的格式输出；各模块取带 `area` 的子 logger。现在的 `options.log: (line: string) => void` 注入点改成接 logger，测试传入收集记录的 logger。不用 Pino 的 transport：它跑在 worker 里，Next 和启动器的单文件包都要另外处理 worker 的路径，而这里用不着。
- 级别由环境变量 `NEXTSKIN_LOG_LEVEL` 决定，默认 `info`，`pnpm dev` 默认 `debug`。
- Pino 的 `redact` 按字段名兜底：`password`、`token`、`secret`、`cookie`、`authorization` 这类名字（顶层和下一层）的值换成 `[redacted]`。这只是兜底，不变量 11 照旧由写日志的地方自己守。
- 插件的 `ctx.log`：`level` 和消息照旧，`source: 'plugin'` 和 `plugin` 由核心填；插件给的 fields 整个放在 `fields` 下，不展开到顶层，插件不能冒充核心的字段。截断照旧：消息截到 1000 个码点，fields 序列化后截到 2000 个字符，截断了的 `fields` 存成字符串。低于 `NEXTSKIN_LOG_LEVEL` 的不记，所以插件的 `debug` 默认只在 `pnpm dev` 里看得到。
- plugin host 的 stderr 照现在按行截断，每行记成 `source: 'plugin-host'`、`warn`。
- Better Auth 的日志接到子 logger，照旧只记消息本身、去掉查询参数。
- 不记访问日志：反向代理有。

### 由启动器拉起时

核心的记录经已有的 IPC 通道（`NEXTSKIN_LAUNCHER_IPC=1`，ADR-0039）发给启动器，消息是 `{ nextskin: 'log', line }`，不写 stdout。核心的 stdout、stderr 从 `inherit` 改成 `pipe`，启动器逐行读，按 plugin host 的规则截断，每行记成 `source: 'core'`、`raw: true`，stdout 来的记 `info`，stderr 来的记 `warn`。Next 自己的输出、打开 logger 之前的报错、崩溃时 Node 打印的堆栈都从这里进来。

- 结构化记录走 IPC，不和原始输出混在 stdout 里：Next 和第三方库打印的行里可能带着请求里的内容，混在一起就只能靠"这一行像不像 JSON"来区分，原始输出也就能伪造成核心的记录。
- IPC 是核心和启动器之间可信的通道，Windows 上也已经在用。plugin host 不用 Node 的 IPC，是因为限不住插件发来的消息大小（ADR-0033），这条理由对核心不成立。
- 核心发不出去、积压在 IPC 里的记录超过 1000 条时，丢掉新的、记下丢了几条，下一次发得出去时先补一条 `warn`（`log_ipc_dropped`）带上这个数。通道断开后改写 stderr。

启动器把三处来的记录（自己的、核心经 IPC 发来的、核心 stdout 和 stderr 的原始行）交给同一个出口，分成终端和文件两路。

**终端**（启动器的 stdout 和 stderr）：

- 默认写成给人看的一行：本机时区的时间、级别、来源和 `area`、消息、字段。`warn` 及以上写 stderr，其余写 stdout。
- `NEXTSKIN_LOG_FORMAT=json` 时原样写 NDJSON，给接了 journald、Docker 再往外送日志的人用。
- 启动器自己的行不再带 `[nextskin]` 前缀，来源一栏写 `launcher`。

**文件**：

- 写在 `<数据目录>/logs/nextskin.log`，NDJSON，POSIX 上权限 0600（同 `setup-code`）。启动时接着写已有的文件。
- 当前文件超过上限就轮换：关掉它，已有的旧文件依次改名后移（`nextskin.1.log` 变成 `nextskin.2.log`……），当前文件改名为 `nextskin.1.log`，再打开新文件；超出份数的旧文件删掉。Windows 上改名失败时照 ADR-0061 的做法重试几次，还不行就接着写当前文件，下一条记录再试。
- 只按大小轮换，不按天：不依赖时钟，占用的空间有固定上限。
- 上限是"高级"分区的两个设置项（ADR-0028），在后台调整：
  - `logging.maxFileSizeMb`：单个文件的上限，1 到 100 MB，默认 10；
  - `logging.maxFiles`：连同当前文件一共留几份，2 到 20，默认 5（默认合计约 50 MB）。至少 2 份：只留 1 份时，每次轮换都会清空全部日志。
- 启动器读不了数据库，设置由核心经 IPC 告诉它（`{ nextskin: 'logConfig', … }`）：核心打开后发一次，之后每分钟读一次这两项，变了才发。启动器在收到之前、核心打不开数据库时用默认值。调小份数后当场删掉多出来的旧文件；调小大小后，当前文件超出的下一条记录就轮换。后台的说明写明"保存后一分钟内生效"。
- `NEXTSKIN_LOG_FILE=off` 关掉文件，只写终端。默认开着，镜像里也开：诊断页读的就是这些文件。systemd、Docker 已经有日志系统、不想多存一份的可以关掉。

**写文件不能拖住核心**：

- 启动器及时读走管道和 IPC，文件异步写。等着写盘的内容超过 4 MB 时丢掉新的记录、记下条数，写盘恢复后补一条 `warn` 说丢了多少。
- 写盘失败（磁盘满、没有权限）同样处理，每 10 分钟最多报一次，启动器不退出。
- 一个数据目录同时只有一个启动器在运行（数据目录的锁，ADR-0039），所以文件只有一个写入方，轮换不需要跨进程协调。

### 不经过启动器时

- `pnpm dev` 和直接运行 `server.js`：核心自己写终端（给人看的格式）和日志文件，只有结构化记录，收不到原始输出；轮换的上限直接读设置。这样开发时诊断页也有日志可看。
- 命令行里在进程内打开核心的命令（`migrate`、`plugin`、`set-role`……）只写终端，不写文件：服务可能正在运行，再写一份会和启动器的轮换冲突。
- 管理进程（ADR-0061）自己的行照旧只写终端，格式换成同样的一行文本，来源写 `manager`；它照旧原样转发启动器的输出。升级的结果已经在 `update-log.jsonl` 里，核心经管理进程的 `status` 读到。

### 诊断页

- 新页面"诊断"（`/admin/diagnostics`），导航排在"更新"后面。
- 新增具名权限 `diagnostics.read`，只给超级管理员：日志里有 IP、邮箱这类个人信息，页面上还有数据目录、数据库版本这些运行环境；这些问题也只有超级管理员能修。
- **健康摘要**（页面顶部）。只读核心已经掌握的状态，不重做 `doctor` 的探测（不另起 plugin host、不请求本机端口）：
  - 版本：NextSkin、插件 API、Node、操作系统和架构；运行方式（管理进程、只有启动器、开发环境）；核心这次启动了多久；
  - 数据库：方言、服务端版本、迁移状态（核心和已启用的插件有没有还没执行的迁移）；
  - 数据目录的剩余空间；日志文件占的空间，最近丢弃了多少条；
  - plugin host 的状态，和插件页的提示一致；
  - 后台任务：排队的个数、最早的一个等了多久、核心死信的个数（链接到失败任务页，ADR-0051）；
  - 最近一次升级的结果（经管理进程的 `status`，没有管理进程时不显示）。
- **日志**：
  - 从新到旧，每次 200 条，"更早的"往前翻，游标是文件加偏移。
  - 筛选：最低级别、来源、关键字（不区分大小写）。一次请求最多扫描 8 MB，没扫完就返回游标，页面上显示"继续往前找"。
  - 停在第一页时每 5 秒取一次新的。
  - 页面上显示文件里的原样内容，不脱敏：超级管理员本来就能读这些文件，脱敏只会妨碍排查。
  - 没有日志文件时（关掉了文件日志、旧版本的启动器），说明日志在哪里。
- **导出诊断包**：`POST` 请求，下载 `nextskin-diagnostics-<UTC 时间>.zip`，用 fflate 打包。包里有：
  - `README.txt`：包里有什么、按什么规则脱敏，提醒"发出去之前自己看一遍"；
  - `summary.json`：健康摘要；
  - `settings.json`：全部设置，机密项只记有没有设置（同 ADR-0028）；
  - `env.json`：设了哪些 `NEXTSKIN_*` 环境变量，只记名字；数据库只记方言；
  - `plugins.json`：已安装插件的 id、版本、启用状态、当前状态、最近的错误码；
  - `jobs.json`：按任务名统计的排队数和死信数，每个任务名最近一条死信的错误（核心任务的错误本来就只有固定的错误码，ADR-0051）；
  - `logs/`：最近的日志，未压缩时最多 10 MB，按下一节的规则脱敏。
- 导出写一条审计：动作 `diagnostics.export`，对象类型 `diagnostics`，对象 id 记 0。查看页面不写审计。

### 诊断包的脱敏

诊断包是给别人看的，可能被贴进公开的 issue。日志里本来就不该有机密（不变量 11），这里主要处理个人信息，顺带兜底：

- 邮箱换成 `<邮箱1>`、`<邮箱2>`……；同一个包里相同的地址编号相同，前后的记录还能对上。
- 公网 IP（v4 和 v6）换成 `<IP1>`……，编号规则同上。内网、回环、链路本地地址保留：排查受信任的反向代理要看它们，它们也指不到具体的人。
- `Bearer` 后面的值、JWT 形状的串、URL 里的 `用户:密码@`、查询参数里 `token`、`code`、`secret` 一类的值，换成 `[redacted]`。
- 本机路径里的实例目录换成 `<实例目录>`，用户主目录换成 `~`。
- 不处理角色名、UUID、材质 hash、uid：角色名和 UUID 在游戏里本来就公开，hash 是公开地址的一部分；去掉它们就查不了问题。
- `settings.json` 里的值也过一遍这些规则，例如 SMTP 的用户名常常是邮箱。
- 脱敏是尽力而为。导出前页面提示服主自己先看一遍。

### 落地

分三个 PR，每个都能单独合并：

1. Pino 接入和调用点的改造。第一步先验证 Pino 打进启动器的单文件包（rolldown）和 Next standalone 之后都能运行；Next 16 默认的 `serverExternalPackages` 已经列了 `pino`。
2. 启动器的出口：管道、IPC、终端格式、文件和轮换、轮换的两个设置项、丢弃计数；部署文档随它一起改。
3. 诊断页、导出和脱敏；e2e 从发行目录启动，检查页面上的日志和导出的包。

## 后果

- 每种部署方式下的日志都在 `data/logs/`，带时间和级别，默认最多约 50 MB，站长可以在后台调整。部署文档和 FAQ 能一句话说清楚日志在哪；`windows.md` 里 NSSM 的 `AppStdout`、`AppStderr` 两行删掉。
- systemd 和 Docker 默认存两份（journald 或 Docker 自己的日志，加上数据目录里的文件），各有上限。嫌重复可以设 `NEXTSKIN_LOG_FILE=off`，代价是诊断页看不到日志。`compose.yaml` 照样给 Docker 的日志设上限。
- 终端里的样子变了：每行多了时间和级别，启动器的行不再有 `[nextskin]` 前缀。按这个前缀过滤日志的脚本要改，仓库里断言它的测试一起改。
- 核心的 stdout、stderr 改由启动器转发，启动器卡住会拖住核心的输出，所以才有上面的上限和丢弃。这段代码的测试要覆盖：管道写满、写盘失败、核心崩溃重启时文件接着写、轮换时改名失败。
- 插件的 `debug` 日志默认不再输出。插件文档里 `ctx.log` 一节改成说明级别和 `fields` 放在哪里。SDK 的类型不变，不需要 changeset。
- 诊断页的健康摘要和 `doctor` 有一部分重叠：`doctor` 是停机或部署时的自检，摘要是运行中的状态。能共用的读取函数放进 domain，探测类的检查只留在 `doctor`。
- 多实例部署（Redis、S3 驱动）时，每个实例的日志在各自的数据目录里，诊断页只看得到处理这次请求的那个实例。
- 命令行命令的日志不进文件。服务运行时执行 `plugin` 命令，运行中的服务按插件表同步时写的记录照样进文件（ADR-0049）。

## 考虑过的其他方案

- **照旧全交给托管方**（ADR-0039 原来的做法）：问题见背景；而且诊断页和诊断包都要求程序自己读得到日志。
- **ADR-0002 的内存环形缓冲**：只有核心自己的记录，看不到 Next 的输出、启动器的行和崩溃时的堆栈；核心一重启就没了。
- **核心自己写文件**（Pino 的文件 transport、pino-roll）：同样收不到核心自己之外的输出，核心崩溃重启的那段时间也没有人写；transport 跑在 worker 里，打包要另外处理。
- **结构化记录也走 stdout**：只能靠"这一行像不像 JSON"来区分，带着请求内容的原始输出能伪造成核心的记录。
- **核心经额外的文件描述符（fd 4）送记录**：同样能和原始输出分开，但 Windows 上额外的管道要另外验证，而 IPC 通道已经在用了。
- **轮换的上限用环境变量设置**：ADR-0002 定了只有数据库连接和密钥放在 `.env`，其余配置存在数据库里、在后台改。留在环境变量里的 `NEXTSKIN_LOG_LEVEL`、`NEXTSKIN_LOG_FORMAT`、`NEXTSKIN_LOG_FILE` 是例外：级别要在打开数据库之前就生效（排查连不上数据库时正要用 `debug`），格式和开关由部署方式决定，和 `NEXTSKIN_MANAGER` 一样由部署的人设。
- **按天轮换**：总量取决于访问量，没有固定上限。按天找文件方便一些，但不如固定上限重要，而且每条记录都带时间。
- **自己写 logger，不用 Pino**：要用的级别、子 logger、按字段名 redact、快速序列化，Pino 都有，而且是纯 JS、没有原生依赖（ADR-0008）。
- **OTel 导出**：只导出日志也要引入一串 `@opentelemetry/*` 包，导出器同样跑在 worker 里；自托管的服主几乎不接外部监控（ADR-0002 也是这么判断的）。真有人需要时，在启动器的出口上加一个导出目标。
- **诊断包上传到某个服务、生成链接**：要有地方收包、存包，存的是别人站点的信息；导出成文件、由服主自己决定发给谁更合适。
- **诊断页对管理员开放**：理由同 ADR-0051。
- **页面上的日志也脱敏**：超级管理员本来就能直接读文件，页面上脱敏只会妨碍排查。
