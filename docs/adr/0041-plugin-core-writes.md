# ADR-0041 插件写核心数据：一项能力对应一个领域用例，插件以 `actor: plugin` 调用，每次写入都要能安全重放；第一项是改积分（`users.score`），带永久的幂等键；注册字段能从地址栏预填

- 状态：已采纳
- 日期：2026-10-20
- 补充 ADR-0033："推迟"表里"写核心数据的能力"一行的通用做法和第一项能力；改积分只记流水、不写审计
- 补充 ADR-0021：积分流水记下来源插件和幂等键
- 补充 ADR-0035：候选期在仓库外迁移的插件定为 share-registration-link

## 背景

ADR-0033 推迟了写核心数据的能力。写操作只能经过领域用例（不变量 4），先要设计"插件以 `actor: plugin` 调用指定用例"，每个用例一项能力。ADR-0035 给它留了 `Actor` 的 `plugin` 成员：`Actor` 是封闭的对象联合，以后再加就是大版本。

### 现状

- SDK 的 `1.0.0-rc.0` 已经发到 npm（2026-10-19，维护者在本地发）。仓库已经公开。七项能力都只读核心数据，或者读写插件自己的数据。
- BS 插件市场（`bs-community/plugins-dist` 的 registry）里，去掉做进核心的、已经迁成官方插件的、不迁移的，以及只对 BS 自己有意义的（insider、fix-v4-update、hide-advanced-menu），剩下六个都卡在推迟项上：

  | 插件 | 卡在 |
  |---|---|
  | mojang-verification | 以指定 UUID 建角色、保护正版名的拦截点、奖励积分 |
  | share-registration-link | 改积分；注册页要能带上分享码 |
  | texture-type-cast | 改材质类型 |
  | embedded-comment | 运行时组件和插槽 |
  | forum-integration、fast-login | 外部数据库 |

  ADR-0035 要求候选期在仓库外迁一个仓库里没有的 BS 社区插件。用现在的公开面，找不到能迁的。
- share-registration-link 2.0.2 的做法：
  - 用户在用户中心生成分享码（20 位随机串，可以删除）；
  - 注册页上的脚本把地址栏里的 `share` 带进注册请求；
  - `auth.registration.completed` 时按分享码找到分享人，给分享人加 `reg_link_sharer_score`（默认 50），给新用户加 `reg_link_sharee_score`（默认 0）。加分是读出来、加上、再存回去，不记流水。一个分享码能用多少次没有限制。
- 核心这边：
  - `adjustScore(tx, { uid, delta, reason, subject })` 是修改 `users.score` 的唯一途径（ADR-0021）：带条件的 UPDATE，扣减时要求余额够，再写一条流水。`reason` 存文案键，最多 128 个字符。从 BS 导入的用户可能是负积分（ADR-0036）。
  - 积分变动不发事件（ADR-0022 的签到，ADR-0036 的改积分）。
  - 审计日志已经有 `actor_type = 'plugin'` 和 `actor_plugin_id` 两列（ADR-0027）。
  - 用户中心的积分记录翻译不了原因时原样显示，代码里留了一句注释：插件写的原因以后在插件自己的命名空间里。
  - 插件调用核心是一次 RPC（`plugins/system.ts` 的 `handleRequest`），按授予的能力放行。事务内的拦截器、迁移和设置校验里，只能访问插件自己的表。
  - 事件至少投递一次，任务失败会重试。插件发出的 RPC 可能在核心已经提交之后，才因为超时、`ctx.signal` 或换代被插件当成失败。任务的 `dedupeKey` 只在任务完成之前去重（`jobs` 只放还没完成的任务），挡不住这类重放。
  - 插件路由能返回 `Location`，网关会去掉 `Set-Cookie`（`packages/api/src/plugins.ts`）。

### 要定的

- 写能力的通用做法：能力怎么划分、actor、记录写在哪里、重放、结果怎么表达、能在哪里调用。
- 第一项能力，以及它的参考插件还缺的东西。
- 以后的写能力怎么加。

## 决定

### 通用做法

以后每一项写核心数据的能力都照这一节做，并在各自的 ADR 里写明下面几项。

- **一项能力对应一个领域用例（或者一组同类的用例），不开通用的写接口。**
  - 能力名沿用 `<领域>.<动作>` 的写法。方法挂在 `ctx` 上同名的命名空间下：`users.score` 对应 `ctx.users.adjustScore`，和 `users.read` 的方法合在同一个 `ctx.users` 上。
  - 类型上照旧用 `Gate` 收窄：没申请这项能力，就没有这个方法。
- **插件以 `{ kind: 'plugin', pluginId }` 调用用例。**
  - 用例照常检查它自己的业务规则（余额、上限、名字规则……），插件绕不过。"谁有权做"由能力代替，不看请求里的用户。
  - 插件在路由里替当前用户操作时（例如用积分兑换东西），用户同不同意由插件自己判断，核心无从知道。这一点写进安装界面和安全须知。
  - 用例本来会发的事件，actor 是插件；本来会写的审计，操作者也记成插件。插件订阅了自己会引起的事件时，用 `event.actor` 认出自己，避免循环。
- **每次写入都要能安全重放。** 每项能力要么有天然的唯一性（例如以后以指定 UUID 建角色，UUID 本身就唯一），要么要求插件给一个幂等键。幂等键的规则：
  - 在本插件内唯一，1–255 个字符，没有首尾空白（同 KV 的键）。
  - 永久保存：和写入记在同一行、同一个事务里，并发的同一个键由唯一索引兜住。任务完成后不失效；卸载插件后也保留，重装同一个 id 的插件，不会把以前做过的再做一遍。
  - 同一个键再调用一次：参数和第一次一样，就返回"已经做过"，什么都不改；参数不一样，调用被拒绝，因为这是插件的 bug。
  - 幂等键顺带能表达业务上的"只做一次"，例如 `sharee:<新用户的 uid>`、`daily:<uid>:<日期>`。
- **结果**：业务上的结果（余额不够、对象不存在、重复）放在返回值的 `status` 里。`status` 是开放的字符串联合（ADR-0035），以后加成员是次版本。参数不对、超出上限、没有能力，照旧抛错。
- **能在哪里调用**：和读核心数据一样，事务内的拦截器、迁移、设置校验里不能调用（ADR-0033）。核心在自己的事务里执行用例，事务里不等网络（ADR-0008）。
- **和插件表配对的写入**：插件没有事务，插件表的写入和核心数据的写入没法一起原子提交。需要配对时，用幂等键分步做：
  1. 先在自己的表里记一行"待处理"；
  2. 用这一行的 id 作幂等键写核心数据；
  3. 再把这一行标记成完成。

  中途失败就用同一个键重跑。作者文档的插件表一篇写这个模式。
- **安装界面**：写核心数据的能力都按高风险展示（`highRiskCapabilities`），写明它能对哪些用户做什么。升级时新增的能力照旧要求重新确认（ADR-0033）。

### 第一项：改积分（`users.score`）

#### SDK

```ts
// capabilities 新增 'users.score'

export interface UsersScoreApi {
  adjustScore(
    uid: Uid,
    delta: number,
    options: { readonly reason: MessageKey; readonly key: string },
  ): Promise<ScoreAdjustResult>
}

export interface ScoreAdjustResult {
  readonly status: 'applied' | 'duplicate' | 'insufficient' | 'userNotFound' | (string & {})
  /** 调用结束时的余额；用户不存在时为 null */
  readonly balance: number | null
}
```

- 只申请了 `users.score` 时，`ctx.users` 上只有 `adjustScore`。
- `delta` 是非零的安全整数，绝对值不超过 2147483647（同后台改积分）。加完会超过上限时，调用被拒绝。
- `status` 的四种取值：
  - `applied`：这次记上了。
  - `duplicate`：同一个键以前记过，参数相同，这次什么都没改。
  - `insufficient`：扣减之后会低于 0，什么都没改。余额本来就是负数的导入用户，扣任何分都是这个结果。
  - `userNotFound`：用户不存在。
- `reason` 必须是插件文案里有的键（任何一种语言里有都行），否则调用被拒绝。不带参数，和核心自己的原因一样只是一个类别。
- 不检查封禁：后台能给被封禁的用户改积分，插件也能。
- 返回值里有余额，所以只申请了 `users.score` 的插件也能看到用户的积分。安装界面照实写。

#### 核心

- **用例**：领域层新增"以插件身份改积分"的用例，内部调用 `adjustScore`。
  1. 在事务里先按 `(plugin_id, plugin_key)` 查流水。查到了，就按上面的规则返回 `duplicate` 或者拒绝。
  2. 没查到，就调用 `adjustScore`，流水带上插件 id 和键。
  3. 并发的同一个键撞上唯一索引时，整个事务回滚；再查一次，照第 1 步处理。
- **流水**：`score_transactions` 加两列：
  - `plugin_id`，varchar(64)，可空：写这一笔的插件，核心自己写的为空。不建外键：卸载之后流水照样要说明来源，同审计的 `actor_plugin_id`。
  - `plugin_key`，varchar(255)，可空：幂等键。
  - 两列要么都为空，要么都不为空（CHECK）。`(plugin_id, plugin_key)` 唯一，四种数据库都允许多个 NULL。
  - `reason` 存插件的文案键。显示时用插件自己的文案，按看记录的人的语言翻译；插件卸载后翻译不了，就显示"来自插件 {id}"。
  - 每个用户的流水，`delta` 之和照旧等于余额（ADR-0021）。
- **不写审计，不发事件**：
  - 积分变动本来就不发事件（ADR-0022、0036）。
  - 审计记的是管理操作。插件给每一次签到、每一个邀请都加分，每笔记一条，会淹没后台的审计页。流水里已经有插件 id、键、时间和变动后的余额，是完整的记录。
- **后台**：
  - 插件详情页显示这个插件累计加了多少分、扣了多少分，以及最近几笔（按 `plugin_id` 查流水）；
  - 用户详情页的积分记录标出每笔来自哪个插件。
- 所以 1.0 里 `Actor` 的 `plugin` 成员仍然不会出现在插件看得到的地方（事件、`RequestScope`）。第一项会发事件的写能力落地时，它才会出现。

### 注册字段从地址栏预填

share-registration-link 要把分享码带进注册。第一版里，插件加在注册表单上的字段只能由用户自己填。

- `formFields` 的条目可以声明 `fromQuery: true`。注册页 `/sign-up` 打开时，用查询参数 `<插件 id>.<字段名>` 的值作为这个字段的初始值。用户看得到也改得了，提交后照常校验。
- 只有 text、textarea、number、select 四种字段能声明，类型上就收窄：
  - password 不行：地址会进日志和 Referer；
  - boolean 不行：不能替用户预先勾上同意。
- 参数名带上插件 id。核心自己在注册页上的参数（`next` 这些）不用带点的名字，所以不会和插件的撞，不同插件之间也不会撞。链接由插件自己拼；要短链接，就由插件路由 302 到注册页。
- 从注册页转去第三方登录时，"完成注册"页上没有这个初始值：参数不经过 OAuth 的往返。作者文档写明这一点。

### 参考插件：share-registration-link

- **迁移后的样子**：
  - 用户中心一页表格：工具栏的动作生成分享码，行动作删除；带参数的注册链接用 `code` 格式的列显示。
  - 设置三项：分享人得几分、新用户得几分，外加一项旧插件没有的"每个分享人最多得几次奖励"（0 表示不限），挡住自己邀请自己刷分。
  - 注册字段 `code`，声明 `fromQuery`。不需要拦截器：分享码无效时照样注册，只是没有奖励，和旧插件一样。
  - `user.registered` 时按分享码找到分享人：
    - 给分享人加分，键是 `sharer:<新用户的 uid>`；
    - 给新用户加分，键是 `sharee:<新用户的 uid>`；
    - 分数为 0 的那一方不调用。
  - `user.deleted` 时删掉这个用户的分享码。
  - 能力：`storage.tables`、`users.score`。
- **落地顺序**：
  1. 核心和 SDK：能力、用例、流水的迁移、RPC、积分记录的显示、插件详情页的累计，以及 `fromQuery`。附 changeset（次版本），在预发布模式里发 `1.0.0-rc.1`。
  2. 在仓库外照迁移指南迁 share-registration-link，只用 npm 上的 rc.1，记下文档和构建命令的问题（ADR-0035 的候选期要求）。修掉之后发下一个候选版。
  3. 把它收进 `plugins/share-registration-link` 作为官方插件，照 ADR-0033 在两条加载路径上各跑一遍端到端测试。

### 以后的写能力

这一份不定，各自另写 ADR，照上面的通用做法：

| 能力 | 需要它的插件 | 要先解决的 |
|---|---|---|
| 以指定 UUID 建角色 | mojang-verification | 只建不改（不变量 2）；名字或 UUID 已被占用时的结果；`player.create`、`player.rename` 拦截点保护正版名；发 `player.created`，actor 是插件 |
| 发通知（`notifications.send`） | 草案里就有 | 核心的通知还没做 |
| 改材质类型 | texture-type-cast | 它更像一次性的管理操作，倾向做成后台的批量操作，不开写能力 |

### SDK 和文档的改动

- **SDK**：
  - `capabilities` 加 `users.score`，开头那句"插件不写核心数据"的注释跟着改；
  - `context` 加 `UsersScoreApi`、`ScoreAdjustResult`，`PluginContext` 多一个 `Gate`；`TransactionalPluginContext` 不变；
  - `formFields` 的条目加 `fromQuery`。
- **type-tests**：
  - 没申请 `users.score` 就没有 `adjustScore`；
  - 事务内的拦截器里没有 `adjustScore`；
  - password、boolean 字段不能声明 `fromQuery`。
- **作者文档**：
  - 上下文一篇：`adjustScore`、幂等键和结果；
  - 插件表一篇：分步配对的模式；
  - UI 一篇：`fromQuery`；
  - 安全须知：申请了 `users.score` 的插件能给任何用户加减积分；
  - 从 BS 迁移：对照表里"写核心数据"一行改成"改积分已经可以，其余的还不行"；share-registration-link 从"第一版推迟"挪到"已迁为参考插件"。

### 测试

- **`*.db.test.ts`，四种数据库**：
  - `applied`、`duplicate`、`insufficient`、`userNotFound` 四种结果；
  - 同一个键、参数不同时被拒绝；
  - 并发的同一个键只记一笔；
  - 流水之和等于余额；
  - CHECK 约束和唯一索引。
- **RPC**：
  - 没有授予能力时被拒绝；
  - 事务内的拦截器、迁移、设置校验里被拒绝；
  - 参数校验，包括 `reason` 不在插件文案里的情况；
  - 同一个事件投递两次，只加一次分。
- **显示**：用户中心和后台的积分记录翻译插件的原因；插件卸载之后显示兜底的文案。
- **端到端**：share-registration-link 在两条加载路径上各跑一遍：生成分享码 → 打开带参数的注册页，字段已经填好 → 注册 → 分享人和新用户的积分记录里出现插件的原因。

## 后果

- 候选期有了能在仓库外迁移的 BS 插件；写核心数据的通用做法在冻结之前，由一个真实的插件验证过一次。
- 1.0 的公开面多一项能力和一个可选属性。以后每加一项写能力，都是次版本。
- `Actor.plugin` 在 1.0 里仍然没有被核心产生过，它的形状（只有 `pluginId`）要等会发事件的写能力来检验。到时候需要更多信息，只能加可选的字段（次版本）。
- 插件出 bug 多发的积分，核心不会自动撤回：管理员先停用插件，按流水里的插件 id 找出受影响的用户，再在后台逐个扣回。
- 流水表多两列和一个唯一索引。以后要是清理旧流水，幂等键会跟着消失，写清理流水的 ADR 时要处理这一点。
- 采纳时：
  - `docs/schema.md` 的 `score_transactions` 补上两列、约束和"插件的原因"；
  - ADR-0033、0021、0035 的状态注明由本 ADR 补充；
  - `PROGRESS.md` 的"插件 API 推迟的部分"指向本 ADR。

## 考虑过的其他方案

- **1.0 只发现在的公开面，写能力以后再加**：以后再加都是次版本，冻结本身不受影响。但候选期找不到能在仓库外迁移的 BS 插件，写能力的通用做法也要到冻结之后才第一次用上。
- **从 mojang-verification 开始**：它是 ADR-0010 选的参考插件，但要同时做以指定 UUID 建角色、两个新拦截点和微软登录的流程，候选期会拖得很长。积分是最小的一项。
- **幂等键可选**：作者容易漏写，事件一重投就多发积分。必填之后，"只做一次"也顺带表达了。
- **用任务的 `dedupeKey` 去重**：它只在任务完成之前有效。
- **另建一张记幂等键的表**：多一张表、每次多写一行。键和流水记在同一行，原子性和"流水之和等于余额"都不用另外保证。以后别的写能力，键也记在各自写入的那一行上。
- **每次改积分写一条审计**：见上，后台的审计页会被淹没，而流水已经是完整的记录。
- **改积分发事件（`user.scoreChanged`）**：ADR-0022、0036 定了积分变动不发事件，也没有插件需要。以后要加是次版本。
- **原因写成自由文本**：积分记录按看的人的语言显示，核心自己的原因也都是文案键。
- **限制每个插件的发放总量，或者单次的上限**：管理员不知道该填多少。插件详情页的累计数，已经能让管理员看出异常。
- **预填的参数由插件自己取名（`?share=`）**：可能和核心以后的参数、或者别的插件撞上。
- **放开插件写 Cookie，用 Cookie 记住分享码**：网关去掉插件响应里的 `Set-Cookie`，不为一个插件放开。
