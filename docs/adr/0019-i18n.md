# ADR-0019 国际化：URL 不带语言前缀，消息集中在一个包里，接口错误带本地化文案

- 状态：已采纳（站内通知由 ADR-0052 落地）
- 日期：2026-10-18

## 背景

ADR-0012 定了用 next-intl（ICU 消息格式），后台可以在数据库里覆盖翻译。现有的相关约定：
- 插件自带 `locales/<lang>.json`，界面里写的是插件命名空间下的消息键（SDK 的 `MessageKey`）；
- `users.locale` 记录用户的语言；积分流水的原因、站内通知存消息键加参数，按收件人的语言渲染（`docs/schema.md`）；
- 插件拦截器拒绝时返回机器可读的 `code` 和已本地化的 `message`（SDK 的 `Deny`）；
- DESIGN.md：中文优先。

注册切片（ADR-0018）马上要用到：注册接口的错误、验证邮件和重设密码邮件、登录注册页面。这些都要先回答几个 ADR-0012 没有回答的问题：URL 带不带语言、按什么决定语言、接口错误怎么表达、邮件用谁的语言、先支持哪些语言。

## 决定

### 语言怎么决定

- **URL 不带语言前缀**（next-intl 的"不用 i18n 路由"方式），同一个页面只有一个地址。
- 按顺序取第一个有的：
  1. 登录用户的 `users.locale`；
  2. Cookie `nextskin-locale`（未登录时语言切换器写这里）；
  3. `Accept-Language` 里最匹配的受支持语言；
  4. 站点默认语言，新设置项 `site.locale`，默认 `zh-CN`。
- 登录用户切换语言时，经领域用例写 `users.locale`。注册时把当时解析出的语言写进 `users.locale`。
- 页面的 HTML 随 Cookie 和 `Accept-Language` 变化，不能被公共缓存；材质、头像这类图片和协议端点与语言无关，不受影响。
- 日期和时间按站点时区显示，新设置项 `site.timeZone`，默认 `Asia/Shanghai`（与 BS 的默认相同）。服务端渲染和浏览器用同一个时区，避免水合不一致。以后可以加用户自己的时区。

### 消息放在哪里

- 新建 `packages/i18n`：
  - `messages/<语言>.json`：核心的全部文案，ICU 格式，按功能分组的嵌套键；
  - 受支持的语言列表、语言解析函数（纯函数，输入是上面四个来源）、回退规则；
  - 用 `use-intl/core` 的 `createTranslator` 建翻译函数的辅助函数，不依赖 React 和 Next。
- `apps/web` 用 next-intl 接入同一份消息；领域层（邮件、站内通知、接口错误）用 `packages/i18n` 的翻译函数。
- `packages/ui` 的组件里不写文案，需要文字的地方由调用方传入，例如 Toast 的 `closeLabel`。这条已经是现在的做法。
- 插件的消息挂在 `plugins.<插件 id>` 命名空间下，和核心的消息合并。
- 后台覆盖翻译（ADR-0012）以后做：运行时把数据库里的覆盖叠在打包的消息上。

### 先支持哪些语言

- `zh-CN`：源语言，文案先写中文（DESIGN.md §1）。
- `en`：和中文同步维护，每次加文案都要同时写英文。
- 其他语言以后由社区翻译。缺键时回退：中文变体（`zh-TW` 等）回退到 `zh-CN`，其他语言回退到 `en`。

### 检查

- 消息的类型以 `zh-CN.json` 为准（next-intl 的 `AppConfig`）：键名拼错、ICU 参数缺失都是编译错误。
- 测试检查每种完整维护的语言（现在是 `zh-CN` 和 `en`）和源语言的键完全相同、ICU 语法正确、同一条消息的参数相同。
- lint 不拦 JSX 里的中文字面量，靠评审：管理员可见的调试信息、测试和 story 里的文字不需要翻译，规则写起来误报太多。

### 接口错误

- 领域用例的错误是机器可读的 `code` 加参数，例如 `{ code: 'player_name_taken' }`、`{ code: 'password_too_short', params: { min: 8 } }`，不带文案。
- HTTP 层把它转成响应：`{ error: { code, message, fields? } }`。
  - `message` 用请求的语言翻译；
  - 表单类的错误放在 `fields` 里，键是字段名，值同样是 `{ code, message }`，网页直接交给 Form 的 `errors`；
  - 插件拦截器返回的 `message` 原样转发，它已经是插件按请求语言写好的。
- 第三方客户端可以按 `code` 自己处理，也可以直接显示 `message`。
- 协议端点（CSL、USM、Legacy、Yggdrasil）不变，错误文案以契约为准（ADR-0016）。

### 邮件和站内通知

- 按收件人的 `users.locale` 渲染，没有时用站点默认语言，不用触发者的语言。例如管理员给用户重设密码，邮件按用户的语言发。

## 后果

- 新功能的固定顺序里，写 UI 之前要先把文案加进 `zh-CN.json` 和 `en.json`。
- 站点名、公告这类管理员填写的内容只有一种语言。以后需要按语言填写时，另做设置项。
- 搜索引擎只会收录一种语言的页面。皮肤站大多是单一语言的社区，这不是目标。
- BS 后台改过的翻译（`language_lines`）不导入：新界面的文案重新写过，键名对不上（`docs/schema.md`）。

## 考虑过的其他方案

- **URL 带语言前缀（`/en/skinlib`）**：搜索引擎能分别收录各语言的页面，但同一个材质页有多个地址；BS 的旧链接、协议端点都在根路径上，前缀会让重写和跳转规则复杂得多。
- **接口只返回 `code`，由网页自己翻译**：网页和第三方客户端都要维护一份 code 到文案的映射，插件拦截器返回的文案也没法统一处理。
- **每个包各自维护文案**：领域层的邮件和网页的页面会有重复、互相不一致的文案，翻译者要在多个地方找。
