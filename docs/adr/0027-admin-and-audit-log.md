# ADR-0027 后台和审计日志：固定角色映射到具名权限，不做 RBAC；审计日志和业务写入在同一事务；举报的状态用带条件的 UPDATE 推进

- 状态：已采纳（具名权限和第一个超级管理员两处由 ADR-0031 补充；其余管理操作、新的具名权限和审计动作、删除用户连带的审计、详情页对管理员显示别人的私有材质由 ADR-0036 补充；权限 `oauthClients.manage` 和 OAuth 应用的审计动作由 ADR-0037 补充；权限 `notifications.send` 由 ADR-0052 补充）
- 日期：2026-10-18

## 背景

ADR-0025、ADR-0026 把管理员处理举报、管理别人的材质和衣柜留到了"第一个管理操作"，`docs/schema.md` 的落地顺序在这一步建 `audit_logs`。

现状：
- `users.role` 是 `banned`、`user`、`admin`、`superadmin` 之一，与 SDK 的 `UserRole` 相同；DTO 的 `role` 和事件 `user.roleChanged` 都用它。
- SDK 已经有插件权限：插件声明权限名，路由和 `area: 'admin'` 的页面可以要求某个权限，"管理员默认拥有全部插件权限"。
- 领域层对管理员的判断只有两处：创建 OAuth 客户端（`auth.ts` 的 `isAdmin`）、管理员不能删除自己（ADR-0023）。

BS 6.0.2 的做法：
- 权限是一个整数：-1 封禁、0 普通、1 管理员、2 超级管理员。后台的路由要求管理员，上传插件和更新程序要求超级管理员。
- **用户管理**（`UsersManagementController`）：只能操作权限比自己低的用户（操作自己除外）；权限只能改成封禁、普通、管理员，任命管理员要超级管理员，不能改自己的权限。
- **处理举报**（`ReportController::review`）：删除材质、封禁上传者、驳回，三选一。
  - 采纳时，`reporter_score_modification` 为负就退还花费，另发 `reporter_reward_score`；
  - 驳回时，`reporter_score_modification` 为正就收回提交时发的奖励；
  - 封禁上传者要求对方的权限低于自己。
- **材质被删除时**（`UpdateScoreForDeletedTexture`），开着 `return_score` 就退上传者的存储费，不管是谁删的。
- 没有审计日志。

BS 这里的问题：
- **处理举报不看状态**：处理过的举报还能再处理一次。退还和奖励前判断的是先读出来的状态，两个管理员同时处理同一条，花费退两次，奖励也发两次。
- **删除材质直接删文件**（ADR-0026 已经列过）。
- **材质删掉之后，同一材质上的其他举报还挂着**，只能逐条处理；这时再选"删除材质"只退花费、不发奖励，后来的举报人吃亏。
- **管理员删掉违规材质，上传者照样拿回存储费。**

## 决定

### 范围

这次做：
- 权限：固定的角色映射到核心的具名权限，用例统一用 `can()` 检查；
- `audit_logs` 和它的写入方式；
- 后台外壳和概览；
- 处理举报；
- 管理员删除别人的材质；
- 用户列表，封禁、解封，任免管理员；
- 审计日志页；
- 设定第一个超级管理员的脚本。

不做，留给后面的切片：
- 用户管理的其他操作：改邮箱（要给 `email_version` 加一，ADR-0024）、改昵称、改密码、改积分、标记邮箱已验证、关掉两步验证（ADR-0023）、删除用户；
- 后台的角色管理：改名、换材质、删除、转让（转让时 `score_paid` 清零，ADR-0022）；
- 管理别人的衣柜；改别人材质的名字、公开状态、模型；管理员在皮肤库里看别人的私有材质；
- 设置页和公告、失败任务（ADR-0021）、后台覆盖翻译（ADR-0019）；
- 把权限单独授给普通用户，见"权限"；
- 用户自己的敏感操作（改邮箱、关两步验证、删除通行密钥）要不要记进审计日志，以后另定。

### 权限

**不做 RBAC**（自定义角色、权限矩阵、一个用户挂多个角色）：
- 站点多是服主自己部署，管理员一两个人。真要分工，也就是"审核员"这样一两种，用不上可以配置的矩阵；
- RBAC 回答"能不能做这件事"，回答不了"能对谁做"：管理员能不能封禁另一个管理员，能不能把自己升成超级管理员。最容易出事故的是后者，无论如何都要另写规则；
- `UserRole` 是插件 API 的一部分，自定义角色要改 DTO 和 `user.roleChanged`。

**具名权限**：
- `users.role` 不变。
- 管理用例检查具名权限，不直接比较角色。每个角色有哪些权限写在代码里（`packages/domain/src/access/`），不建表：

| 权限 | 能做什么 | admin | superadmin |
|---|---|---|---|
| `reports.review` | 查看和处理举报 | ✓ | ✓ |
| `textures.manage` | 删除别人的材质 | ✓ | ✓ |
| `users.ban` | 查看用户列表，封禁、解封 | ✓ | ✓ |
| `users.appointAdmin` | 任免管理员 | | ✓ |
| `audit.read` | 查看审计日志 | ✓ | ✓ |

- 插件权限沿用 SDK 的约定：管理员和超级管理员拥有全部插件权限。
- 以后要把权限授给普通用户时（例如审核员，或者单独授予插件权限），加一张授权表（用户 → 权限名），核心权限和插件权限共用这张表，只改 `can()`。不加角色表。

**能对谁做**：
- 角色从低到高是 `banned`、`user`、`admin`、`superadmin`。改动某个用户的管理操作（封禁、解封、任免管理员，以及处理举报时封禁上传者）要求对方的角色严格低于自己，否则返回 403 `user_not_manageable`。所以谁都改不了自己的角色，管理员动不了其他管理员，同 BS。
- 角色只能改成 `banned`、`user`、`admin`。设为管理员要有 `users.appointAdmin`；改动现有的管理员，本来就只有超级管理员满足上一条。
- 超级管理员不能在后台任命，同 BS，见"第一个超级管理员"。
- 解封一律回到 `user`。被封禁的管理员解封后不再是管理员，要重新任命：封禁和角色共用一列，SDK 的 `UserRole` 也是这样，拆开就要改插件 API。BS 也是这样。
- 删除材质不看上传者的角色，同 BS。

**在哪里检查**：
- 同 ADR-0022，放在用例里：锁住操作者自己的行之后，按事务里读到的角色判断，不信会话里的角色。刚被撤职的管理员，在途的请求也会被拒绝。
- 没有权限返回 403 `permission_denied`。被封禁的人没有任何权限。
- 后台的页面和导航用同一个 `can()` 决定显示什么。这只是体验，防线在用例里。

### 审计日志

`audit_logs`：

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | 自增 | 主键 | |
| actor_type | varchar(16) | 非空 | `user`、`system`、`plugin`，同 SDK 的 `Actor` |
| actor_user_id | integer | 可空，不建外键 | 操作者是用户时的 uid |
| actor_plugin_id | varchar(64) | 可空 | 操作者是插件时的插件 id。插件运行时落地后才会写 |
| action | varchar(64) | 非空 | 例如 `report.resolve` |
| subject_type | varchar(32) | 非空 | `user`、`texture`、`report` |
| subject_id | integer | 非空，不建外键 | |
| details | text | 非空 | JSON，见下表 |
| ip | varchar(45) | 可空 | 操作者的 IP，用 `clientIp()` 解析；脚本和系统操作为空 |
| created_at | 时间 | 非空 | |

- 索引：`(subject_type, subject_id, id)`、`(actor_user_id, id)`。按时间列出就用主键倒序，不另建时间索引。
- `actor_type` 加 CHECK 约束；`subject_type`、`action` 不加，在领域层校验：以后每个管理切片都会加新值，SQLite 改 CHECK 约束要重建整张表。
- **不建外键**：用户、材质删除之后，审计记录照样要说明是谁、对什么做了什么，`set null` 就看不出来了。这是 ADR-0015"核心表之间都声明外键"的例外。对象删除后读不到它的名字，所以 `details` 存下操作时的快照。删除账号时，审计记录不删。
- **和业务写入在同一个事务里**：用例调用 `audit(tx, …)`。用例失败回滚，审计记录也跟着撤销；留下来的记录，对应的操作一定发生了。不从事件派生，理由见"考虑过的其他方案"。
- **只记管理操作**，即操作者凭具名权限动了别人的东西。一次操作改了几个对象就记几条，例如删除材质时连带采纳了三条举报，就记一条 `texture.delete` 和三条 `report.resolve`。

| 动作 | 对象 | details |
|---|---|---|
| `report.resolve` | report | `{ action, tid, refunded, rewarded }` |
| `texture.delete` | texture | `{ name, type, hash, public, uploaderId, reportId? }` |
| `user.setRole` | user | `{ from, to, nickname, reportId? }` |

- `details` 里不放不变量 11 列出的东西。以后加了后台改密码，也只记"改了密码"。
- 不自动清理。保留期等定时任务（`job_schedules`）落地后再加设置项。
- 有 `audit.read` 的人能看到全部记录。

### 处理举报

`POST /api/admin/reports/{id}/resolve`，`{ action }`，要有 `reports.review`：

| action | 做什么 | 举报变成 | 举报人 |
|---|---|---|---|
| `dismiss` | 驳回 | `rejected`，处理方式 `dismissed` | 不退花费（ADR-0026） |
| `deleteTexture` | 删除材质，见"管理员删除材质" | `resolved`，`textureDeleted` | 按实付退还花费，发 `report.reward` |
| `banUploader` | 封禁上传者，材质留着 | `resolved`，`uploaderBanned` | 同上 |

- 只处理待处理的举报：用 `update reports set status = ?, … where id = ? and status = 'pending'` 推进状态，改不到行就返回 409 `report_already_handled`。两个管理员同时处理同一条，只有一个能结算。不存在的举报返回 404 `report_not_found`。
- 同时写上 `resolution`、`resolver_id`、`resolved_at`，发 `report.resolved`。
- `banUploader`：上传者已经注销的返回 404 `user_not_found`，角色规则同"权限"一节。上传者已经被封禁的，举报照样采纳，角色不再改动。
- 两样都想做时，先删除材质（举报随之采纳），再去用户列表封禁上传者。
- 举报人已经注销的，不退也不奖。
- 退还和奖励都经过 `adjustScore`，原因是 `score.reasons.reportRefunded`、`score.reasons.reportRewarded`，关联对象写举报。

### 材质删除时，一并结案它的待处理举报

不管材质是怎么删的（上传者删、管理员删、删除账号时删掉私有材质），都在同一个事务里把这个材质上所有待处理的举报结案，处理方式记为 `textureDeleted`，按实付退还花费：
- 管理员删的：处理人是这个管理员，并发 `report.reward`。删掉违规材质，就是认可了这些举报；
- 上传者自己删的，包括删除账号：处理人为空，不发奖励，同 BS 在材质已被删除时的处理。

每条各发一次 `report.resolved`。这段逻辑放在 ADR-0025 的删除流程里，几条删除路径都会经过。

这样待处理的举报总是指向存在的材质：`report.resolved` 的 `tid` 一定有值，管理员也不会碰上无从判断的举报。导入时，材质已经不存在的待处理举报（包括因为文件缺失被跳过的材质）记为已采纳、`textureDeleted`，处理人为空；举报人付过的花费直接加回他导入的积分，`score_paid` 记 0。

### 管理员删除材质

- `DELETE /api/admin/textures/{tid}`，要有 `textures.manage`，响应是 200，`{ resolvedReports }`。别人的私有材质也能删；不存在返回 404 `texture_not_found`。
- 走 ADR-0025 的删除流程：收藏了它的人按实付退还衣柜费（开着 `score.refundOnDelete` 时），用着它的角色和头像清空，文件按引用计数回收，不直接删文件。
- **不退上传者的存储费**：被管理员删掉的多是违规材质，退了就等于违规不花钱。上传者想拿回存储费，可以自己删。
- 先锁自己的行，再按 ADR-0025 的顺序锁上传者和材质。
- 材质详情页对有 `textures.manage` 的非上传者也显示"删除"。确认框写明后果（DESIGN.md §7），例如"从 15 个衣柜里移除并退还衣柜费，上传者的存储费不退；这个材质上的 2 条待处理举报一并采纳"。详情页仍然看不到别人的私有材质（ADR-0025），它们从举报页删除。

### 用户的角色

- `PATCH /api/admin/users/{uid}`，`{ role }`，取值 `banned`、`user`、`admin`，响应是 200，后台视图里的用户。和当前角色相同时什么也不做。
- 先锁自己的行，再锁对象的行，然后按"权限"一节判断。
- 角色变了，就发 `user.roleChanged`，并写审计记录。
- 封禁不吊销会话：被封禁的用户登录后只看到封禁说明，写操作每次都按数据库里的角色检查（ADR-0022）。CSL 对被封禁用户的角色返回 403，契约用例已经守着。被封禁用户的 Yggdrasil 令牌留给 Yggdrasil 切片处理。

### 第一个超级管理员

安装向导和启动器都还没有。这次在根目录加一个脚本 `pnpm set-role <邮箱> <角色>`，读和 `pnpm dev` 相同的环境变量，调用同一个改角色的用例：
- 操作者是 `system`，不受角色规则限制，可以设为 `superadmin`；
- 照样写审计记录，`ip` 为空。

安装向导和启动器的 `user` 子命令落地后，调用的也是这个用例。

### 页面

- 后台在 `/admin`。按 DESIGN.md 原则 5 做得信息密集，以桌面端为主，在移动端也能用。外壳同用户中心：全站页头、Nav 侧栏、正文。
- 没有登录跳到登录页，同 ADR-0022。没有任何后台权限的用户访问 `/admin` 返回 404。页头的用户菜单里，有后台权限的人多一项"管理后台"。
- 导航项由核心登记，按 `can()` 过滤。插件运行时落地后，再合并插件声明的 `area: 'admin'` 导航项（ADR-0011）。
- **概览** `/admin`：待处理举报数（点进举报页）、用户数、材质数、今天注册的用户数（按站点时区），最近 10 条审计记录。插件的 `admin.dashboard` 插槽以后放在这里。
- **举报** `/admin/reports`：
  - Tabs 分待处理、已采纳、已驳回，带数量。待处理的从早到晚排，便于先来先处理；另外两个从新到旧排；
  - 每行：材质的缩略图、名字、类型、公开与否、收藏数，上传者，举报人，理由，提交时间；已处理的再加上处理方式、处理人、处理时间；
  - 待处理的举报有三个操作，都用确认框写明后果。
- **用户** `/admin/users`：
  - 按 uid、邮箱、昵称搜索，按角色筛选；
  - 列：uid、头像和昵称、邮箱、角色、积分、注册时间、操作；
  - 操作按 `can()` 和角色规则显示：封禁、解封、设为管理员、取消管理员。
- **审计日志** `/admin/audit`：
  - 可以按对象（类型和 id）或操作者筛选；
  - 列：时间、操作者、动作、对象、详情摘要、IP；
  - 对象还在的，链接到它；已经删除的，显示 `details` 里的快照。
- 后台表格每页 50 行，用 Pagination，取代 DESIGN.md 里"后台表格以后另定"的说法。
- 数据流同 ADR-0022：服务端组件调用查询服务，客户端组件通过 REST 写入，再 `router.refresh()`。
- 文案放在 i18n 的 `admin` 命名空间。

### 接口

都认会话 Cookie（ADR-0022），权限在用例里检查：

| 接口 | 请求 | 成功响应 |
|---|---|---|
| `POST /api/admin/reports/{id}/resolve` | `{ action }` | 200，举报 |
| `DELETE /api/admin/textures/{tid}` | — | 200，`{ resolvedReports }` |
| `PATCH /api/admin/users/{uid}` | `{ role }` | 200，用户 |

新错误码：`permission_denied`、`user_not_manageable`、`user_not_found`、`report_not_found`、`report_already_handled`。

### 并发

- 举报的状态用带条件的 UPDATE 推进，见"处理举报"。
- 操作者的角色在锁住自己的行之后读。
- 管理员删除材质沿用 ADR-0025 的加锁顺序。连带结案的举报在锁住材质之后处理，举报人按 uid 升序结算，同 ADR-0025 给很多人退积分时的顺序。
- 遇到死锁或串行化失败，整个用例重试（`docs/schema.md`）。

### 事件和插件 API

- 事件都在业务事务里发：`report.resolved`、`user.roleChanged`、`texture.deleted`，以及删除材质时连带的 `closet.itemRemoved`、`player.texturesChanged`、`user.profileUpdated`。SDK 里都已经有了，插件 API 不变。
- BS 的 `report.reviewing`、`user.permission.updating` 是操作之前发的事件，拦不住操作。这次不加对应的拦截器，需要时按插件 API 变更的流程加。
- 插件通过能力 API 调用管理用例，要等插件运行时落地。

### 组件

- Table：DESIGN.md 的组件清单里已经有这一行，组件还没写。这次写进 `packages/ui`，配 story 和截图基线：后台的密集行高、行内操作、空状态；窄屏时在表格容器里横向滚动，页面本身不横向滚动。
- Pagination 也用于后台表格，同时改 DESIGN.md 里它的那一行。
- 其余复用现有组件：Nav、Tabs、Dialog、Badge、Menu、PlayerHead。

## 后果

- 新迁移：建 `audit_logs`。`docs/schema.md` 已经随采纳更新：`audit_logs` 的逐表设计，`reports` 的结案规则和导入对照。
- 管理用例必须先过 `can()`，这一点没有 lint 守着。REST 测试遍历 `/api/admin/` 下的每个路由，普通用户都要得到 403。
- 在四种数据库上做请求级测试：
  - 两个管理员并发处理同一条举报：只有一个成功，花费只退一次，奖励只发一次；
  - 管理员删除材质：收藏者按实付退还，上传者不退；同一材质上的其他待处理举报一并采纳，各自退还并发奖励；
  - 上传者自己删除被举报的材质：举报结案，只退不奖，处理人为空；
  - 角色规则：管理员不能封禁管理员，超级管理员可以；谁都改不了自己的角色；不能设为 `superadmin`；解封回到 `user`；
  - 撤职之后，这个人的下一次管理请求返回 403；
  - 用例失败回滚时没有审计记录；成功时审计记录的 IP 是 `clientIp()` 的结果。
- e2e 补上：
  - 用户举报一个材质 → 管理员在后台删除它 → 举报人在"我的举报"里看到已采纳，积分退回 → 审计日志里有这几条；
  - 管理员封禁一个用户 → 他进用户中心只看到封禁说明，CSL 对他的角色返回 403。
- 以后的用户管理操作（改邮箱、关两步验证等）同样要过 `can()` 和角色规则，并写审计记录。
- Yggdrasil 切片要处理被封禁用户的令牌。

## 考虑过的其他方案

- **RBAC：角色表、权限表，一个用户可以有多个角色**：理由见"权限"。真要分工，先加授权表；还不够，再考虑。
- **直接比较角色（`role === 'admin'`），不定义具名权限**：现在更省事，但以后加授权表就要改遍所有管理用例。具名权限现在的代价只是一张写在代码里的映射。
- **封禁拆成单独的列，解封后恢复原来的角色**：要改 SDK 的 `UserRole` 和 `user.roleChanged`。误封管理员不常见，重新任命一次就行。
- **审计日志从事件派生（订阅全部事件写日志）**：事件在事务提交之后至少投递一次，可能重复、可能晚到，也没有 IP；事件也不区分管理操作和用户自己的操作。
- **审计日志的操作者和对象建外键（`set null`）**：用户、材质删除后就看不出是谁、对什么做的，审计就没有意义了。
- **管理员删除时照 BS 退上传者的存储费**：理由见"管理员删除材质"。
- **材质删除后，待处理的举报留给管理员逐条处理（BS 的做法）**：`report.resolved` 的 `tid` 会没有值，要改插件 API；材质已经不在了，管理员也没有东西可以判断。
- **处理举报时可以同时删除材质和封禁上传者**：SDK 里 `resolution` 只有一个值。先删除材质、再去用户列表封禁，两步就能做到。
- **第一个注册的用户自动成为超级管理员**：新部署的站点一旦公开在网上，谁先注册谁就是超级管理员。
