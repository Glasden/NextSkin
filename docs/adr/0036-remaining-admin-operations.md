## 背景

ADR-0027 只做了处理举报、管理员删除材质、封禁和任免管理员，把其余的管理操作留给后面的切片：

- 用户：改邮箱（要给 `email_version` 加一，ADR-0024）、改昵称、改密码、改积分、标记邮箱已验证、关两步验证（ADR-0023）、删除用户；
- 后台的角色管理：改名、换材质、删除、转让（转让时 `score_paid` 清零，ADR-0022）；
- 管理别人的衣柜；改别人材质的名字、公开状态、模型；管理员在皮肤库里看别人的私有材质。

另外几处也指向这里：ADR-0034 把后台替用户解绑留到这一步；ADR-0030 把"管理员查看或吊销别人的启动器登录"留给后台用户管理；ADR-0025 说"上传者已注销的公开材质，这次谁也改不了，等后台"。界面已经在让用户找管理员（"手机和备用码都丢了？请联系站点管理员关闭两步验证"，没有配置邮件时"暂时无法验证邮箱。请联系站点管理员"），后台却还没有这些操作。

现状：

- 后台的用户页只有列表，行内菜单只能封禁、解封、任免管理员，没有详情页。指向某个用户的链接都是 `/admin/users?q={uid}`，这是子串搜索，会带出昵称或邮箱里含这串数字的其他用户。后台没有角色页。
- 用户侧的用例都把操作者当作对象本人：`deleteAccount` 核对本人的密码、拒绝管理员删除自己；角色的用例按 `user_id = actor.uid` 取行；材质的修改要求操作者是上传者，改公开时向操作者收费；衣柜的用例只动操作者自己的；`externalLogin.unlink` 只接收 uid。这些都不能原样给管理员用。
- 用户自己改邮箱要核对密码；配置了邮件时先给新地址发确认链接（1 小时有效），确认之后才生效、成为已验证，之后给旧地址发"邮箱已更改"；没有配置邮件时立即生效、成为未验证（ADR-0023）。
- Better Auth 找回密码只按邮箱找人，不看 `email_verified`。`email_verified` 只决定开着 `auth.requireEmailVerification` 时能不能管理角色、上传和修改材质、举报、用启动器登录。
- 找回密码的链接存在 `verifications` 里（标识 `reset-password:<令牌>`，值是 uid，1 小时有效）。重设时只按令牌找人，不看现在的邮箱；重设之后删掉这个用户的全部会话。现在没有代码在改邮箱、改密码时作废它们。
- 改密码由 Better Auth 完成，之后的 `onPasswordChanged` 先单独提交、删掉这个用户的全部启动器令牌，再另开事务发 `user.profileUpdated(['password'])`，actor 写死成被改的用户。Better Auth 的 `changePassword`、`setPassword` 只能作用于当前会话的用户。
- 两步验证：开关在 `users.two_factor_enabled`，密钥和备用码在 `two_factors`。登录时过了密码这一步，Better Auth 在 `verifications` 里写一个挑战 `2fa-<随机>`（值是 uid）和它的尝试计数 `2fa-attempts-2fa-<随机>`（值是次数），10 分钟内补上第二步就建立会话；"信任这台设备"的记录是 `trust-device-<随机>`（值是 uid）。Better Auth 的 `/two-factor/disable` 只能关自己的，要核对密码，只删当前设备那一条信任记录。只改开关、不删 `two_factors` 的行，用户之后再开启会被 Better Auth 以"已经开启"拒绝。
- 通行密钥算一种登录方式，用它登录不过第二步（ADR-0023）。没有任何能用的登录方式的账号，满足 ADR-0034 首次登录的第一步：第三方报告邮箱已验证、邮箱和账号相同时，直接绑定并登录。
- `adjustScore` 只接受非零的安全整数，扣到负数返回 `score_insufficient`，加到超过 2147483647 抛 `RangeError`（REST 返回 500）。导入器会原样导入 BS 的负积分，所以已经有余额为负的用户。
- 皮肤库的详情页对别人的私有材质返回 404，对管理员也一样。上传者注销以后，公开材质的 `uploader_id` 置空、照常留在皮肤库里，按上传者筛选再也找不到；导入器还会产生上传者为空的私有材质，现在只有被举报了才能在举报页看到。
- SDK 里没有角色换主人的事件；`Player` 里带着 `uid`。
- 后台和错误文案用"角色"指 `users.role`（"只能管理角色比你低的用户，也不能改自己的角色"），DESIGN.md §8 的"角色"是 player。加了角色管理页以后，两个意思会出现在同一页上。

BS 6.0.2 的做法：

- **用户管理**（`UsersManagementController`）：对象是自己、或者权限比自己低时放行，所以管理员能在后台改自己的邮箱、昵称、密码、积分、验证状态，后端甚至允许删除自己（只有前端把按钮禁用了）。只有改权限另外禁止了改自己。
  - 改邮箱：只校验格式和唯一，直接写入，验证状态不变，不通知旧地址；
  - 验证状态：取反；
  - 改密码：8 到 16 位，只换哈希，不退出任何登录；
  - 改积分：直接写成绝对值，可以是负数，不写流水；
  - 删除：删掉名下的角色和用户本身，材质和衣柜留着，指向已经不存在的用户。皮肤库的列表对用户表做内连接，这些材质从列表里消失（详情页仍能打开）。
- **角色管理**（`PlayersManagementController`）：主人是自己、或者主人的权限比自己低时放行。
  - 改名：规则、长度、唯一照常校验；
  - 转让：新主人存在就改 `uid`，不检查新主人的权限，不动材质和积分，发 `player.owner.updated`；
  - 换材质：任何存在的 tid 都能设，不检查可见性、衣柜和类型；
  - 删除：不退积分（用户自己删才退）。
- **衣柜管理**（`ClosetManagementController`）：不检查角色等级；加入不检查私有、不扣分、不加收藏数；移出不退分。只有网页内置的命令行用得到，没有页面。
- **皮肤库**（`SkinlibController`）：管理员能改名、改公开状态、改模型（包括在皮肤和披风之间改，不检查尺寸）、删除任何材质，不看上传者的权限；在皮肤库和详情页都能看到别人的私有材质。管理员改公开状态时照样按差价向上传者多退少补，上传者余额不够就失败，上传者已注销时直接出错。
- 各操作前后发 `*.updating`、`*.updated` 事件，前一个拦不住操作。

BS 这里的问题：

- **能在后台改自己**：偷到管理员会话的人，不用核对密码就能改掉这个管理员的邮箱和密码；管理员也能给自己加积分。
- **积分写绝对值、不留流水**：管理员打开表单之后用户签到或花了积分，提交时这笔变动就被覆盖；流水对不上余额。
- **验证状态是取反**：两个管理员同时点，结果互相抵消。
- **改邮箱立即生效、验证状态不变**：输错一个字母，登录名和找回密码的地址就成了别人的，这是 ADR-0023 否决用户侧立即生效的理由；没人核实过的地址还带着"已验证"。
- **改密码不退出登录**：后台重设密码多半是因为账号失控，旧的会话和启动器令牌照样能用。
- **换材质不看可见性**：把别人的私有材质设到角色上，就通过 CSL 公开出去了。
- **转让不动材质**：原主人的私有材质留在新主人的角色上；绑定这个角色的启动器令牌也留着。
- **衣柜管理不检查等级、不改收藏数**：普通管理员能改超级管理员的衣柜；收藏数和衣柜对不上。
- **改公开状态会因为上传者的余额失败**。

## 决定

### 范围

这次做：

- 权限：新增 `users.manage`、`players.manage`，扩大 `textures.manage` 的含义；
- 用户详情页，以及改昵称、改邮箱、改邮箱验证状态、改密码和收回账号、关两步验证、删通行密钥、解绑第三方账号、退出全部登录、改积分、删除用户、管理衣柜；
- 后台的角色页，以及改名、换材质、转让、删除；
- 管理员看别人的私有材质、筛出上传者已注销的材质，改别人材质的名字、模型、描述，把别人的公开材质下架（改成私有）；
- 找回超级管理员的两个命令行脚本；
- 审计动作、通知邮件、SDK 事件 `player.transferred`；
- 顺带堵上两处：邮箱改动生效时作废还没用的找回密码链接（用户侧也是），启动器刷新令牌时在锁内核对角色的主人。

不做，留给以后：

- 把权限单独授给普通用户（ADR-0027 的授权表）；
- 插件以 `actor: plugin` 调用这些用例（ADR-0033 推迟的"写核心数据的能力"）；
- 后台逐条查看、吊销某个用户的网页会话和启动器令牌，逐个删除通行密钥（这次只显示数量、全部删除）；
- 后台的材质列表 `/admin/textures`（上传者已注销的材质先用 `/skinlib?uploader=gone` 找）；
- 管理员把别人的私有材质改成公开、改别人衣柜里材质的名字；阻止上传者重新公开被下架的材质（要加标记，需要迁移）；
- 管理员在皮肤和披风之间改模型：要连带清掉槽位对不上的角色和用披风做的头像、更新这些角色的 `updated_at`，单独做。BS 允许随意改类型，导入的站点可能有标错类型的材质，现在只能删除重传，`packages/importer/MIGRATION.md` 写明这一点；
- Sheet 组件（DESIGN.md §6，见"页面"）；
- 管理操作要求刚登录过，见"考虑过的其他方案"。

### 分三个切片落地

每个切片一个提交，各自更新 `PROGRESS.md`：

1. 用户详情页和账号操作，包括改积分、删除用户、两个命令行脚本、作废找回密码链接；
2. 后台的角色管理，包括 SDK 事件、cdn-refresh 订阅它、刷新令牌在锁内核对主人；
3. 别人的材质和衣柜。

下文的"身份"指 `users.role`（封禁、用户、管理员、超级管理员），"角色"指 player。

### 权限

| 权限 | 能做什么 | admin | superadmin |
|---|---|---|---|
| `users.ban` | 查看用户列表和用户详情，封禁、解封（ADR-0027，多了查看详情） | ✓ | ✓ |
| `users.manage`（新） | 改账号（昵称、邮箱、验证状态、密码、两步验证、通行密钥、第三方绑定、退出登录）、改积分、管理衣柜、删除用户 | ✓ | ✓ |
| `players.manage`（新） | 后台的角色页：改名、换材质、转让、删除 | ✓ | ✓ |
| `textures.manage` | 删除别人的材质（ADR-0027）；改别人材质的名字、模型、描述，把它下架；查看别人的私有材质 | ✓ | ✓ |

- 都给普通管理员，同 BS。"能对谁做"已经在账号、角色和衣柜上把普通管理员限制在用户和被封禁的人身上；材质不看上传者的身份，同 ADR-0027。
- 不塞进 `users.ban`：它的含义是封禁，接管账号级的操作放进去，以后给"审核员"授权时就拆不开（ADR-0027 加具名权限的本意）。
- 积分、删除用户不单独设权限：现在两种管理员都有，分开没有用处。授权表落地之前，权限怎么拆都只改代码里的映射。
- `permissions.test.ts` 补上两项新权限，以及现在漏掉的 `plugins.manage`。

### 能对谁做

- **改动某个用户的**（账号、积分、衣柜、删除）：对方的身份要严格低于自己（ADR-0027），否则 403 `user_not_manageable`。
- **角色**：按主人判断。转让时原主人和新主人都要满足。
- **材质**：不看上传者的身份，同 ADR-0027 的删除材质。**但不能用后台修改、下架自己上传的材质**，返回 403 `admin_own_texture`：上传者自己改私有要按差价付费、要验证过邮箱（ADR-0025），走后台就都绕过了。删除照 ADR-0027 不拦：管理员删除不退存储费，删自己的只会吃亏。
- 所以在账号、角色和衣柜上，后台动不了自己，普通管理员动不了其他管理员，谁都动不了超级管理员；材质只按 `textures.manage` 判断，见上一条。自己的账号、角色、衣柜、材质在用户中心和皮肤库里改，那里有核对密码、刚登录过、限流、收费这些规则；后台能改自己，偷到会话的人就能绕过它们（BS 的问题）。超级管理员的找回见"命令行"。
- 对象被封禁、邮箱没有验证，都不影响管理操作（配置了邮件时的改邮箱例外，见"改邮箱"）：清理被封禁用户的数据正是常见的管理工作，同 BS。管理员自己有没有验证邮箱也不检查，同 ADR-0027 的删除材质。
- `errors.user_not_manageable` 改成"只能管理身份比你低的用户。"
- 后台的接口只要求登录。算密码哈希（改密码）、查快照（连公开材质一起删）这类昂贵的事之前，先在事务外做一次不加锁的预检，按上面的顺序判断权限和对象，免得没有权限的人让服务器白算；结论不作数，事务里锁住之后照样重新判断。

### 昵称和邮箱验证状态

`PATCH /api/admin/users/{uid}` 在 `{ role }` 之外接受 `nickname`、`emailVerified`，至少给一项。每项各按自己的权限检查（`role` 要 `users.ban`，另外两项要 `users.manage`），在同一个事务里执行；真正改了的项各发各的事件、各写一条审计，和当前值相同的项什么也不做。

- **昵称**：规则同注册（去掉首尾空白后 1 到 255 个字符，ADR-0018）。发 `user.profileUpdated(['nickname'])`。
- **邮箱验证状态**：显式设成 `true` 或 `false`，两个方向都可以，不做成取反（BS 的问题）。
  - 设成 `true` 时必须同时带 `expectedEmail`，即页面上显示、管理员核实过的地址。锁住对象的行之后和现在的邮箱比较，不同就返回 409 `email_changed`，页面刷新后重来。否则管理员停在旧页面上时，另一个管理员刚改的、或者用户在没有配置邮件的站点上刚改的地址，没人核实就被标成已验证。设成 `false` 不要求。
  - 它不影响找回密码和登录（见"现状"），只影响 `auth.requireEmailVerification` 挡住的那些功能。没有配置邮件的站点，这是让用户通过"必须验证邮箱"的唯一办法；改回未验证，用于发现地址可疑的时候。
  - 开着 `auth.requireEmailVerification` 时，确认框写明改回未验证之后，对方暂时不能管理角色、上传和修改材质、举报、用启动器登录。
  - 不发事件：用户自己经 Better Auth 验证邮箱时也不发。只在后台这一条路径上发，插件看到的就是半套。以后给 `user.profileUpdated` 的 `fields` 加 `emailVerified` 是次版本变更，到时两条路径一起加。

### 改邮箱

`POST /api/admin/users/{uid}/email`，`{ email, verified? }`。照 ADR-0023 分两种情况：

- **配置了邮件**：同用户自己改邮箱，给新地址发确认链接（ADR-0024 的令牌），用户确认之后才生效、成为已验证；确认之前，登录和找回密码仍然用旧地址。`verified` 不起作用。返回 `{ status: 'pending', pendingEmail }`。
  - 确认链接防的是管理员输错地址：输错一个字母，登录名和找回密码的地址就成了别人的，勾不勾"已验证"都拦不住，Better Auth 找回密码不看它。确认链接防不了冒充者，冒充者给的地址本来就能收信；核实身份是管理员在站外做的事。
  - 发起时 `email_version` 先加一，令牌按加一之后的版本签发：之前发出的改邮箱链接全部作废，包括输错地址的那一条。输错了就按正确的地址重新发起。
  - 需要管理员改邮箱的常见情况，是用户忘了密码、旧邮箱又收不到信：用户侧改邮箱要核对密码，自己改不了。确认链接正好适合这种情况：管理员发起，用户在新地址点确认，再用新地址找回密码。改密码、删通行密钥、解绑、退出全部登录都会作废还没确认的链接（见"作废在途的登录"），所以要等用户确认之后再做，确认框写明。
  - **旧邮箱落到别人手里时不用这个**：发起时发给旧地址的通知，以及确认之前的这段时间，都给了握着旧邮箱的人机会，用旧地址找回密码、登进去把邮箱换掉。这时用"收回账号"，新地址立即生效。确认框写明。
  - 用户点确认走用户侧现有的流程：锁行，核对旧地址和 `email_version`，检查唯一，发 `user.profileUpdated(['email'])`（actor 是点确认的用户本人），给旧地址发"邮箱已更改"。
  - 被封禁的用户点确认照旧被拒绝（ADR-0023），所以对象被封禁时直接返回 403 `user_banned`，不写审计、不发通知；`admin.errors` 的文案提示先解封，或者用"收回账号"。
- **没有配置邮件**：立即生效，同用户自己改邮箱。`verified` 决定新地址算不算已验证；页面上要求管理员明确选一项，不预选，接口缺省是 `false`。开着 `auth.requireEmailVerification` 时写明选"未验证"的后果：站点发不了验证邮件，对方会一直被挡住，直到管理员标记已验证。发 `user.profileUpdated(['email'])`，actor 是管理员。返回 `{ status: 'changed', user }`。
- 两种情况都一样的：
  - 格式、转小写、唯一照注册的规则校验；和现在的邮箱相同返回 `email_unchanged`。**不查邮箱域名的允许或禁止名单**：ADR-0023 查它是防用户绕过限制，管理员是有意为之，`setRoleAsSystem` 也不查。唯一冲突在 PG 上让整个事务作废，同 ADR-0023，等事务失败之后在事务外转成 `email_taken`。
  - 生效时 `email_version` 加一（ADR-0024），之前发出的改邮箱链接随之作废；还没用的找回密码链接也作废，见下一节。
  - 发起时给旧地址发通知（见"通知邮件"）。不退出登录，同用户自己改邮箱。
  - authserver 响应里的 `user.id` 由邮箱算出，生效后会跟着变，与用户自己改邮箱相同（ADR-0030）。

### 作废在途的登录

后台改密码（包括收回账号）、删通行密钥、解绑、退出全部登录和命令行的 `set-password` 共用一个函数，在同一个事务里作废这个用户的：

- 全部网页会话：Better Auth 没有开会话缓存，删掉行，下一次请求就失效；
- 全部启动器令牌；
- 两步验证的挑战：它已经过了密码这一步，10 分钟内补上第二步就成了会话。按值（uid）找出 `2fa-<随机>`，连同对应的 `2fa-attempts-2fa-<随机>` 一起删；
- 找回密码的链接 `reset-password:<令牌>`（值是 uid）：1 小时内还能用它改掉密码，重设时还会删掉全部会话，把刚恢复的用户踢下线；
- 还没确认的改邮箱链接，办法是 `email_version` 加一：确认链接不要求登录，知道密码的人可以先用用户侧的改邮箱把链接发到自己的邮箱，等管理员处理完再确认，然后用新邮箱找回密码。

邮箱改动生效时（谁发起都一样，包括用户自己改邮箱的确认）也删掉还没用的找回密码链接：它们发到了旧地址。用户侧原来没有作废，这是对 ADR-0023 的补充。Better Auth 找回密码时先查出用户、再写入记录、最后发信，都不加锁，改邮箱之前查出的请求可能在删除之后才写入记录、把信发到旧地址。所以发信的回调在一个短事务里先锁住用户行（同 `lockUser`），再重读现在的邮箱，和 Better Auth 查出的不同，就删掉这条记录、不发信。只重读不加锁不够：MySQL 的会话和 PostgreSQL 默认都是 READ COMMITTED，改邮箱的事务删完记录、还没提交时，新写入的记录不会被删到，回调也还读得到旧邮箱。加了锁，回调要么排在改邮箱的事务前面（信发到旧地址，但记录随后被删掉，链接无效），要么等它提交之后读到新邮箱。

这依赖 Better Auth 的标识格式和值，以及标识按明文存储（`verification.storeIdentifier` 保持默认），同"关两步验证"。升级时由测试守住：操作之后，之前签发的找回链接返回 `INVALID_TOKEN`，之前的两步验证挑战无法完成。

单独的改密码、退出全部登录不动通行密钥、第三方绑定和密码本身：知道密码、拿着通行密钥或第三方账号的人能立刻登回来。账号失控时用"收回账号"一次做完。分步做不行：每两步之间，攻击者都能用还没删掉的方式登录，拿到一个刚登录过的会话，再加一把通行密钥或者重新绑定。确认框列出通行密钥数和绑定数，并指向"收回账号"。

### 改密码和收回账号

`POST /api/admin/users/{uid}/password`，`{ password, removeOtherMethods?, newEmail? }`，密码长度同注册，8 到 128 位。

- **直接设新密码**，不提供"发重设链接"：配置了邮件的站点，用户自己就能找回密码；需要管理员的，正是收不到邮件的情况。
- 在事务外算哈希（scrypt 很耗 CPU，不能占着写锁，ADR-0018）。事务里更新 `accounts` 里密码那一行；没有这一行（经第三方登录建的账号、导入时哈希认不出的账号），就插入一行。后台由此也能给没有任何登录方式的账号恢复一种。
  - 插入撞上唯一约束时，在事务外把整个用例重跑一次，这次会走更新那一行的路径；哈希已经算好，重跑很便宜，同角色创建的 `retryOnPlayerUuidRace`。用户可能同时在安全页设置密码（Better Auth 的 `setPassword` 不锁 `users` 的行），而密码行同时落在 `accounts` 的两个唯一索引上（`account_id` 就是 uid），PG 上 `insertOrIgnore` 只能指定一个，撞上另一个照样让事务作废。唯一冲突不能变成 500。
- **同一个事务里作废在途的登录**，见上一节。用户自己改密码时保留当前设备（ADR-0023），后台没有"当前设备"；后台重设密码多半是因为账号失控。
- 不走 Better Auth 的 `changePassword`、`setPassword`，也不复用 `onPasswordChanged`：前者只能作用于当前会话的用户，后者把 actor 写死成被改的人，而且令牌的删除是单独提交的。删启动器令牌的那段抽成一个函数，两边共用。
- 发 `user.profileUpdated(['password'])`。审计只记"改了密码"，以及这次是不是新建了密码行（ADR-0027）。给用户发通知。
- 页面上可以手填，也可以生成一个 16 位的随机密码，只显示这一次，供管理员复制后交给用户。不强制下次登录时改密码：Better Auth 没有这个机制，用户可以到安全页自己改。
- OAuth 的令牌和用户自己改密码时一样不动，等 Yggdrasil Connect 的切片一起定。
- passwordHasher 插件格式的哈希被换成 scrypt，插件不参与（ADR-0033）。
- 返回 `{ revokedSessions, revokedTokens }`。改完之后页面显示剩下的会话数，见"并发"。

**收回账号**：账号失控时，同一个请求再带上：

- `removeOtherMethods: true`：删掉全部通行密钥、解绑全部第三方账号（包括插件停用了的），只留下这个密码；
- `newEmail`：把邮箱改成管理员在站外核实过的新地址，立即生效、算已验证，配置了邮件也不发确认链接。旧邮箱落到别人手里时用它：确认链接要等，等的这段时间握着旧邮箱的人能抢先。新地址在页面上输两遍；输错的代价也比单独改邮箱小，用户拿着管理员给的新密码照样能登录，再自己改。格式和唯一的校验、`email_version`、找回链接、事件、通知同"改邮箱"的立即生效，对象被封禁也可以。

设密码、删通行密钥、解绑、改邮箱、作废在途的登录在同一个事务里完成，攻击者没有空当再登录、再加一种登录方式。审计各写各的：`user.setPassword`、`user.setEmail`、`user.deletePasskeys`，每个解绑一条 `user.unlinkAccount`。页面上是"设置密码"对话框里的选项，确认框写明会删掉几把通行密钥、解绑哪几个账号；做完之后页面显示剩下的会话数、通行密钥数和绑定数，都应该是 0（见"并发"的残余风险）。

- 第三方绑定的回调在请求开头确认会话，之后要向第三方换令牌（网络请求，可能要几秒），最后才写绑定，中间不再确认会话。作废在途的登录恰好在这中间提交的话，盗号的人照样能把第三方账号绑回来。所以写绑定改为在锁住用户行之后，再确认发起绑定的那个会话还在；作废在途的登录在同一把锁下删会话，两者因此串行。这是对 ADR-0034 的补充。
- OAuth 的令牌不动：Yggdrasil Connect 的端点和页面还没做，现在发不出 OAuth 令牌。Connect 的 ADR 要决定收回账号、退出全部登录是否一并吊销它们。

### 关两步验证

`DELETE /api/admin/users/{uid}/two-factor`。一个事务里：

1. 删掉 `two_factors` 里这个用户的行：只改开关的话，用户之后再也开不了；网页和启动器共用的失败锁定也随之清掉。
2. `two_factor_enabled` 改成 `false`。
3. 删掉 `verifications` 里这个用户的两步验证挑战（连同尝试计数）和"信任这台设备"记录。Better Auth 自己关闭时只删当前设备那一条；管理员关闭多半是因为设备丢了，不删的话，用户重新开启之后，旧设备照样不用过第二步。开关已经关着也照样删：用户可能已经在别的设备上自己关掉了，丢了的那台设备的记录还在。开关和密钥行本来就没有时，对用户来说什么也没变，不写审计、不通知。

- 不退出登录：已有的会话本来就过了第二步，要踢人用"退出全部登录"或改密码。
- 不动通行密钥。不发事件（ADR-0023）。给用户发通知。
- 依赖 Better Auth 两步验证插件的表和 `verifications` 的标识格式（见"现状"，标识按明文存储），升级时由"关掉之后能重新开启、信任过的设备要重新过第二步"的测试守住，同 ADR-0034 对它的钩子结构的依赖。

### 删通行密钥

`DELETE /api/admin/users/{uid}/passkeys`：删掉这个用户的全部通行密钥。

- 攻击者控制账号时加的通行密钥，改密码、退出全部登录都挡不住，用它登录还不过第二步。不逐个删：后台分不清哪一把是攻击者加的；用户之后可以重新添加（要刚登录过，ADR-0023）。
- 遵守"最后一种登录方式"，理由同下一节：删完之后没有能用的登录方式时返回 409 `last_login_method`，先设置密码，或者用"收回账号"。在事务里锁住对象的行之后判断。
- 同一个事务里作废在途的登录：拿着这把通行密钥登进来的会话不能留下。管理员打开确认框之后通行密钥已经被删光了，也照样作废、写审计（数量是 0），不通知：通行密钥没了，拿着它登进来的会话还在。
- 不发事件，同用户自己删通行密钥。审计记下删了几把。给用户发通知。返回 `{ deleted, revokedSessions, revokedTokens }`。

### 解绑第三方账号

`DELETE /api/admin/users/{uid}/bindings/{插件 id}/{Provider id}`。

- **同样不能解掉最后一种能用的登录方式**（ADR-0034），返回 409 `last_login_method`，先设置密码，或者用"收回账号"。没有能用的登录方式的账号，正好满足 ADR-0034 首次登录的第一步：谁拿着一个报告邮箱已验证、邮箱和账号相同的第三方账号，登录就会直接绑定。管理员解绑多半是因为第三方账号被盗，盗号的人用同一个账号再登录一次，绑定就回来了。
- 插件停用了的绑定总能解：它不算能用的登录方式，解不解都不改变账号能不能登录，所以只在解的是能用的绑定时才做上面的检查。这和用户侧现在的写法不同，用户侧按解绑之后的状态判断，后台的用例单独判断。事务里先锁对象的行。
- 同一个事务里作废在途的登录：盗号的人已有的会话不能活过解绑，否则还能重新绑定。账号失控时用"收回账号"，见"作废在途的登录"。
- 不发事件（ADR-0034）。审计记下插件和 Provider。给用户发通知。返回 `{ revokedSessions, revokedTokens }`。

### 退出全部登录

`DELETE /api/admin/users/{uid}/sessions`：作废在途的登录，见上文。

- 这是 ADR-0030 留给后台的"吊销别人的启动器登录"。详情页显示未过期的会话数和启动器令牌数，不逐条列出。
- 封禁照旧不吊销（ADR-0027）。两件事分开：要立刻让被封禁的人下线，再点一次这个。
- 不发事件。审计记下删掉的会话数和令牌数。

### 改积分

`POST /api/admin/users/{uid}/score`，`{ delta, note? }`。

- **只按增量**：页面显示当前余额和改完的结果，提交的是增量。不写绝对值：管理员打开表单之后用户的签到和花费会被覆盖；流水本来就记增量。
- 经过 `adjustScore`，原因是新的 `score.reasons.adminAdjusted`，不带关联对象。用户在积分记录里看到"管理员调整"。
- `delta` 是非零整数，0 和小数由 zod 拒绝（400 `invalid_request`），否则 `adjustScore` 抛的 `RangeError` 会变成 500。锁住对象的行后读出余额：扣分后不能小于 0，加分后不能超过 2147483647，否则 400 `score_out_of_range`，参数带当前余额。余额为负的导入用户可以加分，加完仍为负也行。
- `note` 最多 200 个字符，只进审计记录：积分流水没有备注列，`reason` 存的是文案的键。
- 不发事件：积分变动都没有事件（ADR-0022 的签到）。

### 删除用户

`DELETE /api/admin/users/{uid}`，不要密码；查询参数 `publicTextures=delete` 表示连公开材质一起删。

- 把 `deleteAccount` 事务里的主体抽成一个共用的函数：逐个删角色并发 `player.deleted`（不退积分），逐条移出衣柜、扣收藏数，私有材质走删除流程，删用户的行，发 `user.deleted`。用户自删的路径保留核对密码、`admin_cannot_delete_self` 和封禁检查；后台的路径换成权限和"能对谁做"，被封禁的用户也能删。连带事件的 actor 都是管理员。
- **删掉的材质照管理员删除材质处理，只是不发奖励**：待处理的举报结案，处理人记这个管理员，奖励为 0。ADR-0027 给管理员删材质发奖励，理由是"删掉违规材质，就是认可了这些举报"；删一个账号时并没有逐个审查这些材质。处理人不能留空：举报页把处理人为空的已采纳举报说成"上传者自己删除"，而按审计找回的处理人又被当作已注销的用户。
- **公开材质默认留下**，同用户自己注销（ADR-0025）：上传者显示为"已注销"，之后不能再按上传者找到，只能用 `/skinlib?uploader=gone`。清理刷屏账号时，在确认框里勾选"同时删除 N 个公开材质"，这一项还要有 `textures.manage`。BS 的皮肤库列表会把已删除用户的材质藏起来，这里不会，所以要给这个选项。
  - 公开材质先删，一个材质一个事务，按上面的规则逐个删除，最后一个事务删账号，不整体回滚：中途失败时，已经删掉的材质不恢复，重新提交接着删剩下的。公开材质被收藏、用在角色上、设成头像的多，每删一个都要找出引用它的人、逐个退款发事件；几百个放进一个事务，SQLite 的全局写锁会被占得远超默认的 5 秒等待，其他写操作就会失败（AGENTS.md 的坑）。私有材质照旧在删账号的事务里，同用户自己注销。
  - 删除期间对象如果没被封禁，还能上传新的公开材质，这些会留下，用 `uploader=gone` 找。确认框建议先封禁。
- 确认框写明后果（DESIGN.md §7）：几个角色、几个私有材质、衣柜里几件、几个 OAuth 应用一起删除；几个公开材质留下（或者勾选后一起删除），附 `/skinlib?uploader={uid}` 的链接供先查看；"这个邮箱之后可以重新注册，要挡住这个人，就保持封禁，不要删除"。设了审计保留期时，提示角色的 UUID 只留在审计记录里，到期一起删除。
- 审计：一条 `user.delete`，快照里有昵称、邮箱、身份、积分，角色数、衣柜件数，留下的公开材质的数量和前 100 个 tid；名下每个角色各记一条 `player.delete`，删掉的每个材质照 ADR-0027 记一条 `texture.delete`，结案的每条举报记一条 `report.resolve`（`rewarded` 为 0）。`details` 在 MySQL 上是 text，最长 64 KB，所以快照里不放没有上限的列表：角色的 UUID 要完整保留，各自一条记录，不能截断。角色删除以后，它的 UUID 只留在这些 `player.delete` 里（不变量 2 说明了 UUID 对服务器的意义）；设了 `audit.retentionDays` 的站点，这些记录到期也会被删掉。
- 不发通知：邮件任务遇到已经删除的用户会跳过。

### 衣柜

`POST /api/admin/users/{uid}/closet`，`{ tid, name? }`；`DELETE /api/admin/users/{uid}/closet/{tid}`。

- **加入**：
  - 不扣分，`score_paid` 记 0。退还按实付（ADR-0025），之后移出退 0，刷不了分；
  - 收藏数原子加一，同用户自己加入（不变量 5，BS 不加）；
  - 材质要对衣柜主人可见（公开的，或者主人自己上传的），否则 `texture_not_found`：主人看不见的衣柜项会被衣柜列表藏起来，也设不到角色上。已经在衣柜里返回 `closet_item_exists`。名字默认取材质名；
  - 发 `closet.itemAdded`，`uid` 是主人。
- **移出**：同用户自己移出。开着 `score.refundOnDelete` 时按这一件的实付退给主人：主人没有过错，同 ADR-0027 删除材质时退给收藏者。收藏数减一；清掉主人名下用着它的角色（两个槽），头像不动（ADR-0026）。导入留下的、主人看不见的衣柜项也能这样移出。
- 衣柜的移出逻辑抽成一个函数，把"衣柜主人"和"事件的 actor"分开，两条路径共用。
- 用户详情页的衣柜节用一个新的后台查询，包括主人看不见的项（标出来），每页 50 行（ADR-0027），翻页用查询参数 `?closet=`，不和页面上别的分页冲突。

### 后台的角色管理

**角色页** `/admin/players`，要有 `players.manage`：

- 按角色名搜索（不分大小写的包含匹配），或者按 UUID 精确查找（带不带连字符都行）；`?owner={uid}` 列出某个用户的角色，用户详情页链接到这里。服主最常问的是"这个游戏名是谁的"，用户列表查不到。
- 列：pid、头像和角色名、UUID、主人、皮肤和披风、更新时间、操作。每页 50 行（ADR-0027）。查询服务每行还给出主人的身份和角色的 `score_paid`：行内操作只给主人身份比自己低的角色显示，转让的确认框写明不退多少积分。

**共同的规则**：

- 先锁自己，再锁主人。主人在加锁之前读出，锁住之后按 `user_id = 主人` 重读角色；读不到（这期间被转让或删除了）返回 `player_not_found`。
- 和用户侧的用例共用改名、换材质的主体，参数是主人的 uid 和事件的 actor；启动器上传材质的路径不变。顺带统一用注入的时钟（现在 `create`、`delete` 用的是 `new Date()`）。

**改名**：`PATCH /api/admin/players/{pid}`，`{ name }`。规则、长度、唯一同用户侧（ADR-0022），不收积分，UUID 不变（不变量 2）。唯一冲突在事务外转换。发 `player.renamed`。给主人发通知。

**换材质**：同一个接口，`{ skin?, cape? }`，`null` 清空。

- 材质要对主人可见，否则 `texture_not_found`：不这样做，别人的私有材质就通过 CSL 公开出去了（BS 的问题）。
- 类型要和槽位一致，否则 `texture_type_mismatch`。
- **不要求在主人的衣柜里**：这条规则是为了让用户的衣柜费有意义（ADR-0026），管理员代为设置不是用户在绕过它。导入的角色本来就有这种状态，材质改私有或删除时的清理按引用找人，不看衣柜。
- 发 `player.texturesChanged`。一个请求同时改名和换材质时，同用户侧的 PATCH：两个事件用同一个改完的 `Player`，各写一条审计。

**转让**：`POST /api/admin/players/{pid}/transfer`，`{ uid }`。

- 页面上输入新主人的 uid 或邮箱（按邮箱查要有 `users.ban`），经 `GET /api/admin/users/lookup` 查到之后，确认框显示新主人的头像、昵称、邮箱和身份，以及后果：原主人付的积分不退、新主人的 `score_paid` 记 0；要清掉的材质，由角色现在的皮肤和披风各调一次 `GET /api/admin/textures/{tid}?owner={新主人}`、按 `visibleToOwner` 列出；"绑定这个角色的启动器登录会失效"，不写数量。转回去也恢复不了这些。uid 填错一位，带着游戏服务器数据的 UUID 就到了陌生人手里。
- 新主人不存在返回 404 `user_not_found`；原主人和新主人都要严格低于自己。新主人和原主人相同时什么也不做。新主人被封禁也照样转让，确认框写明之后协议端点对这个角色返回 403。
- 加锁：自己 → 原主人和新主人按 uid 升序 → 材质（tid 升序）。角色这一行不单独加锁：改角色的写入都先锁主人，锁住两个主人之后它不会再变。唯一的例外是上传者改材质的模型，它只锁上传者和材质，再改引用这个材质的角色的 `updated_at`；先锁角色再锁材质，就会和它形成环。
- UUID、名字不变；`updated_at` 更新；`score_paid` 清零（ADR-0022）。**原主人当初付的积分不退**，同 BS；需要补偿时用"改积分"，留有审计。
- **新主人看不到的材质从角色上清掉**：别人上传的私有材质，包括原主人的。公开材质和新主人自己的私有材质保留。
- 先改 `user_id`、清材质、改 `updated_at`，再用同一个转让之后的 `Player` 发事件：清掉了材质就发 `player.texturesChanged`（`previous` 是原来的材质），然后发 `player.transferred`。两个事件里的 `player.uid` 都是新主人。
- **同一个事务里删掉绑定这个角色的启动器令牌和设备授权的选择**（`device_code_selections`）。令牌每次使用都核对角色的主人（ADR-0030），旧令牌本来就用不了；但角色再转回原主人时它们会重新生效，而且一直占着原主人的令牌数上限。ADR-0015 也要求有连带效果的删除由用例显式完成。
- **刷新令牌时在锁内重新核对角色的主人**：现在带 `selectedProfile` 的刷新在事务外确认角色属于令牌的用户，进了事务、锁住用户之后不再核对。转让恰好在两者之间提交的话，刷新会给原主人签发一个绑定这个角色的新令牌，正是上一条要消除的状态。改成锁住之后用事务重读，不属于就返回现有的 `profile_not_owned`。
- 进服记录只在缓存里留 120 秒，不处理：转让之前刚进服的那一次，`hasJoined` 在 120 秒内仍可能通过。
- Yggdrasil Connect 记在 `oauth_consents` 里的角色，等 Connect 的切片处理（ADR-0022）。
- 发新事件 `player.transferred`，见"事件和插件 API"。给原主人和新主人发通知。

**删除**：`DELETE /api/admin/players/{pid}`。

- **不退积分**，同 BS 的后台删除和 ADR-0027 的管理员删除材质：后台删角色多半是因为名字违规。需要补偿时用"改积分"。
- 确认框写明："UUID 会和这个角色一起失效，游戏服务器上按 UUID 存的数据对不上；只是名字违规的话请改名，UUID 保留。"
- 发 `player.deleted`，`uid` 是主人。启动器令牌和设备授权的选择由外键级联删除（ADR-0030）。给主人发通知。

### 别人的材质

**查看**：有 `textures.manage` 的人能看到别人的私有材质：

- 皮肤库的详情页；
- `/skinlib?uploader={uid}`，走 `(uploader_id, id)` 索引；`/skinlib?uploader=gone` 列出上传者已注销的材质（`uploader_id` 为空，同样走这个索引），公开和私有都列。`gone` 只对有 `textures.manage` 的人生效，其他人当作没有这个筛选。皮肤库的总列表仍然只有公开材质：混列要带 OR 条件，用不上索引（ADR-0025）。
- 能不能看由查询服务按数据库里的身份判断，不信会话里的（ADR-0027）。
- 后台的其他页面也照这条规则：用户详情页的衣柜节、角色页的皮肤和披风列、按 tid 查材质的接口里出现别人的私有材质时，有 `textures.manage` 才给名字和预览，否则只显示"私有材质"和 tid；衣柜项的名字默认就是材质名，一并不给，后台加入衣柜的响应也照这条。现在两种管理员都有这项权限，这是给以后的授权表准备的。
- **只放开查看**：加入衣柜、设为角色的材质、设为头像、举报，对管理员仍然把别人的私有材质当作不存在。清理流程和衣柜列表都假设衣柜、角色、头像里只有持有者看得见的材质。详情页打开别人的私有材质时，不显示这几个操作，只显示管理面板，并注明"这是别人的私有材质"。
- 审计页对私有材质的链接现在点进去是 404，举报页现在不给私有材质链接；这次都链接到详情页。

**修改**：`PATCH /api/admin/textures/{tid}`，`{ name?, type?, description? }`，至少一项。

- 规则同上传者（ADR-0025）：模型只能在 Steve 和 Alex 之间改，改成 Alex 要求宽高相等；描述可以是 `null`。不检查管理员自己的邮箱验证。
- **上传者已注销的材质也能改**，这是 ADR-0025 留给后台的。
- 发 `texture.updated`。

**下架**：`POST /api/admin/textures/{tid}/unpublish`，把别人的公开材质改成私有。连带效果大，有自己的确认框和审计动作，所以单独一个接口。已经是私有的什么也不做，上传者已注销的私有材质也一样（先判断这一条，再判断下面的 409）。

- **只能下架，不能改成公开**：要不要公开自己的私有材质，是上传者的事，后台没有需要替上传者公开的理由。
- **下架拦不住上传者重新公开**，而被移出的衣柜项、清掉的角色材质和头像不会恢复。处置违规内容用删除或封禁；下架用于不该出现在皮肤库、又不必删除的材质。确认框写明。阻止重新公开要加一个"被下架"的标记，需要迁移，留给以后。
- 连带效果同上传者自己改私有（ADR-0025），只是不包括的那个人换成上传者：别人的衣柜里移除，开着 `score.refundOnDelete` 时按实付退衣柜费；别人的角色和头像清掉；上传者自己的衣柜和角色不动。待处理的举报照旧挂着。
- **不动上传者的积分，`score_paid` 不变**：后台操作不能因为上传者的余额而失败（ADR-0025）。`score_paid` 从此是"实付的存储费"，不一定是当前可见性的价格：上传者删除时，拿回的是付过的数；上传者再改回公开时照常按现价重新计价，差额是 `score_paid` 减去现在的公开存储费。价格没变、又不是导入的材质，差额是 0；改过价格，或者导入的材质（`score_paid` 按 BS 记的大小和奖励算出，见 `docs/schema.md`），要补差价或者退回一部分，同上传者自己来回切换。`docs/schema.md` 里这一列的说明改成"实付的存储费"，去掉"为当前可见性"。
- **上传者已注销的材质不能下架**，返回 409 `texture_uploader_gone`：那样就成了谁都看不到、谁都没付过钱、文件永不回收的条目。要下架就删除。
- 发 `texture.updated`，以及连带的 `closet.itemRemoved`、`player.texturesChanged`、`user.profileUpdated(['avatar'])`。管理员自己衣柜里的这一件也会被移出，管理员不是上传者。

修改和下架都按"自己 → 上传者 → 材质 → 引用者（uid 升序）"加锁，同 ADR-0025 和管理员删除材质：在锁外读出上传者，锁住上传者，再锁材质，锁住之后重新判断上传者，这期间上传者注销了就按上面的规则处理，是自己就返回 403。不锁上传者的话，在 MySQL 和 PostgreSQL 上，上传者注销和下架并发时，注销只删私有材质、下架又把它改成了私有，结果就是一个私有、上传者为空的条目。

### 命令行

后台动不了超级管理员。没有配置邮件的站点，超级管理员忘了密码，或者丢了验证器又丢了备用码，现在没有办法找回：`pnpm set-role` 把另一个账号设成超级管理员也帮不上，超级管理员动不了超级管理员。加两个脚本，读和 `pnpm dev` 相同的环境变量，同 `pnpm set-role`：

- `pnpm set-password <邮箱或 uid> [--remove-other-methods] [--email <新地址>]`：在终端里输入两次新密码，不回显，不放在参数里（会留在 shell 历史里）。效果同后台的改密码和收回账号：作废在途的登录、发 `user.profileUpdated(['password'])`、通知；`--remove-other-methods` 删掉全部通行密钥、解绑全部第三方账号，`--email` 把邮箱立即改成新地址。超级管理员账号失控时，攻击者可能加了自己的通行密钥或绑定，多半还用用户侧的改邮箱把邮箱换成了自己的（只要知道密码）；后台又动不了超级管理员，而重新登进去的人能安装插件。所以三件事要在一个事务里做完，也要能按 uid 找到邮箱已经被换掉的账号。
- `pnpm disable-2fa <邮箱或 uid>`：效果同后台关两步验证，不退出登录、不发事件，通知。

两个脚本调用两个系统入口（`setPasswordAsSystem`、`disableTwoFactorAsSystem`），同现有的 `setRoleAsSystem`：和后台用例共用主体，不受权限和"能对谁做"的限制，REST 不导出它们。后台用例照旧只接收 `AdminActor { uid, ip }`，路由不可能误传系统身份绕过检查。事件和审计的 actor 是 `system`，审计的 `ip` 为空，各项各写各的审计。启动器的 `user` 子命令落地后，调用的也是这两个入口。

### 事件和插件 API

后台操作的 actor 是管理员，命令行找回的 actor 是 `system`，`data` 里的 uid 是对象。删除材质已经是这样（ADR-0025、ADR-0027）。不改 `Actor`：加成员是大版本变更。SDK 的作者文档（`docs/events.md`）补一段准确的说法：

> actor 是发起这次操作的人。后台操作和连带效果（材质改私有或删除后，清理别人的衣柜、角色、头像）里，`data` 里的用户可能不是 actor；后台操作也可能波及管理员自己。只看信封分不出后台操作和连带效果。

插件确实需要认出后台操作时，以后给事件加可选字段，是次版本，这次不在文档里承诺。

| 操作 | 事件 |
|---|---|
| 改昵称、改邮箱、改密码（包括收回账号） | `user.profileUpdated`（`nickname`、`email`、`password`） |
| 改验证状态、关两步验证、删通行密钥、解绑、退出全部登录、改积分 | 不发 |
| 删除用户 | 同删除账号：`player.deleted`、`closet.itemRemoved`、材质的删除事件、`user.deleted` |
| 衣柜 | `closet.itemAdded`、`closet.itemRemoved`，移出时连带的 `player.texturesChanged` |
| 角色改名、换材质、删除 | `player.renamed`、`player.texturesChanged`、`player.deleted` |
| 转让角色 | 新的 `player.transferred`，清掉材质时先发 `player.texturesChanged` |
| 改材质、下架 | `texture.updated`，下架时的连带事件 |

**新事件** `'player.transferred': { player: Player; previousUid: Uid }`，`player` 是转让之后的样子：

- 按 uid 维护角色列表或权限的插件，没有它就不知道角色换了主人。拆成 `player.deleted` 加 `player.created` 是错的：pid 和 UUID 都没变。BS 有 `player.owner.updated`。
- 转让会改变协议响应：主人被封禁时 CSL、USM 和旧版接口返回 403，`updated_at` 也进了 CSL 的 `Last-Modified` 和 USM 的 `last_update`。所以 cdn-refresh 订阅 `player.transferred`，刷新 `playerPaths(player.name)`，不需要新能力。封禁、解封有同样的 CDN 缓存问题（`user.roleChanged` 只带 uid），不在本 ADR 范围内。
- 新增事件是次版本变更。SDK 还在候选期，公开面照样可以改（ADR-0035）。按插件 API 变更的流程，先改 SDK 再改核心：SDK 的 `events.ts`、plugin-host 的事件名列表、type-tests、api-extractor 报告；`docs/events.md` 的小标题、"不需要能力"那句里的事件数和事件表（加 `player.transferred`，`player.texturesChanged` 的"何时发出"补上转让和下架）；README 里的事件数；`migrating-from-bs.md` 的对照表加一行 `player.owner.updated` → `player.transferred`；`.changeset/pre/plugin-sdk-1.md`（1.0 的更新日志摘要）里的"16 个事件"。changeset 覆盖 SDK 和构建命令两个包（ADR-0035，构建命令打进了 plugin-host 的事件列表）。

只有后台才有的状态变化不发事件，先例分别是 Better Auth 的验证邮箱、ADR-0023、ADR-0034、ADR-0022 的签到。验证状态和积分，插件可以经 `users.readPrivate` 读 `PrivateUser` 得到；两步验证、通行密钥、第三方绑定、会话，插件在 1.0 里读不到。以后需要时加事件或字段，都是次版本。

不加拦截点，同 ADR-0027 对 BS `*.updating` 的处理。插件通过能力调用这些用例仍然推迟（ADR-0033）。

### 通知邮件

`packages/email` 加一个模板"管理员修改了你的账号"，写明改了什么和时间，不带链接：

- 账号：改邮箱（发起时发给旧地址，配置了邮件时写明新地址确认之后才生效）、改密码、关两步验证、删通行密钥、解绑第三方账号，发给账号现在的邮箱；收回账号发一封，列出这次改的全部项目，改了邮箱时发给旧地址；
- 角色：改名、删除发给主人，转让发给原主人和新主人。角色带着游戏服务器上按 UUID 存的数据，偷到管理员会话的人最可能做的就是把值钱的角色转走。

邮件任务和修改在同一个事务里入队；没有配置邮件就不发。理由同 ADR-0023 改邮箱时通知旧地址：管理员账号被人滥用时，原主人至少能知道。改昵称、验证状态、积分、退出登录、换材质、衣柜、删除用户不发；材质的修改和下架也不发，同 ADR-0027 的管理员删除材质。

现有的 `emailChanged` 写着"如果不是你本人操作，请联系站点管理员"，不适合管理员直接做的修改。改邮箱经确认链接生效时，确认的是用户本人，旧地址照旧收到它。

### 并发

- 每个用例先锁自己的行，再锁对象（ADR-0027）；要锁几个用户时（转让），自己之后按 uid 升序。
- 材质的修改和下架：自己 → 上传者 → 材质 → 引用者（uid 升序），见"别人的材质"。
- 改积分的余额在锁住对象之后读，两次检查之间不会有别的写入。
- 改密码在同一个事务里改 `accounts` 那一行、作废在途的登录：正在用旧密码签发的启动器登录，锁住那一行之后会发现哈希变了（`docs/schema.md` 的 yggdrasil_tokens）。密码行的插入撞上用户自己设置密码时，在事务外重跑，见"改密码和收回账号"。
- 用户侧在事务外核对密码、之后才写入的几条路径，写入之前确认密码还是核对时那个哈希，不然收回账号之后，盗号的人在途的请求还能生效：
  - Better Auth 的改密码在事务外核对当前密码，之后按行 id 写入新哈希。在它写入的同一个事务里，按核对过的哈希对密码行做一次条件更新，没有更新到就按"密码不对"整体回滚。条件更新会锁住这一行，后台的事务还没提交就等它提交、再按新值判断。不堵的话，管理员设的密码会被悄悄换掉，页面上的计数看不出来。核对过的哈希经 Better Auth 的请求级状态从 `password.verify` 带过去。
  - 用户侧改邮箱、删除账号锁住用户之后比较哈希。不比较的话，改邮箱会按加一之后的版本签发确认链接、或者直接盖掉刚收回的邮箱，删除账号会删掉刚收回的账号。
  - 找回密码不用另做：Better Auth 在事务里先消费令牌，作废在途的登录删掉令牌之后，它拿不到。
- **接受的残余风险**：Better Auth 的网页登录在核对密码和建立会话（或者写入两步验证的挑战）之间不锁任何行，后台改密码的事务恰好在这几十毫秒里提交，就会留下一个会话，或者一个 10 分钟内还能补上第二步的挑战。先核对密码、再重建会话的端点（例如关闭两步验证）也一样。添加通行密钥也一样：Better Auth 先确认会话刚登录过，再写入通行密钥，中间不锁 `users` 的行。改完之后页面显示剩下的会话数、通行密钥数和绑定数，不为 0 就再处理一次；挑战看不到，确认框提示账号失控时过 10 分钟再退出一次。要堵上就得在每次网页登录、添加通行密钥时都锁住用户行重新核对。第三方绑定的空当长得多（要等第三方的网络请求），已经在"收回账号"里堵上。
- 转让和启动器刷新令牌：刷新在锁内核对主人，见"转让"。
- 邮箱、角色名的唯一冲突在事务外转换。
- 遇到死锁或串行化失败，整个用例重试。

### 页面

**用户详情页** `/admin/users/{uid}`，要有 `users.ban`。页首是头像、昵称、uid、身份和返回列表的链接，下面分节，照插件详情页的写法：

| 节 | 显示 | 操作（`users.manage`，除非另注） |
|---|---|---|
| 账号 | 邮箱和验证状态、昵称、注册时间、语言 | 改昵称、改邮箱、标记已验证或未验证；封禁、解封（`users.ban`），任免管理员（`users.appointAdmin`），同列表 |
| 积分 | 余额、最近 10 条流水 | 改积分 |
| 登录与安全 | 有没有密码；两步验证开没开、剩几个备用码；通行密钥数；第三方绑定（插件停用了的标出来）；未过期的会话数、启动器令牌数 | 设置密码（可选收回账号）、关两步验证、删除全部通行密钥、解绑、退出全部登录 |
| 角色 | 名下角色的名字和 UUID | 链接到 `/admin/players?owner={uid}`（`players.manage`） |
| 材质 | 上传的公开和私有材质数 | 链接到 `/skinlib?uploader={uid}` |
| 衣柜 | 衣柜里的材质，每页 50 行，主人看不见的导入遗留项标出来 | 按 tid 加入、移出 |
| 审计 | 以这个用户为对象的最近 10 条 | 链接到完整的筛选 |
| 删除 | — | 删除用户 |

- 操作按 `can()` 和"能对谁做"显示，这只是体验，防线在用例里（ADR-0027）。
- 每个操作是一个 Dialog，需要输入的放 Form，危险的加 alert，确认框写明后果（DESIGN.md §7）。DESIGN.md §6 说编辑详情用 Sheet，这里每次只改一项、要做决定，用 Dialog 合适，同用户中心和插件表格的现有做法（DESIGN.md §11）。
- 按 tid 加入衣柜时，经 `GET /api/admin/textures/{tid}?owner={uid}` 显示预览和主人能不能用。
- 后台的错误文案对管理员说话，见"接口"。
- 用户列表的每一行链接到详情页，行内的身份菜单保留。审计表、举报页、插件表格里指向用户的链接都改成详情页；皮肤库详情页的管理面板也加一个指向上传者详情页的链接。

**角色页** `/admin/players`，见上文。行内操作：改名、换材质、转让、删除。换材质的 Dialog 按 tid 输入，同样经 `GET /api/admin/textures/{tid}?owner=` 显示预览。导航加"角色"一项，要有 `players.manage`。

**皮肤库详情页**：对别人的材质，有 `textures.manage` 的人看到管理面板：编辑（名字、模型、描述）、下架（公开的才有）、删除。自己的材质照旧只有上传者的操作。下架的确认框写明后果，例如"从 15 个别人的衣柜里移除并退还衣柜费，用着它的角色换回默认皮肤；上传者的积分不变"。下架的确认框还写明上传者可以随时重新公开，处置违规内容请删除。别人的衣柜件数和删除确认框的数字一起由 `textureDeletionImpact` 给出（`othersInCloset`：上传者之外的人的衣柜项）。上传者已注销的公开材质不显示下架，写明要处理请删除。现有删除材质的确认框无条件写"退还衣柜费"，皮肤库的 `skinlib.admin.deleteHint` 和举报页的 `admin.reports.deleteHint` 都改成按 `score.refundOnDelete` 写。

**用语**：后台和错误文案里指 `users.role` 的"角色"改成"身份"（"身份：封禁、用户、管理员、超级管理员"），包括插件的能力说明（`admin.plugins.capabilities.users.read`）、用户列表的说明和筛选标签；SDK 作者文档 `docs/events.md` 里 `user.roleChanged` 的说明一起改，只改文档，随同一个 changeset。DESIGN.md §8 的术语表加一行。

### 接口

都认会话 Cookie，权限在用例和查询服务里检查（ADR-0027）。现有的 REST 不用 PUT，这里也不用。

| 接口 | 请求 | 成功响应 |
|---|---|---|
| `PATCH /api/admin/users/{uid}` | `{ role?, nickname?, emailVerified?, expectedEmail? }`，至少一项；`emailVerified` 为 `true` 时 `expectedEmail` 必填 | 200，用户 |
| `POST /api/admin/users/{uid}/email` | `{ email, verified? }` | 200，`{ status: 'pending', pendingEmail }` 或 `{ status: 'changed', user }` |
| `POST /api/admin/users/{uid}/password` | `{ password, removeOtherMethods?, newEmail? }` | 200，`{ revokedSessions, revokedTokens }` |
| `DELETE /api/admin/users/{uid}/two-factor` | — | 200，用户 |
| `DELETE /api/admin/users/{uid}/passkeys` | — | 200，`{ deleted, revokedSessions, revokedTokens }` |
| `DELETE /api/admin/users/{uid}/bindings/{pluginId}/{providerId}` | — | 200，`{ revokedSessions, revokedTokens }` |
| `DELETE /api/admin/users/{uid}/sessions` | — | 200，`{ revokedSessions, revokedTokens }` |
| `POST /api/admin/users/{uid}/score` | `{ delta, note? }` | 200，`{ score }` |
| `DELETE /api/admin/users/{uid}` | 查询参数 `publicTextures=delete`，可选 | 200 |
| `POST /api/admin/users/{uid}/closet` | `{ tid, name? }` | 201，衣柜项 |
| `DELETE /api/admin/users/{uid}/closet/{tid}` | — | 200，`{ refunded }` |
| `GET /api/admin/users/lookup` | 查询参数 `q`：uid 或邮箱，精确匹配 | 200，`{ uid, nickname, email, role, avatar }`；没有就 404 `user_not_found` |
| `PATCH /api/admin/players/{pid}` | `{ name?, skin?, cape? }`，至少一项 | 200，角色 |
| `POST /api/admin/players/{pid}/transfer` | `{ uid }` | 200，角色 |
| `DELETE /api/admin/players/{pid}` | — | 200 |
| `PATCH /api/admin/textures/{tid}` | `{ name?, type?, description? }`，至少一项 | 200，材质 |
| `POST /api/admin/textures/{tid}/unpublish` | — | 200，材质 |
| `GET /api/admin/textures/{tid}` | 查询参数 `owner`：衣柜或角色的主人 | 200，`{ tid, name, type, public, uploaderId, hash, scale, visibleToOwner }`（`scale` 供预览，尺寸认不出时为 `null`） |

- **两个读接口**：ADR-0027 的后台页面由服务端组件直接调查询服务；转让和按 tid 输入的 Dialog 要在提交之前按输入查数据，所以加两个 GET，同用户侧的 `GET /api/closet`。按"别人的材质"一节的同一个标准收紧，免得以后拆权限时比用户详情页还宽：
  - 查用户要有 `players.manage`（只有转让用它），只返回身份严格低于操作者的用户（转让也只接受这些人），其他一律 404 `user_not_found`。按邮箱查、以及返回邮箱，还要有 `users.ban`：否则只拿一个邮箱试探，也能查出它属于谁。
  - 查材质要有 `players.manage` 或 `users.manage`；`owner` 要是操作者能管理的用户，否则 403 `user_not_manageable`。别人的私有材质在没有 `textures.manage` 时只返回 `tid`、`public` 和 `visibleToOwner`。
- **写接口的形状**：每个写接口对应一个用例和一个确认框。一个 PATCH 改了几项，每项各写一条审计、各发各的事件，在一个事务里全部成功或全部回滚，同用户侧的 PATCH；页面上每个 Dialog 只提交自己的字段。连带效果大、要单独确认的操作（下架、转让、删除，以及用户的各项账号操作）各自一个接口：把它们合进一个大 PATCH，各项的权限、副作用和确认框都不同，部分失败时也说不清。
- **zod 约束**：路径和请求体里的 id 照现有接口用 `int().positive().max(2147483647)`；`delta` 是非零整数；`note` 最多 200 个字符；`description` 可以是 `null`，同用户侧。
- **新错误码**：`score_out_of_range`（400）、`admin_own_texture`（403）、`email_changed`（409）、`texture_uploader_gone`（409）。通用文案写在 `errors` 里，`admin.errors` 只是覆盖。
- **复用的错误码**不变：`email_taken`、`email_unchanged`、`user_banned`、`last_login_method`、`closet_item_exists`、`closet_item_not_found`、`texture_not_found`、`texture_type_mismatch`、`player_name_*`、`external_account_not_found` 等。它们现在的文案是对本人说的（"这个材质已经在你的衣柜里了"），所以 REST 按路径选文案：`/api/admin/` 下的接口，`admin.errors` 里有这个错误码就用它，否则用通用的 `errors`。做法同现有的按路径改错误字段名。加一个测试：`admin.errors` 的每个键都是 REST 的错误码，用到的参数是 `errors` 里同名键参数的子集。`admin.errors.texture_not_found` 要同时说得通"不存在"和"主人看不到这个私有材质"两种情况。

## 后果

- 不需要新迁移：用到的列都已经有了，`audit_logs.action` 没有 CHECK 约束。
- 领域层的重构：`deleteAccount` 的主体、衣柜移出、角色改名和换材质、材质修改（付款人、不包括谁、查重排除谁）、删启动器令牌，都抽成接收"对象"和"操作者"两个参数的函数，用户侧和后台共用，用户侧的行为不变，现有测试照常通过。新增"作废在途的登录"的函数和两个系统入口。
- 用户侧和协议的小改动：邮箱改动生效时作废找回密码链接（用户侧的确认流程和没有配置邮件时的立即生效都改），找回密码的发信回调锁住用户行后重读现在的邮箱；写第三方绑定时在锁内重新确认会话；启动器刷新令牌在锁内核对角色的主人；cdn-refresh 订阅 `player.transferred`，补测试。
- 举报页：删除用户连带结案的举报处理人是管理员，不再靠审计找回，`AdminReport.resolver` 上"仍然为 null 的是上传者自己删除"的注释照旧成立。
- `docs/schema.md`：`textures.score_paid` 的说明（见"别人的材质"）；`users.email_version` 加一的时机补上后台发起改邮箱和作废在途的登录；`verifications` 一行补上两步验证的挑战和尝试计数、"信任这台设备"、找回密码和第三方登录的暂存记录；yggdrasil_tokens 里"改密码时删令牌单独提交"一条限定为 Better Auth 的路径，后台和命令行在同一个事务里删；`device_code_selections` 的删除时机加上转让；`audit_logs.action` 的取值指向领域层导出的清单。
- SDK：`player.transferred` 和作者文档，见"事件和插件 API"。
- i18n：用户详情页、角色页、管理面板、`admin.errors`、四个新错误码、`score.reasons.adminAdjusted`、新的审计动作、通知邮件；"角色"改"身份"的几处（`admin.users.columns.role`、`errors.user_not_manageable`、审计的 `userSetRole`、插件能力说明等），e2e 里按这些文案定位的地方一起改。
- `AGENTS.md`：命令表加上两个脚本（`pnpm set-password <邮箱或 uid> [--remove-other-methods] [--email <新地址>]`、`pnpm disable-2fa <邮箱或 uid>`）；`pnpm set-role` 一行改成"设定用户的身份（`users.role`）"、`<邮箱> <身份>`；术语一行加上"身份"指 `users.role`。
- `packages/importer/MIGRATION.md`：在皮肤和披风之间标错类型的材质，现在只能删除重传。
- REST 的遍历测试（`admin.test.ts`）：按路径给出能通过 zod 的请求体和查询参数，普通用户的请求才会走到用例里的权限检查、得到 403；路由数和路径参数（`:pid`、`:pluginId`、`:providerId`）跟上；OpenAPI 的路径列表也加上。

  - 每个改动用户、角色、衣柜的操作：没有权限 403；对象是自己、同级或更高 403 `user_not_manageable`；失败时整体回滚，没有审计记录（删除用户带 `publicTextures=delete` 时，只有删账号的那个事务整体回滚）。材质见最后一条；
  - 验证状态：`expectedEmail` 和现在的邮箱不同时 409，状态不变；
  - 改邮箱：配置了邮件时发确认链接，确认之前旧地址照旧能登录和找回，确认之后版本加一、之前签发的找回链接失效；重新发起之后，前一条链接失效；对象被封禁时 403；没有配置邮件时立即生效，`verified` 生效；两个请求并发改成同一个邮箱，只有一个成功；旧地址收到通知；改邮箱和找回密码并发（造出"记录写在删除之后、提交之前"的交错），发到旧地址的找回链接都已失效；
  - 改密码：没有密码的账号插入了一行，和用户自己设置密码并发也不出 500；会话、启动器令牌、两步验证的挑战、找回链接、还没确认的改邮箱链接都失效；旧密码登录失败、新密码成功；审计里没有密码；
  - 收回账号：通行密钥和绑定全部删掉、邮箱立即换成新地址并算已验证，和设密码在同一个事务里，任何一步失败都整体回滚；对象被封禁也能做；第三方绑定的回调正在换令牌时收回账号或解绑，最终没有新的绑定；
  - 关两步验证：之后能重新开启；信任过的设备要重新过第二步；启动器的失败锁定清掉了；
  - 删通行密钥、解绑：会解掉最后一种能用的登录方式时 409，设了密码之后可以；只剩一条停用插件的绑定时也能解；之后原来的会话都失效；
  - 改积分：上下界；`delta` 为 0 或小数时 400；余额为负的用户能加分；流水之和等于余额；和用户自己的花费并发，不丢失任何一笔；
  - 删除用户：删掉的数据同删除账号；公开材质默认留下，带参数时逐个删除，中途失败之后重新提交能接着删完；举报结案、处理人是这个管理员、不发奖励，举报页显示这个管理员的昵称；每个角色、删掉的材质和结案的举报都有审计，角色的记录里有 UUID；有上千个角色、留下上万个公开材质的用户在 MySQL 上也能删除；
  - 衣柜：加入不扣分、收藏数加一；主人看不见的材质被拒绝；移出按实付退；
  - 角色：改名撞名；换材质的可见性和类型；转让后 UUID 不变、`score_paid` 为 0、原主人的私有材质清掉、两个事件里的 `player` 相同、绑定的令牌删掉、两个主人都受等级限制、原主人和新主人各有一条审计；转让和主人自己删除角色并发；转让和带 `selectedProfile` 的刷新并发，之后没有 `user_id` 是原主人、`player_id` 是这个角色的令牌；删除不退分；
  - 读接口：查用户查不到身份不低于自己的人，没有 `users.ban` 时按邮箱查不到；查材质时 `owner` 不能管理就 403；
  - 材质：管理员对自己的材质修改、下架都是 403 `admin_own_texture`，对其他管理员和超级管理员的材质可以；下架后别人的衣柜按实付退，上传者的积分和 `score_paid` 不变；价格没变的非导入材质，上传者再改回公开差额为 0，改过价格时差额等于 `score_paid` 减去现价；上传者已注销的材质能改名、不能下架；上传者注销和下架并发，结果只能是材质被删或者 409；管理员能在详情页、按上传者和 `uploader=gone` 的筛选里看到私有材质，普通用户照旧 404。
- e2e 补上：用户丢了验证器 → 管理员关掉两步验证 → 用户只用密码登录；管理员改密码 → 用户原来的会话被退出 → 用新密码登录；管理员把角色转给一个没被封禁的用户 → 按 UUID 查档案仍是同一个 UUID，CSL 照常返回材质，新主人在角色页看到它；管理员下架材质 → 别人的衣柜里没有它，管理员仍能打开详情页。
- 采纳时：ADR-0023、0024、0025、0026、0027、0030、0033、0034 的状态行和 README 的索引行注明由本 ADR 补充；`docs/schema.md`、DESIGN.md §8 照本 ADR 改；`PROGRESS.md` 的"后台的其余管理操作"标注 ADR-0036 已采纳，"第三方登录的字段核对"里"后台替用户解绑随……一起做"的半句挪过来。

## 考虑过的其他方案

- **新操作都挂在 `users.ban` 下**：封禁权限就变成了全部账号管理，以后加授权表时拆不开。
- **管理员能在后台改自己（BS 的做法）**：偷到管理员会话的人不用核对密码就能改掉这个管理员的邮箱和密码，管理员也能给自己加积分。自己的事在用户中心做。
- **后台改材质不看上传者是谁，同 ADR-0027 的删除**：管理员能把自己的公开材质下架而不付差价、不验证邮箱，等于给自己省积分。删除没有这个问题，只会少退。
- **能接管账号的操作要求刚登录过，或者再输一次管理员自己的密码**：后台里风险更大的操作（超级管理员安装插件，等于在服务器上执行代码）都不要求，只给用户管理加，前后不一致。要加就整个后台一起加，另行决定。偷到会话的情况由"能对谁做"、审计和通知邮件兜住。
- **改积分写绝对值（BS 的做法）**：覆盖并发的变动，流水对不上余额。
- **验证状态做成取反（BS 的做法）**：不幂等，两个管理员同时点会互相抵消。
- **改邮箱一律立即生效，默认不算已验证**：输错一个字母，登录名和找回密码的地址就成了别人的，这正是 ADR-0023 否决立即生效的理由；不算已验证也拦不住，Better Auth 找回密码不看它。"新地址能收信的话，用户自己就能改"也不成立：用户侧改邮箱要核对密码，忘了密码的用户自己改不了。需要立即生效的情况（旧邮箱落到别人手里）由"收回账号"处理，那里同时设了新密码，输错地址也不至于丢掉账号。
- **改邮箱保留原来的验证状态（BS 的做法）**：没人核实过的地址带着"已验证"，放开了要求验证邮箱的功能。
- **后台改密码改为发重设链接**：没有配置邮件的站点用不了，配置了的用户自己就能找回。
- **改密码不退出登录（BS 的做法）**：后台重设密码多半是因为账号失控。
- **只删会话和令牌，不管找回链接、两步验证的挑战和改邮箱链接**：这几样都不要求登录，事后照样能变成登录或者夺走邮箱。
- **账号失控时分步处理（先改密码，再删通行密钥、解绑、改邮箱）**：每两步之间，攻击者都能用还没删掉的方式登录，再加一种登录方式，或者用旧邮箱找回密码。所以有"收回账号"，一个事务做完。
- **在网页登录时重新核对密码，堵上改密码和登录并发的那几十毫秒**：每次登录多算一次 scrypt；页面上能看到剩下的会话数，再退出一次就够。
- **关两步验证只改开关**：用户之后再也开不了；信任过的设备在重新开启后仍然免第二步。
- **后台解绑、删通行密钥可以解掉最后一种登录方式**，省得管理员先编一个密码交给用户：没有登录方式的账号满足 ADR-0034 首次登录的第一步，盗号的人用同一个第三方账号再登录一次就绑定回来。
- **不提供删除通行密钥**：攻击者加的通行密钥在改密码、退出登录之后照样能登录，而且不过第二步。
- **删除用户时给连带结案的举报发奖励**：管理员没有逐个审查这些材质。
- **连带结案的举报处理人留空，靠审计记录找回是谁**：现有的举报页把审计找回的处理人当作已注销的用户；审计过了保留期，又退回"上传者自己删除"。
- **删除用户时公开材质一律留下**：清理刷屏账号时会留下几百个"已注销"的公开材质，BS 的列表会把它们藏起来，这里不会。
- **公开材质和账号在同一个事务里删除，整体回滚**：几百个公开材质各要找引用者、退款、发事件，SQLite 的全局写锁会被占太久。
- **删除用户只写一条审计，连带删掉的材质和结案的举报不另记**：举报页会把这些举报说成"上传者自己删除"，按材质也查不到它是怎么没的。
- **角色的操作以角色为对象（新的对象类型 `player`）**：从用户出发排查时看不到；角色转走或删掉之后，拿不到 pid。
- **转让时退还原主人的实付，或者让实付跟着角色走**：前者让一次管理操作凭空多出积分，转让又常常是在处理纠纷；后者让新主人删掉角色时拿回别人付的钱（ADR-0022）。需要时用"改积分"补偿。
- **转让不发事件**：按 uid 维护数据的插件无从知道。**发 `player.deleted` 加 `player.created`**：pid 和 UUID 都没变。
- **转让时材质照旧（BS 的做法）**：原主人的私有材质通过新主人的角色公开出去。
- **后台换材质要求在主人的衣柜里**：管理员就得先往别人衣柜里加东西，多一步，也没有保护到什么。**任何存在的 tid（BS 的做法）**：泄露私有材质，槽位和类型对不上。
- **后台删除角色退还实付**：后台删角色多半是因为违规，同 ADR-0027 不退管理员删除的材质的存储费。
- **管理员改公开状态时按现价向上传者多退少补（BS 的做法）**：会因为上传者余额不够而失败，上传者已注销时没有人可以收费。
- **管理员能把别人的私有材质改成公开（BS 的做法）**：公开与否是上传者对自己内容的决定。
- **管理员完全豁免可见性，能把别人的私有材质加进自己的衣柜、设到自己的角色上（BS 的做法）**：衣柜、角色、头像里会出现持有者看不见的材质，清理流程和衣柜列表都不这样假设；管理员被撤职后，这些东西的状态也说不清。
- **皮肤库对管理员混列全部私有材质（BS 的做法）**：查询要带 OR 条件，用不上索引（ADR-0025）。按上传者筛选就够了。
- **往别人衣柜里加材质按现价扣主人的积分**：主人没有要这件东西。**不改收藏数（BS 的做法）**：收藏数和衣柜对不上。
- **一个大的 `PATCH /api/admin/users/{uid}` 收下所有字段**：见"接口"。
- **先做 Sheet，在侧边编辑用户**：要先补组件、story 和截图基线；每次只改一项的操作用 Dialog 就够。
