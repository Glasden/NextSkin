# ADR-0024 改邮箱的确认链接按邮箱版本作废（修正 ADR-0023）

- 状态：已采纳（后台发起改邮箱、作废在途的登录时版本也加一，由 ADR-0036 补充）
- 日期：2026-10-18

## 背景

ADR-0023 的确认链接不落库，只靠确认时的条件 `where id = ? and email = 旧邮箱` 保证"同一个链接只能生效一次"。实现之后的独立核查在四种数据库上复现了一个反例：

1. 签发并确认 A→B 的链接；
2. 再把邮箱改回 A（确认另一条 B→A 的链接，或者没有配置邮件时直接修改）；
3. 一小时之内再提交第 1 步的链接，又成功了，邮箱再次变成 B，并且标记为已验证。

"当前邮箱等于旧邮箱"这个条件可以重新成立，所以挡不住重放。确认接口不要求登录，拿着那封邮件的人就能把登录和找回密码用的地址再改回去。例如用户把邮箱错填成别人的地址、发现后改回来，那个地址的主人在一小时内仍能把账号的邮箱改走。

## 决定

- `users` 加一列 `email_version`：整数，非空，默认 0。邮箱每改一次就加一，包括确认链接、没有配置邮件时的直接修改，以及以后后台修改用户的邮箱。
- 令牌的载荷加上签发时的 `email_version`。确认时的条件改为 `where id = ? and email = 旧邮箱 and email_version = 令牌里的版本`，同一条 UPDATE 把版本加一。确认页的预览按同样的条件判断。
- 版本只增不减：用过的链接，以及邮箱改过之后再拿出来的旧链接，都永久失效。
- ADR-0023 的其余部分不变：令牌本身仍不落库，1 小时内有效，确认页上点按钮才提交。

## 后果

- 新迁移给 `users` 加 `email_version`。导入器写 0：BS 的邮箱修改立即生效，没有待确认的链接需要延续。
- 修改用户邮箱的地方都要给版本加一，否则改动之前签发的链接仍然有效。现在只有改邮箱的领域用例会改邮箱；以后后台的用户管理改邮箱时，也要加一。
- 同一个旧邮箱下签发的几条链接，第一条确认之后其余全部失效，这一点与 ADR-0023 相同。

## 考虑过的其他方案

- **待确认的修改记进 Better Auth 的 `verifications` 表，确认时删掉**：页面上还能显示"待确认的新邮箱"。但领域用例要直接写 Better Auth 的表（ADR-0015 不鼓励），确认也分成 Better Auth 的消费和我们的事务两步，消费之后事务失败，链接就白白作废了。
- **令牌里带 `users.updated_at`**：改昵称、开关两步验证都会改它，待确认的链接会莫名其妙地失效。
- **用时间戳 `email_changed_at` 代替计数**：同一毫秒内的两次修改会得到同一个值，作废条件又可能重新成立。
