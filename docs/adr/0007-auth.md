# ADR-0007 认证：Better Auth + 自写 Yggdrasil 令牌体系

- 状态：已采纳（S1 已通过，见 `spikes/s1-better-auth/README.md`；Connect 的端点、页面、声明和 scope 错误的重定向由 ADR-0037 补充，"创建 OAuth 客户端需要管理员会话"一句已被 ADR-0037 取代）
- 日期：2026-10-16

## 背景

需要的能力：

- 邮箱或角色名登录、找回密码、邮箱验证、记住我、验证码、限流；
- 两步验证、通行密钥（新增）；
- 第三方登录；
- 作为 OAuth/OIDC 授权服务器，服务第三方应用和 Yggdrasil Connect（基于 OIDC，需要设备授权流程，申请 `Yggdrasil.PlayerProfiles.Select` 时访问令牌必须绑定到用户选择的角色）；
- Yggdrasil 协议本身的令牌（accessToken/clientToken）。

BS 的密码可能是多种算法（取决于站点配置），还可能来自 AuthMe 等外部系统。

## 决定

- 网页登录体系使用 **Better Auth**（基于 Kysely，支持三种数据库；锁定 1.7.x）。
- OAuth/OIDC 授权服务器使用 **`@better-auth/oauth-provider`**，加上 `oauthDeviceAuthorization`。Yggdrasil Connect 部分作为我们自己的一个 Better Auth 插件实现。S1 已验证其全部必选能力。
- 必须遵守的配置：
  - `database.transaction: true`（默认是 false，多步写入不在同一个事务里）；
  - `advanced.database.generateId: 'serial'`；
  - 用户表主键列名只能是 `id`（Better Auth 不允许改名），对外 DTO 仍叫 `uid`；
  - ID 令牌用 RS256 签名（`jwt` 插件的 `keyPairConfig.alg`）；
  - 访问令牌和刷新令牌用我们指定的 `storeTokens.hash`（sha256）存储。
- **角色绑定**：所选角色编码为 consent 的 `referenceId`（`player:<pid>`）。
  - 授权码流：申请 Select 时强制进入同意页，在同意页上选择角色，同意请求带上所选 pid。consent 的 before 钩子在同一个请求里完成：校验最终接受的 scope、校验角色归属、写入角色。
  - 设备流：在批准页上选择，选择按 `device_code` 字符串记录，只允许在待批准状态下由认领者选择或更改，兑换或拒绝后删除。签发令牌时包装内置的 device_code grant，补上 `referenceId`。
- **scope 组合规则**必须在所有入口校验：authorize（GET 和 POST 表单）、consent 的 scope 子集、device/code、refresh 的 scope 参数。
- **公共客户端每次都要征求同意**：在外部发起的 authorize 上强制 `prompt=consent`；客户端带 `prompt=none` 时返回 `consent_required`。
- **会话服务器（进服）校验**：按令牌哈希直接查表，不走 introspection。必须同时满足：带 `Yggdrasil.Server.Join`、已绑定角色、角色此刻仍归属于令牌的用户、客户端未被禁用。
- **旧的 Yggdrasil 用户名密码令牌**（authserver）自己实现，并修复旧插件的已知问题：越权上传材质；邮箱大小写导致刷新后的令牌失效。它与 OAuth 令牌体系是否统一，在实现阶段决定。
- **旧密码兼容**：BS 支持的各种算法在核心内置校验器；外部系统格式由插件通过 PasswordHasher Provider 提供。任何一次校验成功后，立刻用当前算法重新哈希。注意 Better Auth 把密码存在 `account` 表里，导入器要写入那里。
- 会话存在数据库中，Cookie 设置 HttpOnly、Secure、SameSite=Lax。

## 后果

- 有一处依赖 Better Auth 未公开的内部结构：`oauthDeviceAuthorization().options.grant.grants`。升级 Better Auth 时必须跑 S1 的场景测试，并向上游提议在设备流里传递 `referenceId`。
- Better Auth 在同意或继续之后，会以 `/oauth2/authorize` 路径在内部重新调用 authorize，同样会触发 before 钩子。我们的钩子必须按请求 URL 区分外部请求和内部续跑。
- `consentReferenceId` 拿不到当前授权请求的上下文，所以"每个授权流程各自的选择"只能在同意请求里完成。不要改回"选择存进 session、同意时再读"的做法：同一用户的并行流程会串用对方的选择。
- scope 校验失败时目前返回 JSON 400，而不是重定向回 `redirect_uri`，与 RFC 6749 §4.1.2.1 有出入，实现阶段再处理。
- 启动器客户端要注册为 `application_type: 'native'` 才能使用回环地址回调；创建 OAuth 客户端需要管理员会话。

## 考虑过的其他方案

- **Auth.js**：不提供 OAuth 授权服务器能力。
- **全部自研**：两步验证、通行密钥、第三方登录各自都是容易出安全问题的大块工作。
- **panva/oidc-provider**：经过认证、非常成熟（BS 官方的 Janus 就用它），但基于 Koa 和 Node 的原生请求对象，很难挂进同一个进程里的 Hono/Next；Janus 也只支持 MySQL。
- **用 postLogin 页面选择角色、把选择存在 session**：S1 第一版就是这样做的，审核发现同一用户的并行授权流程会串用选择，已放弃。
