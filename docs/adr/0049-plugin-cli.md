# ADR-0049 命令行管理插件：`nextskin plugin` 调用后台的同一组用例，操作者是 system；服务运行时也能执行，SQLite 上的插件锁改成跨进程的文件锁

- 状态：已采纳
- 日期：2026-10-21
- 取代 ADR-0039 里"`plugin` 命令推迟"一节
- 取代 ADR-0033"多实例"里"SQLite 只有一个进程，用进程内的锁"一句：SQLite 上改用数据库文件旁边的锁文件
- 补充 ADR-0033"安装、升级和卸载"：命令行的入口、确认方式和运行中的服务怎么接上

## 背景

ADR-0039 推迟 `plugin` 命令的三条理由：

1. 后台的插件页已经够用；
2. 插件不会把管理员锁在外面，超级管理员可以用 `set-password` 找回；
3. 在 SQLite 上，插件管理操作的锁是进程内的锁，另一个进程改插件的状态会绕过它。

第 1 条在实际运维里不成立。在 nya 上把 QQ 绑定插件升到 1.0.1 时，站长手边没有超级管理员的会话，只好临时注册一个账号、`set-role` 成超管去上传，用完再降级注销。服务器上的人本来就能读 `.env` 和数据库，绕一圈后台只多了一个临时的超管账号。

第 3 条是真问题，命令行要和运行中的服务共用一个 SQLite 文件，就得先解决它。另外还有两处只在两个进程之间才会出事：

- **解开的插件包会被服务清理掉**：服务每 5 秒同步一次，顺带删掉插件目录里自己不认识的包目录。刚解开的目录只在解开它的那个进程的内存里记着"新鲜"（10 分钟内不删），命令行解开的目录对服务来说就是不认识的，下一次同步就可能被删，这时命令行正要拉起 host 加载它。
- **命令行不运行安装插件**：`openCore` 不传 host，启用安装插件、升级启用中的插件都要先在新一代 host 里加载、跑迁移（ADR-0033），命令行里做不了。

## 决定

### 命令

| 命令 | 说明 |
|---|---|
| `plugin list` | 列出官方插件和安装插件：id、版本、来源、是否启用、最近的错误、死信数、本实例取不到插件包 |
| `plugin install <插件包> [--yes]` | 安装或升级（按表里有没有这个 id）。先列出和后台预览相同的内容，需要确认的时候确认 |
| `plugin enable <id>`、`plugin disable <id>` | 启用、停用。已经是这个状态时说明没有改动，退出码 0 |
| `plugin uninstall <id> [--yes]` | 卸载。官方插件只能停用 |

- 调用后台的同一组领域用例（`createPluginAdmin`），每个用例多一个 `…AsSystem` 的入口：不查权限，审计的操作者是 system，IP 为空，和 `set-role`、`maintenance` 一样。能以运行服务的用户执行命令的人，本来就能读 `.env` 和数据库。
- 依赖、冲突、版本只升不降、官方插件的 id 不能占用、迁移失败不启用，这些检查都在用例里，和后台一致。
- **确认**：
  - 安装和升级先打印后台确认框里的内容：名字、id 和版本，信任提示，高风险项，升级时新增的能力和出站地址、去掉的登录方式，"这个插件会做什么"的每一项。
  - 要确认的情况：第一次安装；升级时多了能力、出站地址或高风险项，或者去掉了登录方式。升级没有这些变化时直接升级，和后台不再要求重新确认的范围一致（ADR-0033"升级"）。比较用的是本实例上的 manifest，它不是装着的那个包时（本实例取不到装着的包，或者它刚被别人升级、还没同步）比不出新增了什么，也要确认。
  - 要不要确认是按预览时装着的包决定的：预览之后插件被别人装上、升级或卸载了，安装按冲突处理（报"正忙"），不按新的状态继续，否则一次不用确认的升级可能变成没确认过的第一次安装。后台不同：管理员在确认框里看过全部内容，确认时按那时的状态安装或升级。
  - 卸载总要确认：数据表、KV、设置都会删掉，不能恢复。确认前列出名下的第三方账号绑定数，以及卸载后没有别的登录方式的用户数。绑定数按插件 id 数，和卸载删的是同一批，包括新版本去掉的登录方式留下的绑定（后台的卸载确认也改成这样数）。命令行不运行安装插件，算"别的登录方式"时按服务上的情况：已启用、包在本实例上的就算能用。
  - `--yes` 跳过确认。不在终端里运行（stdin 不是 TTY）又要确认、没有 `--yes` 的，拒绝执行。
  - 启用、停用不确认：命令本身就是确认。启用要用高风险能力的插件时，照样打印一行高风险项。
- **输出**照 ADR-0039 直接写中文。能力、拦截点、Provider 的名称和信任提示读 `packages/i18n` 里后台已有的中文文案，不另写一份：新能力加了文案，命令行就跟着显示。命令行自己的句子不进 i18n。
- 退出码：成功 0；参数错误、用例拒绝、取消、失败 1；配置错误 78（ADR-0039）。

### 服务运行时执行

命令行和运行中的服务通过三样东西接上，都已经是多实例部署时实例之间的做法（ADR-0033"多实例"）：

- **插件表**：服务每 5 秒读一次启用集合，和当前这一代不同就自己换代。命令行改完表，服务最多 5 秒后跟上。
- **插件包的存储接口**：命令行把包存进同一个存储（同一个数据目录下的 `plugin-packages`），服务取得到。
- **插件目录**：命令行和服务用同一个数据目录，命令行解开的目录服务直接用，不再解一遍。

需要改的三处：

- **命令行的 host 只用来准备**：`openCore` 多一个选项，命令行传 host 的入口、模式是 `stage`。这个模式下：
  - 同步时不拉起 host、不运行安装插件，也不清理插件目录（服务可能正在用命令行不认识的目录）；
  - 启用安装插件、升级启用中的插件时，临时拉起只有这个插件的一代：确认加载得了、manifest 对得上，在里面跑迁移，提交改动之后杀掉。之后由运行中的服务按表换代；服务没有运行的，下次启动时加载。
  - 不和别的已启用插件一起加载：命令行不会切换到这一代，一起加载只是多花时间。服务换代时的组合加载失败，和多实例时别的实例起不来一样，后台的插件页显示 host 的错误。
- **刚解开的目录跨进程也不清理**："新鲜"改按包目录里标记文件的修改时间判断，10 分钟内不删；安装、升级时用到已经解开的目录，先更新它的修改时间。清理不拿插件的锁：安装拿着锁调用同步，同步里的清理再拿锁会排在自己后面。清理先把目录改名挪开，再查一次修改时间，刚被用上的挪回来；用到已解开的目录的一方更新修改时间时发现它被挪开了，就重新解开一份。挪回失败时，只有那边已经重新解开了一份才删；挪开了没删掉的过了新鲜期再删；空了的插件目录不递归删。挪开到挪回之间只隔几次文件操作，那边恰好在这时加载会失败，重试即可：这个窗口不靠锁关不掉，而在 10 分钟的界限上复用一个旧目录本来就少见。
- **SQLite 上的插件锁跨进程**：`withExclusiveLock` 在 SQLite 上改用锁文件，放在数据库文件旁边的 `<库文件>-locks/` 目录里，每个锁名一个文件（文件名取锁名的 sha256）。拿锁就是用 `node:sqlite` 打开它、开一个排他事务，拿不到立即报忙；放锁就是回滚、关掉。和数据目录的锁（ADR-0039）是同一个办法：进程不论怎么退出，操作系统都会释放，不会留下要手动删除的锁。锁文件不删，每个插件 id 留一个空文件。

命令行不跑后台任务（`startJobs: false`），卸载登记的清理任务由服务在 12 分钟后执行；服务没有运行的，下次启动后执行。

### 不在这一版

- **插件设置**：机密项要在终端里不回显地输入，非机密项要按 JSON Schema 解析命令行参数，还要交给插件按它自己的 schema 校验。等有需要再加。
- **死信**：后台的插件页已经能重试、删除，也不会在后台进不去的时候才要处理。
- **重启 plugin host**：host 是服务进程拉起的，崩溃次数记在服务进程的内存里，命令行碰不到。要重启就重启服务。

## 后果

- 正式部署里第一次能在没有超级管理员会话时安装、升级、启用、停用、卸载插件，也能写进部署脚本（`--yes`）。
- 启用、升级安装插件时，命令行要拉起一个 plugin host，发行目录里要有完整的 `server/`（`doctor` 已经检查它）。
- SQLite 的数据库文件旁边多一个 `-locks` 目录。
- 后台和命令行同时操作同一个插件时，后拿锁的一方报"正忙"，和多实例时一样。
- 命令行启用之后，插件在服务上真正运行要等下一次同步（最多 5 秒）；命令行看不到服务换代成功与否，要看后台的插件页或服务的日志。

## 考虑过的其他方案

- **命令行经运行中的服务执行**（管理接口、本机 socket）：服务停着、起不来的时候用不了；多实例部署时也说不清该连哪个实例。ADR-0039 否决过同样的做法。
- **命令行照服务的做法运行全部已启用的安装插件**：拉起的一代命令行用不上，退出时就杀掉，还要在命令行进程里运行全部插件的代码。
- **命令行只改表，迁移留给服务同步时跑**：迁移就从"处理管理员操作的那个实例在启用之前跑完"（ADR-0033）变成每个实例同步时都可能去跑，要再加一层互斥；迁移失败时命令行也没法告诉执行它的人。
- **SQLite 上用表里的一行做锁**：进程被强制结束后锁留在表里，要估计租约多长。ADR-0039 否决 pid 文件也是这个原因。
- **命令行拿数据目录的锁 `nextskin.lock`**：`start` 运行期间一直拿着它，服务运行时命令行就不能执行了。
