# ADR-0017 皮肤的 2D 正背面由服务端出图，浏览器只做整数倍放大

- 状态：已采纳
- 日期：2026-10-17

## 背景

SkinFigure（DESIGN.md §6）显示材质的 2D 正面和背面，用在材质卡片（×3、×4）、领奖台（×5）和登录页插图（×8）里。鼠标移上去或键盘聚焦时，角色分四格转到背面。

正背面要从材质里拼出来，每一步都要读写像素：
- 把各个面切下来，外层叠在内层上；
- 旧版 64×32 皮肤用右手右腿的镜像补左边；
- 照游戏客户端的规则，把基础层强制设为不透明，并处理旧版的帽子层。

S4 在服务端实现并验证了这些规则（`preview2d`，有黄金图），ADR-0008 也已经规定了渲染结果的缓存键。视觉样稿走的却是另一条路：在浏览器里用 canvas 拼。

两条路都能出图，区别在于：
- 组件需不需要 JS；
- 出图地址和缓存怎么设计；
- 高清皮肤传多大的图；
- 插件、邮件能不能用同一张图。

约束有四条：
- 默认部署在 1 核 2G、带宽很小的服务器上（ADR-0002）；
- 材质可能放在 S3 或 CDN 上（ADR-0002）；
- 材质不经过 `next/image`（不变量 8）；
- 材质只做整数倍缩放（DESIGN.md §5）。

## 决定

### 出图

- 2D 正背面由服务端渲染。正面和背面左右拼成一张 PNG：皮肤是 32×32 个标准像素，披风是 20×16。一张材质只发一个请求。
- 渲染规则与 S4 相同（ADR-0008）：旧格式补全、基础层强制不透明、旧帽子层修正。模型（经典或纤细）取材质条目的 `type`，不重新推断。
- 分辨率用 k 表示：一个标准像素在图里占 k×k 个像素。s 是材质的倍数（宽度 ÷ 64），k 取 s 的约数。k 小于 s 时，从原图按 s/k 的整数比例取最近邻。
- 页面用 `srcset` 给出 1x、2x 两档。设显示倍数为 N，每一档取能整除"N × 设备像素比"的最大 k。这样浏览器只放大、不缩小，而且放大倍数都是整数。
  - 普通皮肤 s = 1，只有 k = 1 这一种。S4 的 6 张真实皮肤，出图在 0.3–2 KB 之间，都比原图小。
  - 高清皮肤按需要的清晰度出图。以 S4 用的那张 512×256 高清皮肤为例（s = 8，原图 112 KB）：
    - 卡片（×4）在 2x 屏上取 k = 8，像素一一对应，图 52 KB；
    - 领奖台（×5）取 k = 1 或 2，图 2–6 KB。DESIGN.md §5 里"高清皮肤放到领奖台不行"的情况，这样也能显示。
- 渲染函数写成不依赖 Node 的纯函数，只读写 RGBA 类型化数组，放进一个新包（暂名 `packages/skin`）。
  - 服务端的图像 worker 用它出图。
  - 浏览器在上传页也用它：推断模型，给还没上传的本地文件出预览。
  - PNG 的解码和把关仍然只在服务端做（ADR-0008）。

### 地址和缓存

- 出图地址包含缓存键的全部内容：材质 hash、模型、k、渲染器版本。具体路径随实现定。响应头是 `Cache-Control: public, max-age=31536000, immutable`。
- 渲染输出有变化时（修 bug、调规则），升渲染器版本。地址跟着变，浏览器和 CDN 不用清缓存；旧版本的缓存文件整批删掉。
- 渲染结果存进 ADR-0002 的缓存接口：默认放本地磁盘，多实例部署时可以换成 S3 驱动。这些文件随时可以重建，所以不进数据库，也不参与 `texture_files` 的认领和引用计数。
- 生成时机：
  - 上传时，worker 手里已经有解码好的像素，顺便生成常用的几种 k，预热缓存；
  - 导入的旧材质、升版本后的所有材质，都在第一次被请求时生成；
  - 同一个键的并发请求合并成一个生成任务。
- 访问控制与 `/textures/{hash}` 相同：知道 hash 就能取。私有材质的原图本来就能按 hash 取到，出图不会多泄露什么。

### 组件

- SkinFigure 只接收出图地址、替代文字、显示倍数和材质倍数，用 `<img>` 显示，不读像素。
- 转身用 CSS 实现：正面那半边按 `steps(4)` 横向缩到 0，再展开背面那半边。开启"减少动态效果"时不转。
- 组件里没有 hook，可以在服务端渲染，不需要 `'use client'`。
- 本地文件的预览：把浏览器端出图得到的 blob URL 传给同一个组件。

### 插件

- 声明式插件界面由核心在服务端渲染（ADR-0011），可以直接放 SkinFigure。邮件模板和社交平台的分享图（Open Graph）也能引用同一套地址。
- 渲染不开放拦截点。缓存键里只有核心的渲染器版本；如果允许插件改变出图结果，缓存键就得带上插件的版本和配置，到时另写 ADR。
- 插件 SDK 的材质 DTO 将来要提供出图地址时，按插件 API 变更的流程走（不变量 9）。

## 后果

- **组件要等渲染代码。** SkinFigure 依赖服务端出图，所以先把 S4 的渲染代码移植进 `packages/skin`，再做组件。移植时按无分配的方式写，并带上黄金图测试。
- **Storybook 用预先生成的图。** Storybook 和截图测试用的出图，由脚本从固定的测试材质生成并提交，做法和字体分片一样。
- **不用等水合。** 首屏 HTML 里就有图片地址；列表页的卡片可以加 `loading="lazy"`。
- **2D 预览不要求 CORS。** 浏览器不需要读材质的像素，所以材质放在 S3 或 CDN 上时，2D 预览不要求它们配 CORS。3D 预览（skinview3d 用 WebGL）仍然要求，这一条要写进部署文档。
- **渲染器版本要认真维护。** 输出变了却忘了升版本，浏览器和 CDN 会一直拿旧图。黄金图变了而版本号没变时，测试要失败。
- **空站点要自带一张皮肤。** 登录页插图用站内的哪张材质，由页面决定。空站点需要一张随核心发布、版权归项目的皮肤，不能用 Mojang 的 Steve 和 Alex。它的出图同样由脚本生成。
- **多一个公开的图片端点，要防滥用。** 做法和 `/textures/{hash}` 一样：
  - hash 格式不对、k 不是 s 的约数、模型未知时，直接返回 404；
  - 生成任务进 ADR-0008 的 worker 池，排队有上限。

## 考虑过的其他方案

- **在浏览器里用 canvas 拼（视觉样稿的做法）**：不需要服务端接口，本地文件也能直接用，所以上传页保留这种用法。缺点：
  - 组件要等水合之后才有图，列表页一屏二十多张卡片会先空着；
  - 邮件、分享图和不执行 JS 的场景都用不了；
  - 读像素要求材质所在的 S3 或 CDN 配 CORS，否则画布被污染，取不出像素；
  - 高清材质要整张下载；
  - 游戏客户端的预处理要么在浏览器里再实现一遍，要么把渲染包发给每个页面；
  - 样稿就漏掉了"基础层强制不透明"。
- **CSS 切片**（每个身体部位一个元素，用原始材质作背景并定位）：不需要 JS，也能在服务端渲染。缺点：
  - "基础层强制不透明"和旧帽子层规则取决于像素，CSS 做不到；
  - 一个人物要二三十个元素；
  - 设备像素比不是整数时，部位边缘会采样到相邻部位的像素。
- **正面、背面分成两张图**：请求数和缓存条目都翻倍。S4 的 `preview2d` 也是拼成一张。
- **出图写进材质存储，跟着材质一起管理**：要并进 `texture_files` 的认领和删除流程；升渲染器版本时，还得把所有材质的派生文件批量重写一遍。当作随时可丢的缓存要简单得多。
- **一律发原始分辨率，由浏览器缩小**：
  - 小服务器的带宽本来就紧张，上面那张高清皮肤放在领奖台上，要多传 9 到 29 倍的数据；
  - 缩小时留下哪个像素由浏览器决定；
  - 比例不是整数时，像素会宽窄不一，违反 DESIGN.md §5，比如高清皮肤放到领奖台是 0.625 倍。
