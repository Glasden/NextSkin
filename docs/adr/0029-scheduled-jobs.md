# ADR-0029 定时任务：job_schedules 记下算出下次执行时间用的 cron 和时区；第一批条目清理过期的认证数据、按保留期清理审计日志、回收存储里的孤儿文件

- 状态：已采纳
- 日期：2026-10-18
- 取代 ADR-0021"定时任务"一节里 `job_schedules` 只有两列、改时区时重新计算的做法，该节的其余部分不变

## 背景

ADR-0021 定了定时任务的机制，留到"第一个定时任务"落地：
- `job_schedules` 表，列是 `name`、`next_run_at`；
- 执行器每 30 秒检查一次，用条件 UPDATE 把 `next_run_at` 推到下一次，影响 1 行才入队，去重键用条目名。停机期间错过的只补跑一次，上一次没跑完不叠加；
- cron 表达式按站点时区（`site.timeZone`）解释，用一个纯 JS、支持时区的解析库；站点时区改了以后重新计算 `next_run_at`。

等着它的事：
- 材质存储里的孤儿对象（存储里有、`texture_files` 里没有行）要遍历整个存储才找得到（schema.md、ADR-0025）。schema.md 已经定了回收方式：先插一条 `deleting` 行认领，再走正常的回收流程；遗留的临时文件直接删除。
- 审计日志的保留期（ADR-0027）：现在不自动清理，说好等定时任务落地后再加设置项。
- 插件 SDK 已经有 `cron` 字段（`define.ts`）：每项是五段 cron 表达式、任务名和可选的载荷，按站点时区解释。

还有一件文档里没有记、查代码时发现的事：认证表里的过期行没有人删。
- Better Auth 1.7.10 只在两处删除过期数据：查验证值时顺手删掉 `verifications` 里全部过期的行；过期的会话被带回来时，删掉这一行。除此之外，Better Auth 和 oauth-provider 里没有按过期时间删除的地方。
- 用户再也不回来，他的过期会话就一直留着。OAuth 的访问令牌只在用刷新令牌换新令牌时删掉旧的；刷新令牌、设备码、客户端断言（client assertion）过期后都留在表里。
- 接下来的 Yggdrasil 切片还要加一张令牌表（schema.md），同样要按过期时间清理。BS 把 Yggdrasil 令牌放在带 TTL 的缓存里，没有这个问题；放进数据库就有了。

还没定的：第一批条目做什么；条目在哪里声明；`job_schedules` 怎么跟上 cron 表达式和时区的变化；遍历整个存储这种长任务怎么切分；用哪个 cron 库。

## 决定

### 范围

这次做：
- `job_schedules` 表和调度器；
- 三个核心条目，见"第一批条目"；
- 设置项 `audit.retentionDays`；
- 材质存储接口加一个列出对象的方法。

不做：
- 插件的定时任务：随插件运行时做。调度器只认"条目名、cron 表达式、任务名、载荷"四样，插件条目怎么命名到时再定。
- 后台查看条目（上次、下次执行时间）和手动触发：需要时随失败任务页一起做。
- 清理长期没有验证邮箱或不活跃的账号：BS 没有这个功能。删用户是不可逆的业务决定，不是维护任务。

### 条目的声明

核心条目写在代码里，每一项有四个字段：

| 字段 | 说明 |
|---|---|
| name | 条目名，也是 `job_schedules` 的主键和入队时的去重键。核心条目以 `core:` 开头 |
| cron | 五段 cron 表达式 |
| job | 到时入队的任务名，必须有注册的处理函数 |
| payload | 入队的载荷，可选 |

- 只接受五段表达式，与 SDK 相同。注册时校验：段数不对、解析不了、或者算不出下一次执行时间（例如 `0 0 30 2 *`）的，直接报错。核心条目由测试守着，插件条目在安装时校验。
- 日和星期两段都限定时，按 Vixie cron 的惯例取"或"：任一满足就执行。
- 条目的任务和普通任务一样重试、进死信，下一次触发不受影响。

### job_schedules

| 列 | 类型 | 说明 |
|---|---|---|
| name | varchar(128) | 主键 |
| cron | varchar(255) | 算出 `next_run_at` 时用的表达式 |
| time_zone | varchar(64) | 算出 `next_run_at` 时用的时区 |
| next_run_at | 时间 | 下一次执行的时间 |

比 ADR-0021 多两列。`next_run_at` 是在某个时区按某个表达式算出来的，这两样都可能变：
- 管理员改了站点时区；
- 核心升级或插件更新改了条目的表达式。

记下算出它时用的值，调度器每次检查都能发现不一致，自己重新计算。设置的写入用例里不用加钩子，ADR-0021 没有考虑到的第二种情况也一并解决了。

### 调度器

- 和任务执行器一起启动、停止。命令行脚本调用 `openCore({ startJobs: false })`，两样都不启动。
- 每 30 秒用读连接读一次整张表（行数就是条目数），只处理本实例注册了的条目：
  1. 表里没有的条目：用 `insertOrIgnore` 插入一行，`next_run_at` 取从现在起的下一次。
  2. `cron` 或 `time_zone` 和当前的不一致：用条件 UPDATE 按当前的表达式和时区，从现在起重新计算，三列一起改，条件带上读到的旧值。这一轮只重算，即使已经到期也不触发。
  3. 到期的（`next_run_at <= 现在`）：在一个事务里用条件 UPDATE 把 `next_run_at` 改成从现在起的下一次，条件带上读到的旧值；影响 1 行，就在同一个事务里入队，去重键是条目名。
- 下一次总是从"现在"算，不从旧的 `next_run_at` 算，所以停机期间错过的只补一次。
- 入队被去重键挡下（上一次还没跑完）时，`next_run_at` 照样推进，这一次就跳过了。
- 本实例没有注册的条目不动。停用插件的条目留在表里，重新启用后，过期的 `next_run_at` 让它马上补跑一次。核心升级以后不再存在的 `core:` 条目，启动时删掉。卸载插件时删掉它的条目（随插件运行时）。

夏令时交给解析库，语义是：
- 春季拨快时跳过的时刻，顺延到跳过之后执行一次；
- 秋季拨慢时重复的时刻，只在第一次执行。

### 长任务：分页续跑

- 一次执行只处理一页，处理完把游标和累计的计数放进载荷，入队下一页。每页的写入都是短事务，SQLite 上不会长时间占着写锁，也碰不到执行器 60 秒的超时。
- 续跑的任务沿用条目名作去重键：一轮还没走完，下一次触发就被挡下，不会叠加。做法同 `core:texture-recycle`：正在执行的任务先清掉自己的去重键，再在同一个事务里入队下一页。
- 删除也分批：每批先查出最多 1000 个 id，再按 id 删除，一批一个事务。MySQL 不支持在 `IN` 子查询里用 `LIMIT`，所以不写成一条语句。

### 第一批条目

| 条目 | cron | 做什么 |
|---|---|---|
| `core:auth-cleanup` | `17 4 * * *` | 删除过期的会话、OAuth 令牌、设备码 |
| `core:audit-log-cleanup` | `27 4 * * *` | 按保留期删除审计日志 |
| `core:texture-sweep` | `47 4 * * 0` | 回收材质存储里的孤儿对象和遗留的临时文件 |

- 都是维护任务，处理函数的并发上限是 1。
- 时刻避开 0 点到 4 点：多数地区在这段时间切换夏令时。分钟也不取 0，错开常见的整点备份。

#### core:auth-cleanup

删除过期超过 1 天的行：

| 表 | 条件 |
|---|---|
| sessions | `expires_at` |
| oauth_access_tokens | `expires_at` |
| oauth_refresh_tokens | `expires_at` |
| oauth_client_assertions | `expires_at` |
| device_codes | `expires_at` |
| device_code_selections | 创建超过 1 天，且对应的设备码已经不在 |

- 多留 1 天，是为了不和正在处理的请求、不和实例之间的时钟偏差抢。
- 撤销了但还没过期的刷新令牌不删：oauth-provider 靠它发现令牌被重放，重放时作废整组令牌。过期以后，重放本来就会被拒绝。
- `verifications` 不在里面：Better Auth 每次查验证值都会删掉全部过期的行。
- 这几列都是 Better Auth 的日期列（ADR-0015），条件里的时间用 `writeAuthDate` 转换。
- 不给 `expires_at` 加索引：清理以后表里只剩没过期的行，每天扫一遍很便宜。
- Yggdrasil 切片的令牌表加进这个条目，不另设条目。

#### core:audit-log-cleanup

- 新设置项 `audit.retentionDays`：0 到 3650 的整数，0 表示永久保留，默认 0，放在 `advanced` 分区。默认值保持 ADR-0027 的行为，升级之后不会有记录被删掉。
- 大于 0 时，删除 `created_at` 早于保留期的记录：按主键从小到大分批，遇到不早于截止时间的行就停。`id` 和 `created_at` 大体同序，不为 `created_at` 另建索引。并发事务插入的先后可能和时间差一点，个别行晚一天删，无所谓。
- 清理本身不写审计记录。

#### core:texture-sweep

- 存储接口加一个列出对象的方法：按键名升序分页，返回键名和修改时间。S3 的 ListObjectsV2 本来就这样分页；本地磁盘读出目录再排序。
- 文件名不是材质 hash（64 位小写十六进制）的跳过，不删：本地目录里可能有服主自己放的文件。
- **孤儿**：修改时间早于 1 天、`texture_files` 里没有行的对象，按 schema.md 回收。插入一条 `deleting` 行认领，插入时发现已经有行，说明不是孤儿，跳过；同一个事务里排回收任务。之后和普通回收一样，等 D（1 小时）再删对象、删行。修改时间只用来挑候选，互斥靠插入的那一行。
- **临时文件**（只有本地磁盘有）：按 schema.md，文件名里的 `claim_id` 已经不是这个 hash 的 `pending` 行的当前认领、修改时间又早于认领租期（10 分钟）的，直接删除。
- 一轮结束记一行日志：回收了几个孤儿、删了几个临时文件。孤儿只会来自手工改动存储或程序缺陷，数字不是 0 就值得看一眼。

### cron 库：croner

- 纯 JS，没有依赖，用 `Intl` 计算时区。`nextRun(起点)` 只算时间，不启动定时器。
- 上面的夏令时语义就是它的行为，测试里用 `America/New_York` 的切换日钉住，升级时不会悄悄变掉。日和星期取"或"不是它的默认行为的话，显式配置。
- 现在只有 `packages/domain` 用。插件运行时要在安装时校验表达式，到时候移进 catalog。

### 插件 API

不变。SDK `cron` 字段的注释补上这次定下的语义：错过的只补一次；上一次没跑完，这一次跳过；夏令时；日和星期取"或"。只改注释，不改类型。

## 后果

- 新迁移：`job_schedules`。新依赖：croner。
- 采纳时改写：
  - ADR-0021 的状态改为"已采纳（`job_schedules` 的列一条已被 ADR-0029 取代）"；
  - `docs/schema.md`：`job_schedules` 补上两列；`audit_logs` 的"不自动清理"和 `texture_files` 的"孤儿对象随第一个定时任务落地"两句改掉；落地顺序里"第一个定时任务"一行。
- 导入器复制材质文件，要照上传的流程先认领、再复制、再激活（schema.md 的"先认领再动对象"）。要是先复制、后插行，扫描可能在两步之间把文件当成孤儿认领掉。导入器为了 `created_at` 保留旧文件的修改时间时，1 天的宽限期也挡不住。
- 材质目录不能和 BS 共用。这一条本来就成立：NextSkin 回收文件时不知道 BS 还在引用它。孤儿扫描只是让后果来得更快：BS 在导入之后新上传的文件，NextSkin 的表里没有，一周之内就会被回收。要写进导入的说明。
- 多实例滚动升级期间，新旧版本给同一条目的表达式不同的话，两边会轮流把行改成自己的表达式，每次都从现在起重算，这个条目在升级期间可能一次都不触发。维护任务晚一天无所谓。
- 每 30 秒多一次读查询，走读连接；只有条目到期时才写入。
- 在四种数据库上做测试（假时钟）：
  - 两个调度器同时检查同一个到期条目，只入队一次；
  - 停机跨过三次触发时间，启动后只执行一次，再下一次是从现在起算的那一次；
  - 到期时上一次还没执行完，不入队，`next_run_at` 照样推进；
  - 改了站点时区或条目的表达式，下一次检查就按新的值重算；
  - `America/New_York` 夏令时切换的两天，每天一次的条目各执行一次；
  - 三个清理任务：边界上的行（刚过期、过期超过 1 天、撤销了但没过期的刷新令牌）、分批、续跑；孤儿认领时遇到已有行就跳过；临时文件只删失效认领的。
- `audit.retentionDays` 要在 i18n 的 `admin.settings.fields` 下补标签和说明，测试守着。

## 考虑过的其他方案

- **照 ADR-0021，表里只有两列，改时区时在设置的写入用例里重算**：设置用例要知道全部条目，包括插件的；条目的表达式改了也发现不了，要等旧的 `next_run_at` 到了才换成新的，周任务改成日任务要等上一周。
- **改时区时清空 `job_schedules`，让调度器重新插入**：同样发现不了表达式的改动。
- **cron-parser**：依赖 luxon，体积大得多，能力上没有多出我们要的东西。
- **自己写 cron 解析**：五段语法不难，难的是时区和夏令时，这正是要交给库的部分。
- **孤儿对象只记日志、不回收**：孤儿本来就访问不到（`/textures/{hash}` 只响应有行的文件），删了不会少掉任何能访问的东西，留着只占空间；schema.md 也已经为回收设计好了认领流程。真正危险的是和 BS 共用目录、导入器先复制后插行，这两种情况靠上面的约束解决，不靠不回收。
- **用 Better Auth 的 adapter（`deleteMany`）清理认证数据**：日期会按它的约定转换，但不能分批，第一次执行可能是一条很大的 DELETE。自己写只多一次 `writeAuthDate` 转换。
- **审计日志默认保留一年**：记录里有 IP，限制保留期更符合隐私要求；但升级之后自动删掉旧记录，是服主没有预料到的数据丢失。默认永久保留，由服主决定。
