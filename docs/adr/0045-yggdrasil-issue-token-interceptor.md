# ADR-0045 拦截点 `yggdrasil.issueToken`：签发能进服的令牌之前调用插件，覆盖启动器登录、刷新和 Connect 的令牌端点；失败时拒绝，不在事务内

- 状态：已采纳（网页上的受限操作由 ADR-0046 补充）
- 日期：2026-10-21
- 补充 ADR-0033："推迟"表里的拦截点多出一个，不在草案的五个里；取不到插件包时按拦截处理的规则推广到每个失败时拒绝的拦截点
- 补充 ADR-0030、ADR-0037：签发启动器令牌、Connect 签发带 Join 的令牌之前多一步

## 背景

一个要迁移过来的站点改过 BS 的代码：账号要先通过站外的聊天机器人绑定，才能用外置登录；网页照常登录，没绑定的人正是要先登录网站才能去绑定。站长想把它改成插件，需要两样东西：机器人能调的接口，和外置登录时的拦截。前者已经有了（插件路由，`auth: 'public'`，插件自己的请求头做令牌鉴权），后者没有：SDK 1.0 只有 `user.register` 一个拦截点（ADR-0033）。

现有的能力绕不过去：`yggdrasil.serverJoined` 是进服之后才投递的事件；passwordHasher 只接管核心认不出的哈希；插件也没有吊销令牌、封禁用户的写能力。

草案里有 `user.login`，收窄 SDK 时删掉了。它不合用：

- 它拦网页登录、第三方登录和通行密钥，这个场景要网页照常登录；
- 失败时放行。访问控制类的插件出错就放行，等于没装。

能进服的令牌有三个来源：

1. `authserver/authenticate`：启动器用密码登录；
2. `authserver/refresh`：每次都签发新令牌、删掉旧的，可以一直续下去；
3. Yggdrasil Connect 的令牌端点 `/oauth2/token`（ADR-0037）：授权码、设备码、刷新令牌三种 grant，签发带 `Yggdrasil.Server.Join` 的访问令牌，完全不经过 authserver。

只拦第一个，没绑定或已解绑的用户拿着旧令牌刷新、或者走 Connect，照样能进服。

## 决定

### 拦截点

```ts
'yggdrasil.issueToken': {
  input: {
    uid: Uid
    /** authenticate：启动器用密码登录；refresh：刷新启动器令牌；oauth：Connect 的令牌端点。次版本可能加成员 */
    via: 'authenticate' | 'refresh' | 'oauth' | (string & {})
  }
  patch: never
}
```

策略：`{ onFailure: 'closed', timeoutMs: 2000, transactional: false }`。

- **不在事务内**：上下文是完整的 `ctx`（`fetch`、`kv`、`jobs`、`db`，按能力读核心数据），插件可以去问外部服务。签发的事务在拦截器放行之后才开始，没有握着写锁等插件的问题，所以预算比 `user.register` 宽，留出一次出站请求的时间。
- **失败时拒绝**：抛错、超时、host 不可用、熔断中、返回值不对，都不签发。熔断沿用 ADR-0033：同一个插件的这个拦截点连续失败 3 次，30 秒内直接拒绝。
- **`scope`**：`actor` 是这个用户（`kind: 'user'`，带 uid 和身份），`locale` 是用户的界面语言、没有就用站点默认语言，`ip` 是客户端 IP（`clientIp()`，见 AGENTS.md）。
- **input 只有 uid 和 via**：邮箱、角色这些插件按能力自己读。不给角色：启动器登录时还可能没选角色，刷新时才选。

多个插件按 priority、插件 id 依次调用，任何一个拒绝就短路，和 `user.register` 一样。

### 在哪里调用

- **authenticate**：核对密码、封禁、邮箱验证都通过之后，签发事务之前。只有密码对了才调用，拦截器的拒绝说明不了账号是否存在；被拒绝不算一次登录失败，不进限流的失败计数。
- **refresh**：核对令牌、clientToken、封禁、角色归属（含这次新选的角色）之后，签发事务之前。被拒绝时旧令牌不删，绑定之后还能接着刷新。
- **Connect**：`/oauth2/token` 签发出访问令牌之后、已有的核对事务之前（`connect.ts` 的 after hook）。令牌的 scope 带 Join 才调用；只读角色、只做身份认证的令牌不调用。拒绝时删掉刚签发的访问令牌和它的刷新令牌，返回 `invalid_grant`。
  - 放在签发之后：三种 grant 的 scope 来自三个地方（授权码、设备码、旧的刷新令牌），签发之后从令牌行读最直接；封禁、`oauth_version` 的检查也在这个位置，同样是删掉再报 `invalid_grant`。
  - 代价：刷新令牌已经被 Better Auth 轮换掉，被拒绝的用户要重新授权。没绑定的用户本来就要先去绑定，可以接受。
- **不调用**：`validate`、`join`、`hasJoined`、`invalidate`、`signout`，以及网页登录、第三方登录、通行密钥。

### 拒绝时的响应

- authenticate、refresh：`ForbiddenOperationException`、403，`errorMessage` 是插件给的 message（截到 200 字符）。插件不可用时同样是 403，`errorMessage` 是核心的文案"外置登录暂时不可用，请稍后再试。"。用 403 而不用 5xx：启动器只把 `ForbiddenOperationException` 的 `errorMessage` 显示给玩家，5xx 多半显示成网络错误。
- Connect：`invalid_grant`，`error_description` 是插件的 message；插件不可用时是 `Token issuance is temporarily unavailable`。RFC 6749 要求 `error_description` 只用 ASCII，插件的 message 多半不是；这是玩家在启动器里唯一能看到原因的地方，取舍为照给。
- 协议契约（不变量 1）不受影响：没有插件拦截这个点时，三处的行为和响应都不变；BS 没有这个拦截点，也就没有要录制的用例。

### 插件启用着、本实例上却不可用

ADR-0033 的规则是：取不到这个版本的插件包，就不知道它拦不拦截注册，按拦截处理。现在推广到每个失败时拒绝的拦截点：

- 取不到包：按拦截全部这类拦截点处理，注册和外置登录都按失败策略拒绝；
- 有 manifest、只是没激活起来（例如激活失败）：按 manifest 里声明的拦截点处理。

### 解绑之后多久生效

已经签发的令牌不受影响，在 `yggdrasil.tokenValidSeconds`（默认 3 天）之内照常进服，之后刷新被拒。要立即生效，管理员在后台对这个用户"退出全部登录"（ADR-0036）。插件吊销令牌的写能力以后需要时按 ADR-0041 另加。

### 参考插件

需求来自站点自己的插件，高度定制（机器人的接口、旧数据的同步），不进仓库、不随发行包分发。仓库里用测试插件覆盖这个拦截点。这和 ADR-0033"只开参考插件用得到的部分"不冲突：用得到它的插件是真实存在的，只是不公开。

### SDK 和文档的改动

- `interceptors.ts`：类型和 `interceptorPolicies`；`type-tests`：这个拦截点的 `ctx` 有 `fetch`、`kv`，返回 patch 编译失败；
- 作者文档 `interceptors.md` 加一节；
- changeset：两个包都是次版本；
- 后台插件详情和安装确认里，拦截点显示成"外置登录：可以拒绝"。

### 测试

- 三处调用：拒绝时不签发（Connect 删掉已签发的令牌），响应是上面的样子；超时、抛错、host 不可用、熔断都拒绝；`via`、`scope` 的值；
- 没有带 Join 的 Connect 令牌不调用拦截器；
- refresh 被拒绝后旧令牌还在；authenticate 被拒绝不进限流的失败计数；
- 启用着却取不到包的插件让外置登录按失败策略拒绝；
- 拦截器里能用 `ctx.fetch`、`ctx.kv`。

## 后果

- 有插件拦截时，启动器登录、刷新和 Connect 换令牌各多一次跨进程调用；没有插件拦截时没有额外开销。
- 插件挂了，全站的外置登录和刷新都停下；已签发的令牌在有效期内照常进服。这是失败时拒绝的代价，站长装这类插件时要知道。
- 解绑不是立即生效，最多延迟一个令牌有效期。

## 考虑过的其他方案

- **照草案恢复 `user.login`**：拦网页登录，这个场景要网页照常登录；失败放行也不对。以后有插件需要拦网页登录，另加一个点。
- **在进服（`join`）时拦**：一处就覆盖两种令牌，解绑立即生效。但每次进服都要跨进程调用插件，进服对延迟敏感；失败时拒绝的话，host 一崩全站进不了服务器，已登录的玩家也一样。
- **只拦 authenticate，另给插件吊销令牌的能力**：插件要在解绑时自己吊销，漏了就绕过；Connect 的令牌也要吊销。拦签发更简单，也不依赖插件做对。
- **在 Connect 的批准页拦**：批准不是签发，刷新令牌照样续；批准页的预先检查只改善体验，以后需要再加。
- **允许插件把失败策略放宽成放行**：草案有过收紧的选项（`failClosed`），没有放宽的。拦截点的策略是契约的一部分，由核心决定。
