# ADR-0039 启动器：`nextskin` 只监管核心进程，plugin host 仍由核心拉起；命令行连同领域层打成单文件，随发行目录分发

- 状态：已采纳（`plugin` 命令推迟一节已被 ADR-0049 取代）
- 日期：2026-10-20
- 补充 ADR-0002：启动器的进程模型、停止和重启、配置、命令和发行目录；`plugin` 命令推迟
- 取代 ADR-0009 里"plugin host 是 `nextskin` 启动器拉起的一个子进程"一句、ADR-0033 里"启动器落地后，改由启动器拉起"一句：host 一直由核心进程拉起
- 补充 ADR-0021：任务执行器一直在核心进程里，"启动器落地之前"的限定去掉；停止时先收任务
- 补充 ADR-0031：命令行改名为 `nextskin import blessing-skin`；同一个数据目录上服务在运行时拒绝导入

## 背景

### ADR-0002 的设想

唯一入口是 `nextskin` 启动器：`start` 拉起核心进程和 plugin host、崩溃自动重启，另有 `migrate`、`import`、`doctor`、`plugin` 几条命令。宝塔的 Node 项目指向 `nextskin start`，服务器上不安装依赖、不编译。发行物是一个通用 ZIP 包和两种架构的镜像。

### 现状

- **运行方式**：生产环境只有 `node apps/web/.next/standalone/apps/web/server.js` 这一种（e2e 就这样跑，静态资源由 e2e 自己复制进产物）。没有发行目录。
- **核心进程**（Next standalone）在 `instrumentation.ts` 里打开核心：跑迁移、启动任务执行器和定时任务、拉起 plugin host。打开失败只记一行 `[core] open_failed`，进程照常运行，下一个请求重试。
- **plugin host** 由核心拉起：帧走 host 的 stdin/stdout；换代由核心发起（后台启用、停用、升级插件，以及每 5 秒和 `plugins` 表同步一次）；stdin 一断，host 自己退出。
- **停止**：核心没有处理。Next 收到 SIGTERM、SIGINT 时关掉 HTTP 服务、等在途请求结束，然后退出。执行中的任务被打断，等租约到期后重新执行（ADR-0021 允许这样）。`openCore` 返回的 `close()`（停定时任务、停执行器、关插件、断开数据库）只有命令行脚本调用。
- **命令行**：`set-role`、`set-password`、`disable-2fa`、`disable-captcha` 在 `apps/web/scripts/`，导入器在 `packages/importer/src/cli.ts`，都由 Node 直接运行工作区的 TS 源码。standalone 产物里没有这些源码，领域层只以 Turbopack 的 chunk 存在，从外面 import 不了。**所以正式部署里一条命令都用不了**，包括丢了超级管理员密码、验证码配错锁死后台时的救急命令。
- **standalone 的 `server.js`** 启动时先 `process.chdir(__dirname)`；监听地址读 `HOSTNAME`（Docker 和不少发行版把它设成机器名），端口读 `PORT`。数据目录默认是工作目录下的 `data`，于是会落进产物里面，升级换产物时一起被换掉。
- **文件追踪**把 `apps/web/data`（开发用的 SQLite 库和材质）带进了本地构建的 standalone 产物。
- **密钥**：生产环境必须设置 `NEXTSKIN_SECRET`，没有就打不开核心。
- **重复启动**：SQLite 上只能有一个服务进程，插件管理操作的锁在 SQLite 上是进程内的锁（ADR-0033"多实例"）。现在没有任何东西防止在同一个数据目录上启动两个服务。导入器要求服务停着，也没有检查。

### 验证：命令行打成单文件

用 rolldown（打包 plugin host 已经在用）把 `disable-captcha`、`set-role`、`set-password` 和导入器的命令行，连同领域层、官方插件一起打包，拷到仓库之外运行：

- 打包用时 0.5 秒，没有解析不了的依赖。不压缩共 6.2 MB（各入口加上共用的 chunk）。
- 对一个空的数据目录运行 `disable-captcha`：建库、跑完全部核心迁移、启动官方插件、执行用例、写审计，正常退出。
- 领域层里有两处 worker 不在 import 图里：`image-pool.ts` 的图像 worker 和 `plugin-reader.ts` 的 SQLite 只读连接。把它们加成额外的入口，再把 `new URL('./x.ts', import.meta.url)` 改写成产物里的文件名，就能加载（验证了图像 worker 能起来）。`pg-native` 是 `pg` 的可选依赖，设为外部依赖。
- 没有验证：打包后的 MySQL、PostgreSQL 驱动。落地时在四种数据库上各跑一遍打包后的 `migrate`。

## 决定

### 进程

```
nextskin start（启动器：读配置、锁数据目录、监管）
 └─ 核心进程：Next standalone 的 server.js（照旧打开核心、跑迁移、执行任务）
      └─ plugin host（照旧由核心进程拉起）
```

- **启动器只监管核心进程，plugin host 照旧由核心拉起。** 换代由核心发起，帧协议在核心和 host 之间直连。改由启动器拉起的话，每次换代核心都要请启动器开新一代，帧要经启动器中转或改走 socket，"核心退出、host 跟着退出"也要重新做。换来的只是 host 的生命周期独立于核心，而核心重启时插件本来就要重新加载。ADR-0009 的可选档位（unix socket、TCP、容器）不受影响。
- 任务执行器和定时任务一直在核心进程里，不拆成独立进程（ADR-0002 的单进程默认档位）。大站要把任务和网页分开时另议。
- 网页导入照旧在核心进程里运行，ADR-0031 的"在独立的进程里运行"仍然推迟。
- 启动器是常驻的第二个 Node 进程，只加载监管用的代码，不加载领域层。内存占用落地时实测，写进部署文档。

### 启动器和核心进程之间

- 启动器带 IPC 通道拉起核心进程，只传两种控制消息，不传业务数据：
  - 核心发给启动器 `ready`：打开核心之后发，打开失败（HTTP 照常服务）也发；
  - 启动器发给核心 `shutdown`。
  - Next 只在它自己的私有环境变量下用 IPC，启动器忽略不认识的消息。
- IPC 断开（启动器被强制结束）时，核心按收到 `shutdown` 处理，然后自己退出，不留孤儿进程。这和 host 对核心的做法一样（ADR-0033）。
- POSIX 上，核心进程放进自己的进程组。这样终端里按 Ctrl+C 只发给启动器，停止一律走下一节的顺序，不会被 Next 自己的信号处理抢先。Windows 上做不到：按 Ctrl+C 时核心按 Next 的处理直接关掉 HTTP 服务，执行中的任务等租约到期后接手。

### 停止

启动器收到 SIGTERM、SIGINT（Windows 上是 Ctrl+C 和关闭控制台）后，按下面的顺序停止：

1. 给核心发 `shutdown`。核心先停定时任务和执行器：不再认领新任务，等执行中的任务结束，最多等 10 秒（`jobs.stop` 现在的上限）；到时还没结束的 abort，等租约到期后由下次启动接手（ADR-0021）。这期间 HTTP 照常服务。
2. 核心按 Next 收到 SIGTERM 的流程关闭 HTTP 服务：不再接受连接，等在途请求结束，然后退出。host 的 stdin 随之断开，host 自己退出。Windows 没有信号，在进程内触发同一个处理函数。
3. 启动器从发出 `shutdown` 算起最多等 30 秒。核心还没退出就强制结束它，然后启动器以退出码 0 退出。

不经过启动器、直接给核心进程发 SIGTERM 也能停下，只是不做第 1 步，和现在一样。（落地时补充：宝塔停止项目、systemd 默认的 `KillMode=control-group` 会把 SIGTERM 同时发给启动器、核心和 plugin host（ADR-0040）。所以由启动器拉起的核心接管 Next 注册的 SIGINT、SIGTERM 处理函数，直接收到信号也照第 1、2 步停；plugin host 忽略 SIGTERM，和 SIGINT 一样等核心关掉 stdin 再退出，核心要强行结束它时发 SIGKILL。直接运行 `server.js` 时不接管，和现在一样。）

（落地时补充：启动器被强制结束时，IPC 通道断开，核心照同样的顺序自己停下；通道在核心注册监听之前就断开的，注册时发现后也停下。这时第 3 步的强制结束没人做了，核心自己从开始停止算起 35 秒后退出，例如数据库不回握手、核心一直打不开的时候。不留下锁外运行的核心。）

### 崩溃重启

- 核心进程退出、但不是启动器让它退出的，就算崩溃：记一行日志（退出码或信号），退避之后重新拉起。退避从 1 秒开始翻倍，上限 60 秒；核心发出 `ready` 之后连续运行满 5 分钟，退避清零。
- **不设放弃的上限。** 网站停着比日志里多几行更糟，宝塔这类环境外面也不一定有人再把它拉起来。外面还有 systemd、Docker 的重启策略时，两层并存，互不冲突。
- **配置错误不重启**：启动器在拉起核心之前先自己检查（见下面"启动前检查"），不通过就以退出码 78（`EX_CONFIG`）退出。外层可以据此不再重试，例如 systemd 的 `RestartPreventExitStatus=78`。
- 核心打开失败（连不上数据库、迁移失败）照现在的做法：HTTP 照常服务，每个请求重试，进程不退出，不算崩溃。日志照旧不带异常内容（不变量 11）。

### 配置

- **根目录**：发行目录里是 `nextskin.mjs` 所在的目录；在源码里运行命令时是 `apps/web`，和现在一样。
- **`.env`**：从根目录读，`NEXTSKIN_ENV_FILE` 可以改它的位置。已经在环境里的变量优先，不被 `.env` 覆盖（`process.loadEnvFile` 就是这样）。Docker 和面板里直接设环境变量就行。
- **相对路径按根目录解析，不按工作目录**：`NEXTSKIN_DATA_DIR` 默认是 `<根目录>/data`，`sqlite:` 后面的相对路径也一样。启动器把解析好的绝对路径传给核心进程。这样做是因为宝塔、systemd 的工作目录各不相同，`server.js` 还会切走工作目录。
- **监听地址**：`NEXTSKIN_HOST` 默认 `0.0.0.0`；`NEXTSKIN_PORT` 没有时取 `PORT`（面板常用），默认 3000。启动器把它们换成 Next 认的 `HOSTNAME` 和 `PORT`，继承来的 `HOSTNAME` 一律不用。
- **其余环境变量**原样传给核心进程（`NODE_OPTIONS` 等）。plugin host 的环境照旧是空的（ADR-0009）。
- **密钥**：
  - 生成的条件：环境里和 `.env` 里都没有 `NEXTSKIN_SECRET`，而且 `.env` 文件不存在。这时启动器生成 `.env`，写入一个随机的 `NEXTSKIN_SECRET`（32 字节，base64url）；POSIX 上文件权限是 0600。生成之后提示服主备份这个文件：丢了它，后台里保存的机密设置都要重新填。
  - 不生成、报错退出（78）的两种情况：
    - `.env` 已经存在，但里面没有密钥：不改这个文件；
    - 根目录不可写，例如镜像以非 root 用户运行：提示改用环境变量给出密钥。
  - 适用范围：所有要打开核心的命令都按这条规则，服主可以先跑导入、后启动服务。
  - 不写进数据目录：数据目录常常被整个备份、拷走，密钥和它加密的库放在一起就失去了意义。

### 启动前检查

`start` 按下面的顺序检查，任何一项不通过就以退出码 78 退出，一行写明原因和怎么改：

1. **Node 版本 ≥ 24**；24、25 上提示 plugin host 拦不住插件直接连网（ADR-0033），建议用 26。入口文件 `nextskin.mjs` 只用旧版 Node 也能解析的语法：先查版本，再加载其余代码。这样用太旧的 Node 运行时，服主看到的是这句提示，而不是语法错误。
2. **配置**：按上一节读配置，检查密钥长度和 `NEXTSKIN_DATABASE_URL` 的格式，规则同 `coreConfigFromEnv`。这部分解析从 `bootstrap.ts` 拆成不依赖数据库驱动的模块，启动器和核心共用。
3. **数据目录**能创建、能写。
4. **锁数据目录**：一个数据目录同时只能有一个 `start` 在用。
   - 锁的实现：数据目录里有一个 `nextskin.lock`，启动器用 `node:sqlite` 打开它，开一个排他事务、一直不提交。拿不到锁，就说明已经有服务在用这个数据目录。
   - 进程不论怎么退出，操作系统都会释放文件锁，不会留下要手动删除的锁文件。也不需要原生依赖（ADR-0008）。
   - （落地时补充：拿不到锁时先等，最多 40 秒，等的时候提示一行；还拿不到才以 78 退出。宝塔重启项目时发完 SIGTERM 只等 0.5 秒就启动新的，上一个实例可能还在收任务（ADR-0040）。上一个启动器 30 秒后强杀核心，核心自己 35 秒兜底，40 秒够它放开锁。`start` 从一开始就接住停止信号，等锁时收到就放弃、以 0 退出，不再拉起核心：作为容器的 PID 1 时，没有处理函数的 SIGTERM 会被内核忽略。）

启动器不连数据库、不跑迁移。迁移照旧在核心打开时执行（`openCore`），`pnpm dev` 和命令行也是这一条路径。多个实例同时启动时，由迁移的锁表排队（Kysely）。

### 命令

在发行目录里运行 `node nextskin.mjs <命令>`；在源码里运行 `pnpm nextskin <命令>`，原来的 `pnpm set-role` 等脚本去掉。

| 命令 | 说明 |
|---|---|
| `start` | 见上面几节 |
| `migrate` | 执行核心的迁移，列出这次执行了哪些。用于在切换流量之前单独升级 MySQL、PostgreSQL 上的库；`start` 照旧会自动迁移 |
| `set-role`、`set-password`、`disable-2fa`、`disable-captcha` | 从 `apps/web/scripts/` 搬过来，参数和行为不变 |
| `import blessing-skin` | 原来的 `pnpm import:bs`，参数不变（ADR-0031）。拿不到数据目录的锁（同一个数据目录上服务在运行）就拒绝 |
| `doctor` | 环境自检，见下一节 |
| `version`、`help` | |

- 除了 `start`，其余命令照旧不启动任务执行器、不运行安装插件（`openCore` 传 `startJobs: false`，不传 host）。除了导入，都可以在服务运行时执行，和现在一样。
- 命令读的 `.env` 和环境变量与 `start` 相同，相对路径同样按根目录解析，所以在别的目录里执行也打开同一个库。
- 官方插件的清单从 `apps/web/lib/official-plugins.ts` 挪进一个包，核心和命令行共用。
- 退出码沿用各命令现在的约定，配置错误统一为 78。
- 输出沿用现在命令行脚本的做法，直接写中文，不进 i18n。

**`plugin` 命令推迟**，理由有三条：

- 后台的插件页已经够用；
- 插件不会把管理员锁在外面：passwordHasher 只影响插件格式的哈希，超级管理员可以用 `set-password` 找回；
- 在 SQLite 上，插件管理操作的锁是进程内的锁，另一个进程改插件的状态会绕过它（ADR-0033）。

### doctor

逐项列出通过、警告和失败，有失败时退出码非 0。输出不写密钥和连接串（不变量 11），数据库只写方言、主机和库名。检查以下几项：

- Node 版本，以及权限模型能不能拦住网络；
- `.env` 在不在、密钥长度够不够；POSIX 上 `.env` 别人可读时警告；
- 数据目录能不能写，剩余空间；
- 数据库连不连得上，迁移状态：
  - 有没有还没执行的迁移；
  - 库里有没有程序不认识的迁移。有的话说明库比程序新，旧版本打不开它；
- plugin host：`host.mjs` 在不在，能不能带着 `--permission` 起来、完成握手；
- 服务在不在运行（看数据目录的锁）；在运行的话，请求本机的监听地址，看能不能响应。

### 日志

- 核心进程的 stdout 和 stderr 直接继承；启动器自己写的行带 `[nextskin]` 前缀。日志文件和轮转交给面板、systemd、Docker。
- 启动时，启动器写一行版本、Node 版本、数据目录、数据库方言和监听地址。核心 `ready` 之后，站点还没安装的，提示打开 `/setup`、安装码在哪个文件，不写安装码本身。

### 发行目录

`pnpm build` 在 `dist/nextskin/` 组装出发行目录，ZIP 包和镜像都从它打出来：

```
nextskin/
├─ nextskin.mjs     入口：查 Node 版本，再加载 cli/
├─ cli/             启动器和命令行的其余代码、两个 worker
├─ server/          Next standalone（带 .next/static、public 和 plugin host 的 host.mjs）
├─ package.json     只有 "scripts": { "start": "node nextskin.mjs start" }，没有依赖
├─ .env.example     全部环境变量和说明
└─ data/            运行时创建，不在包里
```

- 不需要 `npm install`，不编译（ADR-0002）。`package.json` 是为了让面板和 `npm start` 找到启动命令；宝塔、1Panel 的 Node 项目怎么选启动命令，落地时在两个面板上实测，写进部署文档。
- 不带 Node：带了就要按平台和架构分包，和通用 ZIP 冲突。
- **升级**：停服务，换掉除 `.env` 和 `data/` 之外的文件，再启动，迁移在启动时执行。旧版本的程序打开新版本迁移过的库时，迁移器会拒绝（库里有它不认识的迁移），不会弄坏数据。要回退，就连库一起恢复备份。
- **产物里不能带构建机上的东西**：standalone 的文件追踪现在会带进 `apps/web/data`，在 `next.config.ts` 里排除它。组装时检查产物里有没有 `data/` 和 `.env*`，有就构建失败。（落地时补充：`outputFileTracingExcludes` 只作用于路由的追踪，开发数据是经 instrumentation 和 proxy 的追踪带进来的，排除不了；Next 还会把 `apps/web/.env`、`.env.production` 原样复制进 standalone。两样都改在组装时跳过，检查照旧。）
- e2e 改成从 `dist/nextskin` 用启动器启动全部服务，用打包后的命令行设定身份。这样 CI 就覆盖了启动器、打包和发行目录。
- ZIP 包和镜像的发布流程另写 ADR，包括版本号、CI、校验和，以及镜像的基础镜像、PID 1、`stop_grace_period`（`docker stop` 默认只等 10 秒）。镜像的约束先记在这里：
  - 配置全部经环境变量给出；
  - `data/` 是卷；
  - 根目录只读、以非 root 用户运行。所以镜像里不会自动生成 `.env`，没给密钥就报错。

### 落地

分两个切片：

1. **启动器和命令行**：

- 正式部署第一次有了救急命令。发行目录可以直接打成 ZIP 包和镜像。
- 发行目录里多一份领域层的代码（命令行的包，不压缩约 6 MB），和 Next 产物里的那份重复。

## 考虑过的其他方案

- **启动器拉起 plugin host**（ADR-0009、0033 原来的写法）：理由见"进程"。
- **不做进程监管，交给面板、systemd、Docker**：多数环境外面确实有这一层，但 `nohup`、Windows 的控制台窗口和一部分面板没有。启动器本来就要负责配置、路径、锁和命令行，多监管一个子进程的代价很小。
- **命令行经运行中的服务执行**（管理接口或本机 socket）：救急命令恰恰是在服务起不来、管理员登录不了的时候用；导入还要求服务停着。
- **在发行目录里直接运行 TS 源码**（Node 的类型剥离）：要带上整个工作区的 `node_modules`，而且 Node 不剥离 `node_modules` 里的 TS。
- **启动器在拉起核心之前跑迁移**：比现在多一条和 `pnpm dev`、命令行不同的路径，没有好处。
- **用 pid 文件防止重复启动**：进程被强制结束后会留下陈旧的文件，要判断那个 pid 还在不在，pid 又会被复用。
- **`start` 不生成密钥，要服主自己写**：总有人会写一串容易猜的字符。
