# ADR-0031 BS 导入器：安装向导、后台和命令行共用一个导入引擎，每次运行整库替换，在一个目标库事务里写完；不经过领域用例；报告逐个比对全部角色

- 状态：已采纳（Janus 标记的公共客户端、整库替换时保留公用应用由 ADR-0037 补充）
- 日期：2026-10-18
- 取代 ADR-0006 里对账报告"抽样比对"的部分，ADR-0006 的其余部分不变
- 补充 ADR-0004：导入器直接写表，是"写操作只能经过领域用例"的唯一例外
- 补充 ADR-0027：具名权限加一项"数据迁移"；第一个超级管理员也可以在安装向导里创建

## 背景

ADR-0006 定了大方向：
- 导入命令 `nextskin import blessing-skin --from <dsn>`；
- 只读旧库，幂等，可以先试跑、切换前再做一次最终同步；
- 结束时输出对账报告：各表行数、材质文件是否存在、抽样比对结果。

逐表的导入规则已经写在 `docs/schema.md` 的"从 BS 导入"：
- 各表的列对照、引用失效时跳过还是置空；
- 必须停止的三种冲突：重复的邮箱、重复的角色名、两个角色同一个 UUID；
- UUID 候选值的收集和裁决、设置项对照、不导入的数据。

其他 ADR 补充过的：
- ADR-0015：时区默认 `Asia/Shanghai`，可以用命令行参数覆盖；导入前检查最大 id，导入后同步自增序列。
- ADR-0022、0025、0026：各种 `score_paid` 的算法。
- ADR-0027：第一个超级管理员现在只能用 `pnpm set-role` 设定。
- ADR-0030：网页登录要不要也接受 trim 之前的密码，留给导入器。

服主大多不熟悉命令行。BS 的安装是网页上的 `/setup` 向导：填数据库、站点信息和管理员账号就装好了。迁移也应该能在网页上完成：刚装好的站点在安装向导里直接导入，已经在用的站点（例如切换前的最终同步）从后台发起。

还没定的：
- 导入引擎放在哪，网页和命令行怎么共用它；
- 安装向导的流程，以及公网上刚装好、还没有管理员的站点怎么防止被别人抢先安装；
- 网页上发起的导入怎么在服务里运行：耗时几分钟，期间站点处于什么状态，进度怎么显示；
- "幂等"和"最终同步"具体怎么做，怎么避免把新站自己的数据冲掉；
- 材质文件怎么复制，像素 hash 怎么算；
- 导入器和"写操作只能经过领域用例"（不变量 4）的关系；
- 报告的格式，以及"抽样比对"比对什么；
- 怎么测试。

录制环境里 BS 6.0.2 的实际情况（`tests/contract/bs-v6`）：
- 时区写死在 `config/app.php`；
- 材质目录默认是 `storage/textures`，`.env` 的 `TEXTURES_DIR` 可以改，`FS_DRIVER` 还可以换成非本地的存储；
- 表名带 `.env` 的 `DB_PREFIX`；
- `oauth_clients` 的时间列是 `timestamp`，其余是 `datetime`，两种都是 Laravel 按应用时区写进去的本地时间。

## 决定

### 形态

导入引擎在新包 `packages/importer`，三个入口共用它：

| 入口 | 什么时候用 | 运行方式 |
|---|---|---|
| 安装向导 `/setup` | 刚装好的站点，第一次导入 | 在服务进程里作为后台任务运行，站点进入维护模式 |
| 后台的"数据迁移" | 已经在用的站点：切换前的最终同步，或者用"新站"建好的站点后来要导入旧数据 | 同上 |
| 命令行 | 多实例部署、自动化脚本、超大的站点 | 启动器落地之前用根目录的 `pnpm import:bs -- <参数>`，之后是 `nextskin import blessing-skin`。服务要停着 |

- 引擎提供进度回调和取消信号，三个入口只是不同的外壳。
- 包的依赖方向：
  - `packages/importer` 依赖 `@nextskin/db` 和 `@nextskin/domain`，用后者的设置编码、密码格式、名字规范化、图像解码和材质存储；
  - 网页用的导入服务由 `apps/web` 在创建核心时一并创建，注入 Hono 应用；
  - `packages/api` 只依赖它的接口类型，不依赖 `@nextskin/db`（不变量 4 的包依赖规则不变）。
- 命令行打开目标库用和 `pnpm dev` 相同的环境变量（`NEXTSKIN_DATABASE_URL`、`NEXTSKIN_DATA_DIR`、`NEXTSKIN_SECRET`），开始前把核心迁移跑到最新。命令行运行时服务要停着：导入会改写整个库，`core:texture-sweep` 也会回收存储里没有记录的文件。导入器不探测服务是否在运行，迁移指南里写明。

### 安装向导

- `/setup` 只在站点**未初始化**时可用：没有用户，`import_runs` 里也没有成功的导入。初始化之后访问它返回 404。
- **安装码**：
  - 服务启动时发现站点未初始化，就生成一个随机安装码，写进数据目录的 `setup-code` 文件，只有运行服务的用户能读；日志里只提示文件的位置，不打印安装码（不变量 11）。
  - 进入向导要先输入安装码。公网上刚装好的站点谁都能打开 `/setup`，没有这一步，别人可以把站点导成自己准备的数据、拿到超级管理员。BS 的 `/setup` 没有这层保护。
  - 安装完成后删除这个文件。
- 两条路：
  - **新站**：站点名称、站点地址（默认是当前访问的地址），超级管理员的邮箱、昵称和密码。经过领域用例创建（新增"创建第一个超级管理员"的用例），完成后直接登录。`pnpm set-role` 保留，用来找回管理员。
  - **从 BS 导入**：见下面的步骤。

### 导入的步骤（安装向导和后台共用）

1. **旧站的 `.env`**：上传或粘贴。从里面取数据库连接、表前缀、密码算法（`PWD_METHOD`）、盐（`SALT`）、材质目录（`TEXTURES_DIR`），填进下一步的表单。没有 `.env` 也可以跳过，手动填。
2. **连接和路径**：
   - 数据库的类型、地址、端口、库名、用户名、密码、表前缀；
   - 材质目录：NextSkin 所在机器上的路径，NextSkin 进程要能读，也就是同一台机器，或者把旧站的目录挂载进容器；
   - 时区。
   - 点"检查"：连上旧库，认出 BS 的表和插件（yggdrasil-api 或 yggdrasil-connect 的 `uuid` 表），确认材质目录可读、抽查几个文件。
3. **试跑**：即命令行的 `--dry-run`，完成后显示报告。有停止类问题时不能继续；报告里写着在旧站怎么处理，处理完重新试跑。
4. **确认**：
   - 站点地址：默认是当前访问的地址，覆盖导入的 `site_url`，因为迁移时常常换了域名或端口；
   - 从后台发起时，列出将被删除的新站数据（用户数、角色数、材质数，以及导入之后新站产生的数据），要求勾选确认。这对应命令行的 `--replace` 和 `--force`。
5. **导入**：显示进度（当前阶段、已处理的行数和文件数），可以取消。
6. **完成**：显示报告，可以下载 Markdown。提示用旧站的账号登录：导入替换了全部用户，发起导入的会话也不在了。

### 后台的"数据迁移"

- 只有超级管理员能用：新增一个具名权限，只映射给超级管理员（ADR-0027 的做法）。
- 列出历次运行（试跑和导入）的时间、结果和报告；"开始导入"走上面的步骤。
- 表单预填上一次的非机密项：类型、地址、端口、库名、用户名、表前缀、材质目录、时区。数据库密码和盐每次重新输入，或者重新上传 `.env`。

### 在服务里运行

- 导入作为后台任务在服务进程里运行，不让请求一直等着：大站要几分钟。同时只能有一个运行。
- 运行期间站点进入**维护模式**，试跑也一样。试跑同样在目标库的事务里写入再回滚：SQLite 上一直占着写锁，MySQL、PostgreSQL 上锁住所有业务表，站点本来也用不了。
  - 页面显示维护页，协议端点和 REST 接口返回 503 和 `Retry-After`；向导、进度和取消接口除外。
  - 任务执行器和调度器暂停。
- **进度只在内存里**：导入事务提交之前，SQLite 上别的写入都要排队，进度写不进库。开始和结束时写进 `import_runs`。因此网页导入要求单实例部署，多实例的站点用命令行；向导和后台在检测到多实例配置时提示这一点。
- **进度页认运行令牌，不认会话**：开始导入时发一个只用于这次运行的令牌（HttpOnly Cookie），进度和取消接口认它。导入会替换用户表，发起人的会话随之失效。
- **取消**：中止读取，目标库事务回滚。
- **进程中途退出**：数据库自己回滚事务；下次启动时，把 `import_runs` 里还在 `running` 的记录标为失败，退出维护模式。
- **机密**：数据库密码和盐只在这次运行的内存里，不写进 `import_runs`，日志里也不出现（不变量 11）。盐导入后按 schema.md 存进机密设置 `auth.legacyPasswordSalt`，加密保存。

### 命令行的参数

网页表单的各项与这些参数一一对应。

| 参数 | 说明 |
|---|---|
| `--from <dsn>` | 旧库：`mysql://…`、`postgres://…` 或 `sqlite:<文件>`。BS 支持的三种数据库都能导 |
| `--bs-env <文件>` | 旧站的 `.env`，从里面读 `PWD_METHOD`、`SALT`、`DB_PREFIX`、`TEXTURES_DIR` |
| `--textures <目录>` | 旧站的材质目录，覆盖 `.env` 里的值 |
| `--timezone <时区>` | 默认 `Asia/Shanghai`；改过 `config/app.php` 的站点要传。同时写进 `site.timeZone` |
| `--site-url <地址>` | 覆盖导入的 `site_url` |
| `--uuid-overrides <文件>` | 逐个指定角色的 UUID，用来裁决 UUID 冲突（schema.md "UUID" 第 5 条）。JSON：`{ "<pid>": "<uuid>" }`。网页上在试跑报告的冲突旁边逐个选择 |
| `--dry-run` | 完整跑一遍、生成报告，最后回滚，不复制文件 |
| `--replace` | 重跑时必须加，见"每次运行整库替换" |
| `--force` | 发现导入之后新站产生的数据时仍然继续 |
| `--report <文件>` | 报告的位置，默认是数据目录下的 `import-<时间>.md` |

- 盐不能从命令行传：命令行参数在进程列表里看得见。只从 `.env` 读，或者从环境变量 `BS_SALT` 读。
- 没有给 `.env` 时，密码算法默认 `BCRYPT`。如果旧库里有不是 bcrypt、argon2 格式的密码哈希（十六进制摘要），就停止，提示提供 `.env`：不知道算法就导入，这些用户全都登录不了。网页上同样检查。
- 旧站的材质不在本地磁盘上（`FS_DRIVER` 不是 `local`）时，先同步到本地目录再导入。

### 读旧库

- 只读打开，整个读取在一个快照里完成：
  - MySQL、MariaDB：`START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY`；
  - PostgreSQL：`REPEATABLE READ READ ONLY`；
  - SQLite：只读模式打开文件。
- 旧站没停时试跑，读到的也是某一时刻的一致数据。材质文件不在这个快照里，所以最后一次同步时旧站仍然要停（schema.md "通用规则"）。
- 按主键分页读，内存里只留查冲突要用的键（邮箱、角色名、UUID），数据量和站点规模无关。
- 按名字关联 UUID 的查询在旧库里执行，比较规则和 BS 运行时一致（schema.md）。
- 列出旧库里认不出的表和它们的行数，例如其他插件的 `mojang_verifications`，提醒服主这些数据没有迁移。

### 每次运行整库替换

- 每次运行都从旧库重新导入全部数据：
  - 在**一个目标库事务**里，清空导入涉及的表，再写入；
  - 发现要停止的问题、中途出错或被取消，整体回滚，目标库保持上一次的状态；
  - 试跑走同一条路径，最后总是回滚，所以试跑的报告和真正导入的完全一样。
- 不做增量同步。BS 的表没有更新时间，删除也不留痕迹，靠比对两边找出改动和删除既慢又容易漏；整库替换天然满足"结果与旧库当时的状态一致，包括旧库里删掉的数据"。
- 停止类问题先收集、读完再判断，一次报告全部问题，不在遇到第一个时就停。服主改完旧站重跑一次就能看到是否都解决了。
- 清空的范围：
  - 所有业务数据：用户（连同级联的账号、会话、角色、衣柜、令牌等）、材质、材质文件、举报、OAuth 客户端、积分流水、审计日志、任务；
  - 保留站点自己的配置和导入记录：`settings` 里导入器不写的键、Better Auth 的 `jwks`、`job_schedules`、`import_runs`、迁移记录。
- 什么时候能写：
  - 目标库**没有业务数据**（新装、刚迁移完）：直接导入。
  - 目标库有数据、并且来自上一次导入（`import_runs` 里有成功的导入）：命令行要加 `--replace`，网页上要勾选确认。
  - 发现上一次导入之后新站产生的数据（会话、OAuth 令牌、不是"导入"的积分流水、导入之后创建的用户），或者目标库有数据却从没导入过（用"新站"建的站点）：停止并列出这些数据，命令行再加 `--force`、网页上再勾选一次"删除新站的数据"才继续。这时多半已经切换上线或者新站已经在用，再导入会冲掉玩家在新站的操作。

### import_runs

新表，每次运行（试跑和导入）一行：
- 状态：运行中、成功、有停止类问题、失败、已取消；是否试跑；开始和结束时间；
- 入口（安装向导、后台、命令行）；发起人的邮箱快照：用户表会被替换，不建外键；
- 旧库的标识：类型、地址、库名、表前缀，不含密码；材质目录和时区；
- 报告（JSON）。

"站点是否初始化""有没有导入过""上次导入之后新站有没有产生数据"都按这张表里最近一次成功的导入判断。

### 材质文件

- 文件按原字节复制（不变量 3），按 hash 存进 NextSkin 的材质存储，在目标库事务之外进行。存储里已经有、大小相同的文件不再复制，所以大站重跑只复制新增的文件。回滚后多出来的文件由 `core:texture-sweep` 回收（ADR-0029）。
- 像素 hash、宽高按上传的规则解码、规范化后计算（`@nextskin/skin`），与新上传的文件一致，上传查重才能命中导入的旧文件。只解码，不重新编码。
- 规范化取决于材质类型（例如窄披风要补宽）。一个文件被几种类型的材质引用时，按 `tid` 最小的那条材质的类型算。
- 能解码、但尺寸不合 NextSkin 规则的旧文件照样导入，像素 hash 按解码出的原图算，在报告里列出。解码不了的按 schema.md 跳过。
- 重跑时，目标库上一次导入的 `texture_files` 里已经有同一 hash、同样大小的行，直接沿用它的像素 hash 和宽高，不再解码。
- 解码放进图像 worker 池（ADR-0025），大站有几十万个文件。

### 写入：不经过领域用例

- 导入器直接写表：用 Kysely 和 `packages/db` 的辅助函数，按四种数据库的约定（不变量 6），分批插入。
- 这是不变量 4 的唯一例外，只限 `packages/importer`，网页发起的导入也一样：
  - 导入期间站点处于维护模式（命令行运行时服务停着），没有并发的用户操作；
  - 导入的是历史状态，不该触发事件、拦截器、审计日志，也不该按现价扣积分。领域用例做的恰恰是这些。
- 安装向导的"新站"不属于这个例外，经过领域用例创建管理员。
- 积分流水只按 schema.md 写一条"导入"。
- 写完对每张表同步自增序列（ADR-0015）。

### 对账报告

报告是结构化的数据（JSON）：网页上直接渲染，存进 `import_runs`；命令行和网页的下载按同一份数据生成 Markdown。内容：
- 各表：旧库行数、导入数，跳过和置空的数量，按原因分列。
- UUID：
  - 每个角色 UUID 的来源：按 pid、按名字、离线算法生成、随机生成、指定；
  - 名字不完全相同的映射行，没有对应角色的映射行数；
  - schema.md 要求单独列出，这一节放在最前面。
- 文件：缺失、无法解码、尺寸不合规则的，复制了多少、沿用了多少。
- 设置：
  - 导入了哪些、取了边界值的；
  - 不导入但不是默认值的；
  - 公告和内容政策的其他语言版本、含原始 HTML 的。
- 衣柜和举报：去掉的重复行；点赞数重新统计后与旧库不同的材质。
- 认不出的表。
- **比对**：导入完成、提交之前，在同一个事务里用协议端点同一套查询（`players/queries.ts`）把**全部**角色读回来，与旧库比对 UUID、皮肤和披风的 hash、模型。比对不一致是停止类问题。全部比对代价不大，比抽样更能说明结果。
- 停止类问题放在开头，每条写清楚在旧站怎么处理。

命令行的退出码：0 成功；1 有停止类问题，目标库没有改动；2 参数错误、连不上数据库。

### 密码：网页登录也接受 trim 之前的值（ADR-0030 留下的）

- BS 的 TrimStrings 对网页登录和注册同样生效，旧站的哈希是按 trim 之后的密码算的。习惯在密码末尾带空格的用户，在旧站能登录，导入后网页登录会失败。
- 网页登录核对**旧格式**的哈希时，按原值不通过、原值首尾又有空白，就再按 trim 之后的值核对一次。通过后，按 trim 之后的值换成当前算法的哈希。
- 当前算法的哈希按原值核对：在 NextSkin 设置的密码，首尾的空格是密码的一部分。

### 界面

- 安装向导和后台的导入步骤共用一套组件。`packages/ui` 补两个组件，照 AGENTS.md 配 story 和截图基线：步骤条（像素字体的步骤序号，`text-pixel-3`），进度条。
- 安装向导是全屏的单列流程，不套用户中心和后台的外壳；维护页同样。
- 报告页按结构化数据渲染：停止类问题和 UUID 在最前面，其余分节折叠。

### 测试

- **四种数据库**上的测试（`*.db.test.ts`）：
  - 源库和目标库各用一个测试库。源库按 BS 6.0.2 的迁移建表，列类型照抄，`uuid` 表有 yggdrasil-api 和 yggdrasil-connect 两种结构；
  - 写入覆盖 schema.md 每一条规则的数据，导入后逐条检查；
  - 停止类问题、试跑、重跑、`--replace` 和 `--force` 的保护、取消、回滚后目标库不变，都要测。
- UUID 是后果最严重的一项（ADR-0006）：pid 和名字两类候选值、大小写不同的名字、带连字符的旧格式、冲突、指定、离线算法和随机算法，都要有专门的用例。
- **网页**：
  - API 测试：未初始化之外访问 `/setup` 的接口一律 404，没有安装码、安装码错误被拒绝；维护模式下各类端点返回 503，向导和进度接口不受影响；运行令牌；同时只能有一个运行；
  - e2e：安装向导的两条路。导入那条用一个按 BS 表结构建的 SQLite 文件作旧库（BS 支持 SQLite），不需要 Docker：试跑、处理冲突后重新试跑、导入、用旧站的账号登录。
- **录制环境上的端到端检查**，手动运行，和录制一样需要 Docker：
  - `tests/contract` 加一个脚本，把 BS 录制环境（录制脚本写入的固定数据）导入一个新的 SQLite 库，再用它回放契约用例；
  - 固定数据里有意制造的"导入之后存储里丢了文件"的材质（`world.ts` 的 `stored: false`），真实导入时会因为缺文件被跳过，这几个用例列为已知差异，不比较；
  - 这样旧站真实的表结构、密码哈希和 UUID 分配，都经过一次"导入后协议行为不变"的检验。

### 落地顺序

分两步：
1. 导入引擎、`import_runs`、报告、命令行，以及网页登录的 trim 回退；四种数据库的测试和录制环境上的检查。
2. 安装向导（含"新站"）、后台的"数据迁移"、维护模式、两个新组件；API 测试和 e2e。

### 不做

- 增量同步：见上。
- 网页导入的多实例支持：进度在内存里，见"在服务里运行"。启动器落地后，可以改为由启动器拉起独立的导入进程，到时另议。
- 旧站链接跳转（ADR-0006 提到的 301）：属于网页路由，等对应的页面落地时再做。
- 其他插件的数据：texture-description 的描述按 schema.md 导入；其余（包括 `mojang_verifications`）只在报告里列出。
- 导入站内信、Yggdrasil 操作日志等 schema.md "不导入的数据"列出的内容。
- 通过上传压缩包导入材质：大站的材质有几个 GB，上传不现实；材质目录要能被 NextSkin 进程直接读到。

## 后果

- 新包 `packages/importer`，根目录加 `import:bs` 脚本；新表 `import_runs`；`packages/importer` 写一份迁移指南：试跑、处理冲突、停旧站、最终同步、切换。
- `docs/schema.md`：
  - 加 `import_runs` 的表；
  - "从 BS 导入"补上清空的范围、"能不能写"的判断、`--uuid-overrides` 的格式、像素 hash 的算法；
  - "落地顺序"加上导入器这一行。
- 不变量 4 多了一个只限导入器的例外，写进 AGENTS.md 那一条的说明里。
- ADR-0027：第一个超级管理员可以在安装向导里创建，`pnpm set-role` 改为找回管理员的手段；新增"数据迁移"的具名权限。
- 新增维护模式：Next 的 `proxy.ts` 和 Hono 都要认它，任务执行器和调度器要能暂停。
- 新增领域用例"创建第一个超级管理员"，以及安装码的生成和校验。
- 改 `auth/password.ts`：旧格式哈希的 trim 回退，网页登录和 authserver 共用。
- 大站一次导入的时间主要花在解码文件上。第一次导入之后，重跑只解码新增的文件。
- 整库替换意味着最终同步的停机时间等于一次完整导入的时间，复制文件除外。几十万用户的站点大概是分钟级；迁移指南里写明先试跑估时。

## 考虑过的其他方案

- **只做命令行**：实现最简单，但服主大多不熟悉命令行，BS 的安装本来就是网页向导；迁移是服主换到 NextSkin 的第一步，体验不能比 BS 的安装更难。
- **安装码打印在日志里**：Jenkins 等软件这么做，最方便；但日志常常被收集、转发，违反不变量 11。写进只有服务用户能读的文件，服主一样拿得到。
- **网页导入在独立的进程里运行**：进度能写进库，多实例也能用，取消和崩溃都不影响服务进程；但现在没有启动器来拉起和监管这个进程。等启动器落地后再考虑。
- **增量同步**（按主键比对两边，只写改动的行）：最终同步更快，但 BS 的表没有更新时间，判断一行改没改要比较全部列，删除也要全量比对才能发现。复杂度和出错的机会都换不来多少停机时间：慢的是解码文件，而重跑本来就不再解码。
- **导入器通过领域用例写入**：会触发事件、审计日志和按现价收费，导入的却是历史状态；逐条走用例也慢几个数量级。
- **先完整检查一遍，再另读一遍写入**：要读两次旧库，两次之间旧库可能变了，检查过的不一定是写入的。单遍读、在一个目标库事务里写，有问题就回滚，检查的和写入的是同一份数据。
- **抽样比对**（ADR-0006 原来的说法）：全部比对的代价是每个角色一次查询，大站也就几分钟，不必冒漏掉个别角色的险。
